# Tadayo technical design

Version 1.0 · 1 November 2026

The build specification (`docs/tadayo-build-spec-v3.md`, "the spec") fixes the product rules, the data model, the API contracts and the acceptance tests. The design book (`docs/tadayo-design-book-2.1.md`, "the book") fixes the visual system and the interaction contracts. This document is the founder's CTO layer on top of them. It covers:
- the concrete stack and the hosting;
- how Claude Code builds an iPhone app from a Linux session with no Mac;
- the repository, CI and the environments.

Follow it. To change a decision, write an ADR in `docs/DECISIONS.md` with your reasons and evidence, raise it in the PR, and wait for the founder's answer before building on it. Where this document says "you choose", decide, record it in `docs/DECISIONS.md` and note it in the PR.

## 1. Platform and stack

| Layer | Choice | Why |
|---|---|---|
| iOS app | Swift 6 and SwiftUI. iOS 17 minimum until the founder confirms the phones (FQ4), built with the newest Xcode on GitHub's `macos-26` image, pinned in the workflow. Targets: `Tadayo` (the app) and `TadayoShare` (the share extension, screen C04). `TadayoWidgets` joins in M1 (FQ9). Both targets carry a privacy manifest and `ITSAppUsesNonExemptEncryption = NO` | iPhone first (ADR-001). The book asks for native navigation, sheets, pickers, keyboard and share extension (book p35, p50) |
| Shared Swift code | Swift packages under `packages/swift/`: `TadayoCore`, `TadayoAPI`, `TadayoDesign` | `TadayoCore` and `TadayoAPI` compile and test on Linux. They use Foundation, Observation, swift-crypto (CryptoKit's API on Linux), and the OpenAPI runtime with its URLSession transport. Never SwiftUI, UIKit or Combine. The keychain sits behind a protocol that the app implements. `TadayoDesign` imports SwiftUI and compiles only on CI |
| Project file | Generated by XcodeGen from `apps/ios/project.yml`; the `.xcodeproj` isn't committed | A project file edited without Xcode breaks; a generated one is reviewable |
| API and worker | TypeScript strict on Node 26 LTS, which ships the Temporal API, Fastify 5, zod schemas that generate the OpenAPI document, the `postgres` driver with tagged-template SQL (no ORM), numbered SQL migrations | Spec 30's modular TypeScript service. The cutoff and the limits need lock order and the clock after locking, which plain SQL states exactly (ADR-005) |
| Database | PostgreSQL on Supabase, on its Pro plan, at the major version Supabase gives new projects. The API, the worker and the workflows connect through Supabase's session pooler, because the direct host is IPv6-only and GitHub's runners have no IPv6. The tables live in an `app` schema that Supabase's data API never exposes, and that API is off. They belong to `tadayo_app`, the role the API and the worker connect as. The public roles (`anon`, `authenticated`) and `service_role` get no grants on them, and row-level security with no policies backs that up for the public roles (ADR-015). `pg_trgm` for caption search. CI tests use the same major version | Managed backups; one bill; T53 |
| Identity | Supabase Auth with six-digit email codes and custom SMTP through Resend. The API verifies Supabase JWTs and maps the subject to `users.id`. Sign in with Apple and Google arrive in M1 | ADR-011; D06 |
| Object storage | Supabase Storage, private buckets: `uploads` (originals, quarantined until ready) and `renditions`. Each bucket carries D09's file-size limit and its allowed file types. Uploads go straight to storage with a signed upload URL scoped to one object. Reads go only through the API: the media route, which runs the read predicate on every request, and the author's own preview (T11), both streaming the bytes. No signed read URL ever reaches a client, because Supabase's CDN keeps serving a signed URL after it expires | D10; spec 33; ADR-009; T12 |
| Hosting | Fly.io, one Docker image, two process groups: `api` and `worker`. Region per FQ3 | Close to the database; cheap at trial size |
| Push | APNs directly, token-based (`.p8` key), from the worker, to Apple's production host (`api.push.apple.com`) in every environment, because TestFlight builds use production push. The key covers the production environment | No third-party push SDK sees names or events |
| Web | `apps/web`: the signed-out invitation page, `apple-app-site-association`, and the privacy, terms and support pages, static on Cloudflare Pages. The invitation token travels in the URL fragment (`/i#<token>`), which never reaches a server or a log; the page's script shows only the inviter's name, fetched with the token in a request body | T7; spec 04 |
| Deletion log | One Cloudflare R2 bucket, append-only, written by the worker | ADR-010; spec 23 |
| Images | `sharp` (libvips) in the worker, with `limitInputPixels` at 64 megapixels. Renditions: `display` (1290 px wide) and `full` (2560 px on the long edge), JPEG; `widget` (720 px) comes with widgets in M1 | D09; spec 33 |
| Image safety | A provider interface in the upload pipeline, set to `none` for the closed trial (FQ8) | Spec 33 |
| Video providers | Adapters per provider behind flags. TikTok: the official Embed Player (`https://www.tiktok.com/player/v1/{post_id}`) in an isolated web view. Instagram: accepted and normalized, opened as the original after the reveal (FQ11) | Spec 17; refs R01, R02 |
| Rate limits | A token-bucket table in Postgres. No Redis | Spec 16's burst limits at trial scale |
| Analytics | An `analytics_events` table, pseudonymous ids, a weekly report through the `ops` workflow | ADR-012; spec 36 |
| Tests | Vitest against real Postgres (Docker in the session if its daemon runs, else a local install; CI's Postgres service is the authority); the privacy matrix and the leak scanner; XCTest and swift-snapshot-testing on macOS CI | Spec 37; T16, T59 |

**Not in the trial:**
- Android, widgets and Sign in with Apple or Google;
- Live Photo motion, embedded Instagram and external sharing;
- an operator console, Remember this, and a staging environment;
- Redis and microservices.

`docs/MILESTONES.md` says when each arrives.

## 2. Building iOS without a Mac

Claude Code's cloud sessions run Ubuntu. Everything that can run on Linux runs in the session; the rest runs on GitHub's macOS runners and comes back as files.

| Work | Where | How |
|---|---|---|
| API, worker, migrations, every backend test | The session | Postgres in Docker, or the local install from the setup script if Docker's daemon isn't running; `pnpm test` |
| `TadayoCore` and `TadayoAPI` tests | The session | The Swift toolchain from the environment's setup script, pinned to the Swift version of the runner's Xcode; Docker's matching `swift` image as the fallback |
| SwiftUI views, the share extension, snapshot and UI tests, the simulator | The `ios` workflow on `macos-26` | XcodeGen, `xcodebuild test`; snapshot PNGs, contact sheets and the test log are pushed to the `evidence` branch under `<branch>/<short-sha>/ios/` |
| TestFlight builds | The `ios-release` workflow, run by hand | `xcodebuild archive` and export with `destination: upload`, signed with the App Store Connect API key and Xcode-managed profiles |
| On-device checks: share extension speed, background upload, the video player, push, VoiceOver, feel | The founder's iPhone | A TestFlight build with exact steps; the trial overlay (section 11) shows timings |

Rules that follow:
- **Keep logic out of views.** These live in `TadayoCore`, with tests that run on Linux:
    - the view models;
    - the date and countdown formatting, and the target and next-date logic;
    - the upload queue's state machine and the draft store;
    - the idea helper's batching.

    Views are thin.
- **Look at your screens.** After every `ios` run, open the contact sheets from the evidence branch. Each one puts the state's render on the left (2.1 or Claude Design) and your snapshot on the right (`docs/DESIGN-HANDOFF.md`). List the differences against the book's contracts before you call a screen done. A state with no render shows the snapshot alone, marked "built from spec".
- **Batch pushes to iOS branches.** Each `ios` run costs about 15 macOS minutes. GitHub Pro's included Actions usage covers roughly 300 macOS minutes a month; after that, about $0.06 a minute. Push when a slice is ready to look at, not after every edit.
- **Snapshot tests are the design review.**
    - Every state in `design/reference/INVENTORY.md` gets a snapshot in light, in dark and at the largest accessibility text size, at the 393-point width, with the book's fixture cast.
    - The representative states marked `-dark` and `-xl` in the inventory are also snapshotted at 320 and 430 points (book p27).
    - The founder's gate PDFs are built from them.
- **Reference snapshots are committed** under `apps/ios/**/__Snapshots__/`.
    - CI never runs in record mode, so a test with no reference fails.
    - The ios lane updates a reference from the evidence branch only when the screen matches its render and the contracts, and the PR shows the before and after.
- **Work against `dev` goes through the `ops` workflow** (section 9), because the session's proxy carries HTTPS only: no direct Postgres connection, no `fly ssh`.

**Evidence for the founder** goes on a separate branch, `evidence`, which is never merged and not protected. Create it as an orphan branch (`git switch --orphan evidence`), with none of the project's files: then the journal hook, which acts only where `tools/ci/journal_hook.py` exists, leaves evidence commits alone. It holds snapshot PNGs, contact sheets, gate PDFs, MP4s and test logs, under `<branch>/<short-sha>/` or `gates/`. The `ios` workflow pushes there with its `GITHUB_TOKEN`, under a concurrency group so that two runs never race. Link each file from the PR.

The evidence branch must not grow without limit:
- A pushed run carries only the states the branch touches. Full sets go up only for gates.
- Contact sheets are JPEG.
- Once a month, with the founder's yes (it is a destructive action), the branch is replaced by a fresh one that keeps only `gates/`: the session copies `gates/` out, the founder deletes `evidence` on GitHub, and the session pushes a fresh orphan `evidence` holding only `gates/`. Never force-push it (`CLAUDE.md`, "Git").

## 4. The iOS app

### Targets and sharing

- **The app group and keychain.** One app group (`group.app.tadayo`) and one keychain access group are shared by the app and the share extension. They hold:
    - the session credential and the account id;
    - the upload queue;
    - the per-account encrypted draft store;
    - a small roster cache for the extension's first frame: clubs, members and next dates, never captions.
- **The share extension is the compact composer** (spec 10, screen C04).
    - It shows club, person and exact date before Add (T31), from the roster cache, and refreshes it from the API.
    - A link goes to `POST /v1/sources/resolve`.
    - A photo is converted on the device (ADR-014) and handed to a background `URLSession` with the app group's container identifier, so the upload survives the sheet closing.
    - The receipt says "Added for Debby's Friday" only after the commit (T20). A pending item says it's pending. The book's "Added for" wins over spec 10's "Added to".
- **Photos.**
    - The app uses the system photo picker without full-library access, asking for the compatible representation. The camera is requested when it's used (T50).
    - Live Photos upload as stills (FQ10).
    - Several photos make several drops, each with its own caption (D05).

### Time on the device

- Every Home and day response carries `server_now`. `TadayoCore` keeps the offset and runs countdowns from it. The device clock is never used to decide anything (T1).
- The app schedules refreshes at the next `reveal_at` and `close_at` instants (UTC from the server), and on foreground.
    - At 7 AM it updates without moving someone away from a caption they're reading.
    - At 1 AM it changes Home only when the person returns (book p12; T5).
- Countdowns read as the target date to VoiceOver, never as every tick (T47).

### Networking and local data

- `TadayoAPI` is generated from `packages/contracts/openapi.yaml` on every build, so the client and the server can't drift.
- Every mutation the contract marks idempotent carries a key (UUIDv7) created when the action starts. The key is stored with the queued item and reused on retry (T19).
- **Drafts** are encrypted per account: files in the app group container with complete data protection, sealed with swift-crypto under a per-account key kept in the keychain. They are never sent anywhere except as the upload a person explicitly starts (T30, FQ15).
- **Caches** are keyed by account and content version. Author previews have their own cache, which is never shared. Logging out or switching accounts purges every cache and the roster cache (T11; Q26).
- **Deep links** are universal links on the domain with opaque ids only, such as `/c/<club>/d/<occurrence>/<drop>`. Invitations use `/i#<token>`. Every link rechecks access before showing anything (T38).

### Design system

- **`TadayoDesign`** holds the tokens as Swift constants named by role: canvas, surface, primary, secondary, action, on-action, separator, accent, on-accent, destructive, input border, the six cover colours, and the spacing and radii.
    - The values come from book p35 until the brand handoff replaces them (ADR-006).
    - Type styles map the book's sizes (day title 31/34, utility title 32/35, body 17/23, row 17/22, metadata 13/18, tab 11/14) onto the system font through `UIFontMetrics`, so everything scales with Dynamic Type.
- **The components** are the book's contracts (book p34):
    - the day header and the weekday plaque;
    - the folded card for a collecting caption, with a 151-point minimum height at default size;
    - the 91 by 69-point highlight cover with its folded corner;
    - the drop card and its states (private draft, uploading, processing, committed collecting caption, revealed, removed);
    - the person row, the target block ("For Debby · Friday 13 Nov"), the compact receipt, the quiet allowance line ("2 of 6 drops · 0 of 2 video links") and the 50-point primary button.

    Screens compose these; nothing defines its own colour or size.
- **Native where native exists:** `TabView` with the system bar, navigation stacks, sheets, the photo picker, the keyboard, alerts and toggles. iOS draws its own tab bar; the bar in the renders is a picture of one (T45).
- **Motion:** the 650 ms fold is the one named animation. Reduce Motion, the in-app setting and repeat viewings open the photo without it (T48).
- **The Lab.** A screen that shows every component with the fixture cast, light and dark, at three text sizes. It's compiled only into builds that point at `dev`, behind a `LAB` flag like `TRIAL_OVERLAY`, never into a build that points at `prod`. TestFlight builds are release builds, so the flag, not the debug configuration, decides. A Swift flag removes code, not files, so the fixture photographs live in their own asset catalog, which `project.yml` leaves out of the builds that point at `prod` (for example with `EXCLUDED_SOURCE_FILE_NAMES` in their configurations); the `ios-release` workflow checks that a prod archive holds none of them. The snapshot tests render the Lab too.
- **Brand assets** arrive in a Claude Design delivery (`docs/DESIGN-HANDOFF.md`).
    - Claude Code extracts the wordmark as a PDF vector, with "Preserve Vector Data" in the asset catalog.
    - It rasterizes the icon to 1024-pixel PNGs from the delivered vector.
    - Nothing in the catalog is drawn or generated by Claude Code (T46).
- **Snapshot tests are named after inventory states** (`H01-open`, `H01-open-dark`, `H01-open-xl`), so the `ios` workflow pairs each snapshot with its render.

### The video viewer (screen E01)

- **The web view.** A `WKWebView` with `WKWebsiteDataStore.nonPersistent()`, created only when the person taps, one at a time, released on close (T39).
- **The shell.** A small bundled HTML shell hosts the provider's iframe.
- **Navigation and messages.**
    - A navigation delegate allows only the provider's documented hosts and assets.
    - Script messages are accepted only from the expected origin, with the TikTok player's message schema (`x-tiktok-player`, `onPlayerReady`, `onStateChange`, `onPlayerError`).
    - Any other top-level navigation is stopped, and the person is asked before leaving.
- **States.** A fixed-size loading shell with Close; the provider's own controls; login or consent required; unavailable; timeout or network loss; Open original. Spec 17's table gives the full list.
- **Embedding origin.** TikTok's documentation says it may limit requests per embedding domain. Spike S3 records how the bundled shell's base URL behaves, and whether a hosted page is needed.

## 5. The API and the worker

- **Modules as in spec 30:** identity, clubs and membership, schedules, drops, media, provider adapters, interactions, memories, safety and notification policy. Two more are shared: authorization and time.
    - Each module is a folder in `packages/domain` (policies and commands) and in `services/api` (routes and serializers).
    - A module's tables are written only by its own commands, which keeps spec 30's module boundaries.
- **One authorization module.**
    - It implements the read predicate (T9) once, as TypeScript policies plus the SQL fragments that filter reads.
    - Routes, jobs, notification dispatch, search and the media route all call it.
    - It answers "may this viewer see this drop's caption / media / reactions now", never "is this drop visible".
- **Every write is one command**, in this order:
    1. Reserve the idempotency receipt.
    2. Lock rows in a fixed order: club, occurrence, membership interval, contribution counter, drop.
    3. Sample the clock after the locks: `clock_timestamp()` through the time module, never `now()`, which is the start of the transaction.
    4. Re-run the policy.
    5. Write, and append the outbox events.
    6. Store the receipt, and commit.

    The commit of a drop does all of this in one transaction (T3, T8, T17, T19):
    - checks membership, audience, media readiness, the cutoff and both limits;
    - inserts the immutable audience rows;
    - seals the audience with a trigger that refuses later rows.
- **Serializers are explicit field lists per viewer role:** author, star, member before the reveal, member after it, operator (T55). The pre-reveal DTO for non-authors is exactly spec 14's whitelist (T10). The leak scanner (section 8) fails on any field outside it.
- **The worker.**
    - It polls `outbox_events` with `FOR UPDATE SKIP LOCKED` and runs idempotent handlers with dedupe keys, bounded retries, exponential backoff and a dead-letter table that raises an alert (T54).
    - Its jobs: occurrence generation (several weeks ahead), upload preparation, opening and closing events, notification aggregation, membership revocation, media purge, the deletion log, and analytics roll-ups.
    - Permissions never depend on it. A stopped worker leaves access and Home correct, and only delays caches and pushes (T1, T5; Q18).
- **The time module** resolves 07:00 and 01:00 per ADR-008. The dev clock is ADR-013. Nothing else reads the system clock.
- **Media pipeline.**
    1. `POST /v1/uploads` creates a scoped intent and a signed upload URL for one object, with overwriting off (`upsert: false`). It's the only storage URL a client ever gets (T12). The bucket's own limits refuse anything over D09's size or of another type.
    2. `POST /v1/uploads/{id}/complete` starts preparation in the worker:
        - check the real bytes against the file signature, then JPEG, PNG and WebP only, 20 MiB and 64 megapixels;
        - decode with `sharp`, apply the orientation, strip the metadata;
        - make the renditions and the scoped content hash;
        - run the safety provider;
        - mark the upload ready, or held, or rejected.
    3. Only a ready upload can be committed. Originals and renditions stay private (T12).
    4. Reading: `GET /v1/drops/{id}/media?rendition=display|full` runs the read predicate and streams the rendition with `Cache-Control: private, no-store` and an ETag of the content version. No URL for reading storage ever leaves the server (ADR-009).
- **Source resolution.** `POST /v1/sources/resolve` normalizes the link and checks the adapter.
    - TikTok: `tiktok.com/@user/video/<id>`, and the short links `vm.tiktok.com/<code>`, `vt.tiktok.com/<code>` and `www.tiktok.com/t/<code>`.
    - Instagram: `instagram.com/reel/<code>` and `/p/<code>`.
    - Short links are followed through a fetcher that allows only https and the provider's hosts, at most three redirects, with DNS pinned and private, loopback and link-local ranges refused (spec 33).
    - It stores the provider identity and returns author-only details. Nothing about the source reaches other members before the reveal (T40).
- **The embed endpoint** returns the player parameters only after the reveal, and only when the provider's switch is on. The TikTok player uses its documented options: no autoplay, and `rel=0`, which limits suggestions to the author's videos without removing them.
- **Logging.** pino, with a redaction list for every field in T52. A test asserts that a commit with a caption leaves no caption in the log output.
- **Rate limits** are checked in the route, before the transaction: a token bucket per key in Postgres.

## 6. Data and contract notes

Spec 31's entities, with these implementation choices:
- **Memberships.** `memberships` has one row per interval (`interval_id`, `club_id`, `user_id`, `joined_at`, `left_at`, `state`), with a partial unique index on the active interval per club and user. Every audience, reaction, comment, highlight and counter refers to the interval, never to the user (spec 31).
- **Audience rows.** `drop_audience (drop_id, interval_id)` is written only by the commit command. A trigger refuses a row for a drop whose audience is sealed (T8).
- **Occurrences.** Each row stores `local_date`, `reveal_at`, `close_at` (UTC), `schedule_version_id` and `status`. Home and access never read `status` to decide; they compare instants (T1, T5).
- **Limits.** `contribution_counters (occurrence_id, interval_id)` holds the totals and external counts, reserved and committed. They're updated only under the counter's row lock inside the commit or the reservation (T17).
- **Highlights.** `highlights (occurrence_id, interval_id)` is unique, with a foreign key to the drop and a check that the drop is the contributor's own, in the same occurrence (T22).
- **Tombstones and audit.** `deletion_tombstones` is mirrored to the R2 log (ADR-010). `operator_actions` is the audit trail for every moderation script (FQ27).
- **Idempotency.** `idempotency_receipts (actor, operation, key)` is unique, with the request hash and the stored response (T19). A mutation's response, and so the stored response, carries identities, versions, the target and the status, never a caption's or comment's text: the client already holds the text it sent, which a replay's body must match. `POST /v1/uploads` also returns its signed upload URL, which the stored response leaves out: a replay signs a new one for the same object only while that upload is still pending, before `POST /v1/uploads/{id}/complete`, and otherwise returns the stored response with no URL (T12). An account's receipts are purged with the account (T27).
- **The contract.** Spec 32's endpoints, plus what the screens need:
    - invitations (create, preview with the token in the body, accept, revoke);
    - the club list for the switcher, and schedule proposals and confirmation;
    - leave with keep or withdraw; blocks; pictured removal and hide-for-me;
    - reading a drop's comment thread, with its replies (spec 16); comment edit and delete, thread mute;
    - favourites list; memory search;
    - `GET` and `PATCH /v1/me` and the authored-contributions list;
    - device registration with the device's zone, and its removal at logout or account switch, sent before the session credential is dropped; a device token belongs to one account at a time, so registering it moves it from any other account, which covers an account switch; a logout made offline queues the removal, authorized by a removal secret the app generated and sent with that registration (the server keeps only its hash, replaced at the next registration, so the secret can remove that registration and do nothing else), and a background `URLSession` sends it when the network returns (and if iOS cancelled that transfer, as a force-quit does, the app queues it again at its next launch), after which the app deletes the secret; until it lands, the old account's pushes can still reach the device; notification preferences per account, club and thread;
    - `POST /v1/sources/resolve` for the composer's and the share extension's links (section 5);
    - `GET /v1/config` for flags and provider switches;
    - a small events endpoint for client-side analytics (spec 36).

    Errors are spec 32's codes, plus neutral `NOT_FOUND`, `IDEMPOTENCY_CONFLICT`, `INVITATION_EXPIRED`, `ROSTER_CHANGED`, `CLUB_FULL`, `CAPTION_CONTAINS_SOURCE`, `DUPLICATE_DROP` and `RATE_LIMITED`. Errors carry the current totals and the target where spec 11 asks (T4).

## 8. Testing

| Layer | Tools | What must be covered |
|---|---|---|
| Domain | Vitest, pure | The read predicate; time (ADR-008's zones, both DST rules, nonexistent and ambiguous 01:00 in Europe/London); schedules (Q01, Q02, Q04); limits; next-date targeting; caption rules, with grapheme counts that match Swift's (T13); the idea helper's batches (Q24); the copy lint |
| Integration | Vitest against Postgres in Docker, with the time module's fake clock, connected as a non-superuser role that owns the `app` tables, as `tadayo_app` does in Supabase (ADR-015) | Every command; the cutoff under the lock; idempotent replays after the cutoff and after midnight (Q12); upload crossing 7 AM (Q13); reveal and close with workers stopped (Q18); removal propagation (Q19); deletion jobs (Q27); restore with tombstone replay (Q28) |
| Privacy matrix | A table-driven test generated from the OpenAPI paths: every route × every role × three phases (collecting, open, past) × six states of the drop (active, withdrawn, removed, held, its occurrence suspended, its club suspended), so the SQL fragments that filter reads meet every condition of T9. ## 9. CI

Workflows (GitHub Actions), one file each in `.github/workflows/`:

| Workflow | When it runs | What it does |
|---|---|---|
| `ci` (required) | Every push to every branch except `evidence`. No `pull_request` trigger | See below |
| `ios` | Pushes that change `apps/ios/**`, `packages/swift/**`, `packages/contracts/**` or `design/reference/**`, filtered with `on.push.paths`. It isn't a required check, so a skipped run is fine | On `macos-26`: XcodeGen, build both targets, unit, snapshot and UI tests, then the contact sheets (render beside snapshot per state). Pushes PNGs, sheets and logs to the evidence branch under `<branch>/<short-sha>/ios/` |
| `ios-release` | Run by hand on a chosen branch | Archive, export with `destination: upload`, TestFlight. Needs the App Store Connect API key |
| `deploy-dev` | On push to `main` | Migrations to `tadayo-dev`, Fly deploy of `api` and `worker`, then the Supabase probe on a Fly machine (section 8), and the Cloudflare Pages deploy |
| `deploy-prod` | Run by hand | The same against `prod`, after the founder asks |
| `ops` | Run by hand, with inputs | Against `dev` only (and `prod` for the moderation scripts, the Supabase probe and the review-access switch, after the founder asks). It is how Claude Code operates `dev`, since the session can't reach Postgres or Fly directly. It runs migrate, seed the fixture clubs, and a named script from `tools/ops/`, such as the dev clock, the scripted club members, the Supabase probe, a moderation action, the restore drill or the weekly trial report. Claude Code starts it through the REST call in `docs/GITHUB.md`, if the session's token may; otherwise the founder starts it from the Actions tab |
| `load` | Run by hand | k6 against `dev` |

**What `ci` runs.** On Linux, with a full checkout (`fetch-depth: 0`) so that the guards can compare with `origin/main`:
- install, lint and typecheck;
- OpenAPI generation, with a check that nothing changed;
- the domain and integration tests, against a Postgres service at Supabase's major version, as a non-superuser role that owns the tables (ADR-015);
- the privacy matrix and the leak scanner;
- the journal tools' own tests (`python3 tools/ci/journal_hook_test.py` and `python3 tools/ci/journal_check_test.py`);
- the copy lint and the Swift package tests;
- the web build.

**Two guards** compare the branch with `main`; both are skipped on `main` itself.
- **Guard 1:** a branch that changes `.yamllint.yaml`, `.github/`, `.claude/` or `tools/ci/` changes nothing else, except the logs `docs/DECISIONS.md`, `docs/LIMITATIONS.md` and `docs/JOURNAL.md` (T58).
- **Guard 2:** the journal check, `python3 tools/ci/journal_check.py --branch`: a log entry for every commit made on the branch (merges and commits made on GitHub's website aside), every field filled, the old log unchanged, no audit row deleted, and the state rewritten.

The final `ci` job has `if: always()` and `needs:` on every other job, and fails unless every result is `success`.

Rules for every workflow:
- least-privilege `permissions`;
- third-party actions pinned to commit SHAs;
- secrets only in workflows run by hand or by a push to `main`, never in `ci` or `ios`;
- once `prod` exists (Gate D), no key that reaches `prod` is available to a run on any branch but `main`. Each environment's keys are secrets of a GitHub environment of the same name (`dev`, `prod`), not repository secrets, and reach only that environment: a Fly deploy token per app (`fly tokens create deploy -a <app>`), and that environment's project ref and database URL. A key that reaches both Supabase projects, such as the account access token, is given only to jobs that run on `main`. The `prod` environment's only deployment branch is `main`, so a `prod` run executes merged code only. Starting or re-running anything against `prod` still waits for the founder's word (`CLAUDE.md`, "Ask me first");
- never print a secret;
- keep workflow files thin and put the logic in `tools/ci/`, because cloud sessions can't push workflow files (`docs/GITHUB.md`, "Workflow files").

## 12. Security checklist for every feature

- **Who can call this?** Is the membership interval in the drop's audience and still active? Has `reveal_at` passed for anything beyond the caption? Does it touch Supabase directly? Only sign-in may (T53), and the client's own pending upload to the signed upload URL the API issued for it: one object, write only, with overwriting off (ADR-009, T12).
- **Does the unauthorized case** return the same not-found as a missing object?
- **Can a retry, a double tap, a lost response or a queued send** duplicate anything, or retarget it?
- **Can two writes race?** The last slot, a commit against the cutoff, a withdrawal against a highlight, a removal against a favourite.
- **Does anything hidden leak** through a serializer, a count, a cache key, an accessibility label, a log, a push, a widget payload or a URL?
- **Does it touch time?** Nothing may move a promised reveal or extend Home's window.
- **Does it fetch a URL or decode bytes?** Then spec 33's SSRF and decoding rules apply.
