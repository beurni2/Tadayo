# Decisions

Record every technical choice the specs leave to you, and every ADR that proposes changing `docs/TECH-DESIGN.md`. An ADR changes the design only after the founder approves it. Decisions are numbered ADR-001 onwards, because the spec already uses D02 to D11 for its implementation defaults.

Format:

```
## ADR-001 · <short title> · <date> · <status: decided | proposed | approved | rejected>
Context: what needed deciding and why.
Decision: what you chose.
Alternatives: what else you considered, and why not.
Consequences: what this commits us to; how to undo it.
Links: PR, spec sections, invariants.
```

## ADR-001 · iPhone first, built on macOS CI · 2026-11-01 · decided
Context: Spec 30 proposes native SwiftUI on iOS and Kotlin with Compose on Android, with widgets and share extensions on both. Every member of a club must be able to install the app, so the first platform depends on the trial members' phones. The founder has no Mac, and Claude Code works from Linux cloud sessions.
Decision: The founder chose iPhone first (FQ1).
- Swift 6 and SwiftUI, with iOS 17 as the minimum until the founder confirms the phones (FQ4), built with the newest SDK so that newer iPhones get the current system look.
- Logic lives in Swift packages that compile and test on Linux.
- Views, the share extension and the snapshot tests are built on GitHub's `macos-26` runners.
- TestFlight uploads go from CI with an App Store Connect API key.
- Android follows the trial as a native Kotlin app against the same OpenAPI contract.
Alternatives: Android first, which is cheaper on CI and lets Claude Code screenshot screens in its own session, but the founder's own phone is an iPhone. Both before the trial, which roughly doubles the app work before the first club starts. A cross-platform framework, which still needs native extensions and would imitate the native controls the book asks for.
Consequences:
- Each `ios` run costs about 15 macOS minutes. About 300 a month are free on GitHub Pro; beyond that, about $0.06 a minute.
- Screens are judged from snapshots, not a simulator.
- The trial is for iPhone owners only, on phones that run the minimum iOS.
Links: `docs/TECH-DESIGN.md` sections 1, 2, 9; spec 30; FQ4.

## ADR-002 · No outside code reviewer · 2026-11-01 · decided
Context: The founder's rule from his earlier projects: no CodeRabbit.
Decision: Every PR gets an independent review from a fresh Claude Code subagent. A change that touches authorization, the database, time, idempotency, media, caches, tokens, notifications or the video viewer also gets a privacy and security review (`docs/GITHUB.md`). The founder merges.
Alternatives: CodeRabbit's GitHub App with a required approval check, which the founder dropped.
Consequences: Review quality rests on the reviewer brief in `docs/GITHUB.md`, the privacy matrix and the leak scanner. Adding an outside reviewer later is a CI-configuration PR.
Links: T58.

## ADR-003 · Supabase, Fly.io, Resend, APNs and Cloudflare · 2026-11-01 · decided
Context: Spec 30 asks for a modular TypeScript service on PostgreSQL, private object storage, durable workers and push.
Decision:
- **Supabase:** Postgres, Auth (email codes) and Storage (private buckets).
- **Fly.io:** the API and the worker, as two process groups of one image.
- **Resend:** sign-in emails.
- **APNs:** push, sent directly.
- **Cloudflare:** Pages for the invitation and policy pages, DNS, and one R2 bucket for the deletion log (ADR-010).
The app calls Supabase only to sign in and to put its own pending upload at the one-object signed upload URL the API gives it (ADR-009); everything else goes through the Tadayo API with the session token. Supabase's own data API stays closed (ADR-015). The API, the worker and the workflows reach Postgres through Supabase's session pooler, because the direct database host is IPv6-only and GitHub's runners have no IPv6.
Alternatives: Neon with Clerk and S3, which means more vendors. Supabase Edge Functions as the API, which have no long-running worker. Cloudflare R2 for media, which has zero egress fees but adds a second media store; revisit it if egress grows.
Consequences:
- Small bills at trial size: Supabase on its Pro plan from B0, because free projects pause after about a week without activity and the founder's TestFlight builds point at `dev`; Fly; a domain.
- Authorization lives in the API, not in row-level security; row-level security is on only as a closed backstop (ADR-015).
Links: `docs/TECH-DESIGN.md` sections 1, 7, 10.

## ADR-005 · Plain SQL and generated contracts · 2026-11-01 · decided
Context: The cutoff, the six-and-two limits and the immutable audience all depend on row locks, the clock sampled after locking, and database uniqueness. The app must not drift from the server.
Decision: The `postgres` driver with tagged-template SQL, and numbered SQL migrations. Zod schemas generate `openapi.yaml`, and the Swift client is generated from it on every build.

## ADR-008 · Reveal and close instants computed in TypeScript · 2026-11-01 · decided
Context: Spec 05 resolves 07:00 and 01:00 independently in the club's zone: an ambiguous time takes its first occurrence, and a nonexistent time takes the next valid instant. PostgreSQL's `AT TIME ZONE` gives an ambiguous local time the offset in force after the transition (the later instant), so it would get the autumn case wrong. The UK and Ireland change their clocks at 01:00, so a London club's `close_at` is nonexistent one night a year and ambiguous another.
Decision: One `time` module in `packages/domain` resolves civil times with the Temporal API, which Node 26 ships, with explicit code for both rules. No built-in disambiguation option returns "the next valid instant" for every gap, so that rule is written out. Occurrence rows store the resolved UTC instants. Postgres only compares instants.
Alternatives: `AT TIME ZONE` in SQL, which is wrong for the ambiguous case. Adding 18 hours to `reveal_at`, which the spec forbids.
Consequences: Tests cover Europe/London, America/New_York, Australia/Lord_Howe (a 30-minute shift), Antarctica/Troll (a 2-hour shift), America/Santiago and Africa/Ouagadougou (no DST).
Links: spec 05; T2; Q03.

## ADR-009 · Media only through the API · 2026-11-01 · decided
Context: D10 allows signed media URLs that live at most five minutes. Spec 33 says to consider an authenticated byte proxy if stronger online revocation is needed. Supabase's Smart CDN, on by default on its paid plans, caches signed-URL responses at the edge "for as long as possible", and revoking or expiring a token doesn't purge that cache. A signed URL would keep working for someone who left, was blocked or lost access, for as long as the edge holds the file.
Decision: No signed read URL or media token ever reaches a client.
- `GET /v1/drops/{id}/media?rendition=…` runs the read predicate on every request and streams the bytes from private storage with `Cache-Control: private, no-store`.
- The author's preview has its own endpoint, with the same headers.
- Uploads still go straight to storage through a signed upload URL: one object, for the client's own pending upload, with overwriting off. It is the only storage URL a client ever receives, and it reveals nothing.
Alternatives: Signed URLs that live five minutes, which the CDN turns into links that last indefinitely. Deleting objects on every loss of access, which can't work, because other members still need them.
Consequences:
- A removed photo stops loading at once; a copy already on someone's phone goes at the next reconciliation, and the privacy copy says so (T24).
- Every image's bandwidth passes through Fly: a few dollars a month at trial size.
- The app caches decoded images per account and content version.
Links: spec 33; D10; T12, T24.

## ADR-010 · Deletion tombstones kept outside the database · 2026-11-01 · decided
Context: Spec 23 says a backup restore replays deletion tombstones before serving content. If the tombstones live in the same database, a restore rolls them back with everything else. Supabase Storage's object list also lives in that database.
Decision: Every deletion writes a tombstone row and appends the same record to an append-only log in a Cloudflare R2 bucket used for nothing else. The restore procedure replays the R2 log, then purges orphaned storage objects, before any traffic reaches the restored service.
Alternatives: Tombstones in Postgres only, which is wrong after a restore. A second database, which is another bill and another secret.
Consequences: One more secret (R2 keys, in Fly secrets) and one more drill step.
Links: spec 23, 34; T28; Q28.

## ADR-013 · A clock that only `dev` can move · 2026-11-01 · decided
Context: Gates need the 7 AM reveal, the 1 AM close and the cutoff races shown on demand, not by waiting a day.
Decision: The server's clock is `clock_timestamp() + offset`, read after the locks are taken (Postgres's `now()` is the start of the transaction, before any lock). The offset comes from a `dev_clock` table that exists only in `dev`. In `prod` the offset is a compile-time zero, and a test proves that the `prod` configuration refuses any offset. The app always follows `server_now`, so the countdown moves with it.
Alternatives: Waiting for real reveals, which is too slow. Per-request time headers, which could leak into `prod`.
Consequences: Demonstrations are scripts in `tools/ops/`. A test holds a commit on the occurrence lock across 07:00 and proves that the cutoff uses the time after the lock.
Links: T1, T3; `docs/TECH-DESIGN.md` section 5.

## ADR-014 · Photos prepared on the device · 2026-11-01 · decided
Context: iPhone photos are HEIC by default, and the server's image library, `sharp`, doesn't decode HEIC in its prebuilt form. The share extension has a small memory limit. Spec 23 removes location data from delivered photos.
Decision:
- The app and the share extension upload JPEG made with ImageIO, at up to 4096 pixels on the long edge, without decoding the full image, and without GPS metadata. In the app this goes through the system photo picker's compatible representation.
- Screenshots stay PNG.
- The server accepts only JPEG, PNG and WebP. It still checks the real bytes against 20 MiB and 64 megapixels (D09) and strips metadata from every rendition.
Alternatives: Uploading HEIC originals and building libvips with HEIF support, which means a heavier image and patent questions. Full-resolution originals, which are slow on weak networks and risky in the extension.
Consequences: Originals are at most about 12 megapixels for a 4:3 photo. Change the cap with a new ADR.
Links: D09; spec 23, 33; FQ10.

## ADR-015 · Supabase's own data API stays closed · 2026-11-01 · decided
Context: The app ships Supabase's project URL and public key so people can sign in. Supabase exposes tables in its default `public` schema through its REST and GraphQL endpoints, and grants its public roles access by default. Without row-level security, anyone holding the public key could read every club's captions and storage keys, bypassing the Tadayo API and the reveal.
Decision:
- The data API (REST and GraphQL) is turned off in both projects.
- The app's tables live in a schema the data API doesn't expose (`app`).
- The `anon`, `authenticated` and `service_role` roles get no grants on it. `service_role` bypasses row-level security by Supabase's design, so for it the missing grants are the lock.
- Row-level security is enabled on every table with no policies, as a closed backstop for `anon` and `authenticated`.
- The API and the worker connect as their own database role, `tadayo_app`, which owns the `app` schema and its tables. A bootstrap script creates the role, the schema and the extensions the schema needs (`pg_trgm`, which `tadayo_app` can't create) once per database, as its admin role (`postgres` on Supabase); every migration then runs as `tadayo_app`, so everything it creates belongs to it. A table's owner isn't held by row-level security unless it's forced, so the API reads and writes normally, while `anon` and `authenticated` would see nothing even if a grant slipped in. No role Tadayo creates gets `BYPASSRLS`, and no table is set to `FORCE ROW LEVEL SECURITY`.
- `ci` does the same: the bootstrap as the Postgres service's superuser, then every migration and test as `tadayo_app`. Never the superuser, which bypasses row-level security and would hide a mistake that `dev` would show. The CI bootstrap also creates `anon`, `authenticated` and `service_role` as roles without login, as Supabase has them, so the migrations' revokes run and a test can prove those roles read nothing.
- Storage's buckets are private and its objects get no policies; the API reads them with the service key, and clients get only the upload URL of ADR-009.
- The Supabase probe (`docs/TECH-DESIGN.md` section 8) checks each real project with the public key and with a signed-in user's token, and fails on anything but a refusal or an empty answer.
Alternatives: Row-level security policies as the authorization layer, which would duplicate the read predicate in a second place and drift from it. Granting the API's role `BYPASSRLS`, which works but makes the backstop depend on one attribute nobody sees.
Consequences: B0's bootstrap creates `tadayo_app`, the `app` schema and `pg_trgm`; its first migration sets the grants and row-level security. The founder turns the data API off in each project's settings. The probe runs after every deploy, and its results on `dev` and `prod` are part of Gate 0 and Gate D.
Links: T53; spec 30, 33.

## ADR-022 · The founder approves each PR, and Claude Code merges it · 2026-11-02 · decided
Context: `CLAUDE.md`, ADR-002 and `docs/GITHUB.md` had the founder merge every PR, the merge being the approval: every PR is opened from the founder's GitHub account, so GitHub can't take the founder's approving review. On 2 November 2026 the founder told Claude Code it could merge PR #1, which it did (`0a6c91c`). Asked whether that covered later PRs, the founder first picked "Only PR #1; I merge the rest", then wrote "i will approve then you merge".
Decision: For each PR, once `docs/GITHUB.md`'s steps 1 to 6 are done (`ci` green once it exists, every finding fixed or answered, the evidence linked, "Ready for the founder" filled in), the founder approves it in a message in the project's thread, naming the PR or answering Claude Code's message about it. Claude Code then squash-merges it through REST at the head the founder approved (`gh api -X PUT repos/beurni2/tadayo/pulls/<n>/merge -f merge_method=squash -f sha=<head> -f commit_title='<PR title> (#<n>)' -F commit_message=@<file>`), with a merge message written for the merge that holds no personal data; without `commit_title` and `commit_message`, GitHub uses the repository's default, every commit's message (`COMMIT_MESSAGES`). Nothing on GitHub approves a PR: everything Claude Code posts there appears under the founder's account, so a comment or review can't show that the founder wrote it. A push after the approval needs a new approval. Gates are unchanged: only the founder passes a gate.
Alternatives: The founder merges every PR, as `CLAUDE.md` said and the founder's first answer kept; the founder's later message replaced it.
Consequences: This supersedes the last sentence of ADR-002 ("The founder merges."). `CLAUDE.md` ("I approve every gate and merge every pull request"; "Git": "Never merge") and `docs/GITHUB.md` (its introduction, "What GitHub enforces" ("his merge is the approval"), step 6 and "Never") are brought in line in a PR of their own, since the rulebook documents change only in their own PRs (`docs/MILESTONES.md`, "Lanes"), and `README.md`'s "Rules of the road" ("The founder merges.") with them; the founder's instruction applies from 2 November 2026 meanwhile. To undo it, the founder says so, and the rulebook goes back in its own PR. A PR that adds or changes a file under `.github/workflows/` (the B0 plan's slices 2, 9, 10b, 10c and 12) may have its merge refused, as the session's pushes and its merges from `main` can be (`docs/GITHUB.md`, "Workflow files"); slice 2's merge is the first test, and its result goes in `docs/LIMITATIONS.md`. If the merge is refused, Claude Code doesn't work around it (no other token, no contents API, no bot): it asks the founder to merge that PR with Squash and merge, at the head the founder approved. T57's "founder's approval in the PR" for a destructive change was the founder's merge; where it lives now is FQ39, and until it's answered no PR with a destructive migration is merged.
Links: ADR-002; T57; FQ39; `CLAUDE.md`; `docs/GITHUB.md`; `docs/MILESTONES.md`, "Lanes".

## ADR-026 · CI runs the bootstrap as a role made like Supabase's `postgres` · 2026-11-03 · approved
Context: ADR-015 has `ci` run `db/bootstrap.sql` as the Postgres service's superuser. On `dev` and `prod`, `ops` runs the same file as Supabase's `postgres` role, which isn't a superuser: Supabase's image makes it a superuser that owns the database `postgres` (supabase/postgres, `migrations/db/migrate.sh`), then demotes it to `NOSUPERUSER CREATEDB CREATEROLE LOGIN REPLICATION BYPASSRLS` with `GRANT ALL ON DATABASE postgres` (the migration `10000000000000_demote-postgres.sql`), and keeps `supabase_admin` as the superuser. So a statement that only a superuser may run passes `ci` and can fail on `dev`, the first time `ops` runs the bootstrap there, after the B0 plan's slice 10b. Slice 4 is likely to write one: on Postgres 16 and later, a role that isn't a superuser and has just created `tadayo_app` can't run `CREATE SCHEMA app AUTHORIZATION tadayo_app` ("must be able to SET ROLE"), because creating a role gives its creator only the ADMIN option on it. PR #8's independent review reproduced that on PostgreSQL 16.15, as a role with those attributes, in a rolled-back transaction. The founder chose to build it in PR #8 on a decision card in the api thread, at 01:26 UTC on 2026-11-03.
Decision:
- The `postgres` service's superuser is `supabase_admin`, the role Supabase keeps as its superuser (`POSTGRES_USER: supabase_admin` and `POSTGRES_DB: postgres` in `.github/workflows/ci.yml`). It can't be the service's default `postgres`, demoted afterwards: a cluster's first role must stay a superuser ("The bootstrap user must have the SUPERUSER attribute", seen on PostgreSQL 16.15).
- `db-bootstrap` (`tools/ci/ci_steps.py`, `SUPABASE_SQL`), as `supabase_admin` and in one transaction, makes:
  - Supabase's `anon`, `authenticated` and `service_role` (ADR-015) as its image has them: without login, inheriting (the migration `20230529180330_alter_api_roles_for_inherit.sql`), `service_role` bypassing row-level security;
  - the role `postgres` as its image makes it: `NOSUPERUSER CREATEDB CREATEROLE LOGIN REPLICATION BYPASSRLS`, the owner of the database `postgres`, with `GRANT ALL ON DATABASE postgres`, and with `anon`, `authenticated`, `service_role`, `pg_monitor`, `pg_read_all_data` and `pg_signal_backend` granted to it with the ADMIN option (the migration `20250605172253_grant_with_admin_to_postgres_16_and_above.sql`).
  Each role is made with a plain `CREATE ROLE`, so a role already there fails the step.
- Connected as `postgres`, it checks that `postgres` isn't a superuser and fails otherwise. Then it runs `db/bootstrap.sql` connected as `postgres`, as `ops` does on `dev`.
- Migrations and tests still run as `tadayo_app` (ADR-015). `DATABASE_ADMIN_URL`, for tests that act as `anon` or `authenticated`, is `supabase_admin`.
- This replaces only ADR-015's "the bootstrap as the Postgres service's superuser".
Alternatives: Keep ADR-015's superuser, and find such a statement on `dev` after slice 10b, when it needs a fix to slice 4 before `deploy-dev.yml` can be sent. Or have slice 4's database tests run the file as such a role themselves, which puts CI's setup into every package that tests the database.
Consequences: Slice 4 writes `db/bootstrap.sql` for a role that isn't a superuser (for example, `GRANT tadayo_app TO postgres` before `CREATE SCHEMA app AUTHORIZATION tadayo_app`). Differences between `ci`'s plain Postgres and Supabase's remain, so the first `ops` bootstrap on `dev` is still the proof: the schemas Supabase's image adds (`auth`, `extensions`, `storage`) and its grants on them; the role `authenticator`; supautils' reserved roles; and supautils' privileged role (`supabase_privileged_role`, which `postgres` belongs to on Supabase), which lets `dev`'s `postgres` run some statements that otherwise need a superuser (publications, foreign data wrappers, event triggers, some settings) and that `ci` refuses. A local check needs a server made like `ci`'s (`initdb --username=supabase_admin`), because the session's own cluster's first role is `postgres` (`docs/LIMITATIONS.md`). To undo it, `db-bootstrap` runs the file as `supabase_admin`, in a CI-configuration PR of its own (T58).
Links: ADR-015; T53, T58, T59; `docs/TECH-DESIGN.md` section 9; the B0 plan's slices 2, 4 and 10; PR #8.

## ADR-028 · CI lets Xcode run the OpenAPI generator's build plugin · 2026-11-05 · approved
Context: `TadayoAPI` is "generated from `packages/contracts/openapi.yaml` on every build" (`docs/TECH-DESIGN.md` section 4; ADR-005), which the Swift OpenAPI Generator does as a SwiftPM build plugin. Xcode runs a package's build plugin only once a person has trusted it in Xcode's dialog, and `xcodebuild` without that trust refuses it. On the check branch `ios/b0-plugins-check`, which never merges, `ios` run 41958887177 (at `ab8968c`, the app linking `TadayoAPI`, `tools/ci/` as on `main`) failed in its build step with `Validate plug-in "OpenAPIGenerator" in package "swift-openapi-generator"` and `** TEST BUILD FAILED **`, and printed only the second: no line of the build log says `error:` (the evidence branch's `ios/b0-plugins-check/ab8968c/ios/logs/build.log`). CI has no person to trust it.
Decision:
- `tools/ci/ios_steps.py` passes `-skipPackagePluginValidation` to both of its `xcodebuild` calls: the build (`build-for-testing`, or `build` for a scheme with no tests) and `test-without-building`, which resolves the package graph again. `ios_steps_test.py` checks both. With the flag, run 41961456622 on the same branch (at `a45fa23`, started by hand, since a push that changes only `tools/ci/` doesn't start `ios`) ran "Running swift-openapi-generator", compiled the generated `Client.swift` into the app, built (`** TEST BUILD SUCCEEDED **`, the build step 3 minutes 24 seconds) and passed its tests, with no warning from `TadayoAPI`.
- The build step also prints `xcodebuild`'s list of the commands that failed (`The following build commands failed:`, its indented lines and its count; `LogFilter`), since that list is the only place a refused plugin is named.
- Since the flag trusts every plugin, the build step then reads its build log for the plugins Xcode ran (`package_plugin_problems`) and fails on one outside `tools/ci/toolchain.py`'s `PACKAGE_PLUGINS`, today `OpenAPIGenerator`, from `swift-openapi-generator`, on `TadayoAPI` only. It reads Xcode's own lines (`Compile plug-in “P” in package “K”`, `Validate plug-in …`, `Apply build tool plug-in “P” to target “T”`, as run 41961456622's log has them at lines 118 and 125) and the folders a plugin's executable and output go to (`PluginExecutables/P`, `BuildToolPluginIntermediates/<package>.output/T/P`). A line about a plug-in it can't read fails, and so does a build of `TadayoAPI` with no line saying the generator was applied to it, since then Xcode words its lines differently and the check would find nothing.
- Slice 12's archive (`ios/b0-release`) passes the same flag, or the first TestFlight build fails the same way.
What the flag turns off: Xcode's check that a person trusted each package build plugin in the build graph, for every plugin, not only this one. Today the graph has one, `OpenAPIGenerator`. It doesn't skip macro validation (`-skipMacroValidation`, not passed), so a package macro still fails the build. The plugin runs code at build time: the generator, pinned `exact: "1.14.3"` in `packages/swift/TadayoAPI/Package.swift` (which `ios/b0-api-client`, PR #19, adds), and the packages it depends on. Those float within their own requirements, because `Package.resolved` is ignored (`packages/swift/.gitignore`) and XcodeGen makes the project afresh on each run, and so do the app's other dependencies' (swift-snapshot-testing brings swift-syntax, swift-custom-dump and xctest-dynamic-overlay; the generator brings OpenAPIKit and Yams). A new release of any of them could add a build plugin with no change in any `Package.swift` or `apps/ios/project.yml`, so review can't be what catches one: the build step's check is. It runs after the build, so such a plugin has already run, in Xcode's plugin sandbox, in a build job that holds no secret and only a read-only token (`.github/workflows/ios.yml`, `permissions: contents: read`); the run fails, and the PR shows it.
Alternatives: Commit the generated sources, with a check that they match the contract: no plugin and no flag, but about 59,000 generated lines in the repository and a regeneration step on every contract change, where TECH-DESIGN asks for generation on every build. Run the generator's command plugin before `xcodebuild` into an ignored folder: a second path for the same code, which Linux's `swift test` would need too. Trust only this plugin by writing Xcode's own trust record on the runner, or set the `IDESkipPackagePluginFingerprintValidatation` default: the format of the first and the effect of the second aren't documented, so a check could pass for a reason nobody can read.
Consequences: Xcode, the Linux `swift test` in `ci` and the session all run the same generator on the same contract, so the client can't drift from the server. Pinning the generator's own dependencies is a later change if one of them moves badly (the `docs/LIMITATIONS.md` row PR #19 adds). An api PR that changes an operation the app calls changes it additively, or in three steps (the api thread and the ios thread, 5 November 2026; written in PR #19's `docs/PROGRESS.md` ios section, "Needs from the other lane"). Adding a build plugin is a CI-configuration change: a `PACKAGE_PLUGINS` entry, in its own PR (T58).
Links: ADR-005; T58; `docs/TECH-DESIGN.md` sections 2 and 4; the B0 plan's slices 11 and 12; runs 41958887177 and 41961456622.
Approved by the founder with PR #18, in the ios thread on 5 November 2026 at 06:00 UTC ("you can merge PR #18"), which merged as `c98bb0f`.

## ADR-034 · The `ops` runner reaches the Machine over SSH, and removes the run's WireGuard peer · 2026-11-12 · approved
Context: `storage-setup` and the API half of `supabase-probe` run on the API's Machine of `tadayo-api-dev`, where Fly's secrets hold Supabase's service key (T56; `docs/plans/api-b0-deploy.md`, section 6). Slice 10a ran them with `flyctl machine exec`, one HTTP request to Fly's Machines API (`POST /v1/apps/{app}/machines/{id}/exec`) that waits for the command to end. The first `supabase-probe` on `dev` (run 43160900116, 2026-11-12 05:22 UTC) was answered with HTTP 408 about 60 seconds into that request, though it asked for 300: the Machines API's "at most 600" bounds the request's `timeout` field, not how long Fly keeps the request open, and fly-go caps its own blocking calls to that API at 60 seconds (`proxyTimeoutThreshold`). The probe gives itself 150 seconds to ask and 240 to clean up; `storage-setup` took 2 seconds that day and may take 120. `docs/TECH-DESIGN.md` doesn't say how the scripts reach the Machine; the slice's plan named `machine exec`, and `docs/LIMITATIONS.md` named `fly ssh console` as its fallback. The founder was asked on a card in the api thread on 2026-11-12 at 06:05 UTC, and chose this way there at 07:36 UTC ("Fly SSH, cleaned up each run"), which approves this ADR; PR #41 built it, approved by the founder and merged as `0b6558a` on 2026-11-12.
Decision:
- `tools/ops/src/on-machine.ts` runs the same plain-words command with `flyctl ssh console -a tadayo-api-dev --machine <id> -q -C "<command>"`. flyctl 0.5.8 (its source) brings up its own WireGuard tunnel to Fly's private network over a websocket (no root, no UDP), checks it once with a DNS lookup of at most five seconds and ends the session with `Error: tunnel unavailable: …` when that check fails (nothing retries it; `docs/LIMITATIONS.md`), has Fly issue a one-hour SSH certificate, and runs the command on the Machine in the Machine's environment, as root (flyctl's default and Fly's own examples), with no shell and no terminal. An SSH session has no 60-second cap. The call is given 600 seconds: 240 for flyctl's agent to make the peer and bring its tunnel up, which flyctl 0.5.8 doesn't bound (only its one check of the tunnel, five seconds; `internal/wireguard/wg.go`'s `Create` runs under `context.TODO()`), 60 to connect, and the command's 300 (`COMMAND_SECONDS`), a minute more than the probe's own deadline; only those 600 end a session that hangs before the command.
- flyctl exits 0 when the command did, and otherwise 1 with its last line `Error: ssh shell: Process exited with status N` (golang.org/x/crypto's wording), which is how the command's code is read; the last line `Error: ssh shell: wait: remote command exited without exit status or exit signal` is a session that ended without saying how the command ended, which the Machine's end and a connection lost on the way both give; any other ending is flyctl's own failure (its trailing empty lines left out; when flyctl describes the failure after its `Error:` line, as it does its agent's failure to start, with the agent's log, every line is said and the first ones word it), and a failed tunnel check adds that running the script again may work. Exit 0 is necessary, not sufficient (flyctl also exits 0 for a session that closed before the command ran), so `run.ts` keeps asking for each script's own last line. Every line that came back is said, also from a session that failed or was cut short, so a cut-off probe still shows its run's id.
- flyctl's agent makes a WireGuard peer in the organization for the session, named `interactive-<host>-<the token's email, as a slug>-<ULID>`, before it brings the tunnel up; on a fresh runner every run makes a new one, flyctl never removes it, and a peer reaches the organization's whole private network (today only `tadayo-api-dev`) until it is removed. So the runner lists the organization's peers (`flyctl wireguard list <org> --json`, the organization being the one the token sees) before the session and again after it, whatever the session did, and removes (`flyctl wireguard remove <org> <name>`) each one that wasn't there before and whose name starts as flyctl's agent names a peer on this runner, `interactive-<host>-`, whatever follows (an organization token with no email gives `interactive-<host>--<ULID>`). A peer that was there before is never touched, and no clock is read (T1: only the time module reads one, which `one-clock.test.ts` holds every ops script to). A new peer named otherwise is left, since it may be another's, and fails the run, said without its name, and, when none of this run's is found, as one that may be this run's under a name not foreseen (beside one that is found it can't be: flyctl names every peer its agent makes the same way). No other runner holds the token while this one runs (the `ops-dev` concurrency group), though a host named like this one with more after a dash couldn't be told from it. If the token's organization can't be told, or its peers can't be listed first, no session is started, since its peer couldn't be told apart. Before the session the runner says that it makes a peer, how to list and remove one by hand and how this run's names start, for a run cancelled before its clean-up. flyctl 0.5.8 can exit 1 after removing a peer (its `PruneInvalidPeers` runs after the removal), so a removal that failed is checked with a new list, and the peer counts as left only when that list still shows it or no list can be had. A peer left, a new peer named otherwise, a list it couldn't get after the session, or no new peer found though the session reached the Machine, fails the run with the commands that do it by hand. After flyctl's own failure or a timeout, with no new peer of this run's listed, the runner says so, with the same commands, since flyctl's agent makes the peer before it checks the tunnel, and a timeout may come before or after the Machine. A call the runner couldn't make (one `forDevApp` refuses) is said as not made, never as flyctl's exit code, and the clean-up goes on. The names hold an email, so none is printed, nor what flyctl prints about one. `forDevApp` (`tools/ops/src/fly.ts`) admits those two calls in exactly those shapes, and a removal only of a name that starts `interactive-`.
Alternatives:
- A throwaway Machine per run (`flyctl machine run --rm`, or `flyctl console`): no peer, but the report comes back through Fly's logs, which lag and can drop lines, the exit code only through the Machine's exit event, and fly.toml's `[env]` isn't applied.
- One short exec that starts the command detached, then short execs that ask how it is going: the image changes, and whether a detached process outlives its exec isn't documented.
- Fitting the probe under 60 seconds, by splitting it into several execs or cutting its limits: more moving parts, or fewer checks.
- Leaving the peers and removing them by hand now and then; or flyctl's token mode, whose peers expire, which is in 0.5.8's source behind a feature flag and untested.
Consequences:
- Each SSH session adds and removes one peer and one SSH certificate in the organization. Since PR #53 (`api/b0-ops-fresh-agent`, 2026-11-13), each session runs with a configuration folder of its own, made by `mkdtemp` under the runner's temporary folder (mode 0700: the runner's user alone, and root), as `FLY_CONFIG_DIR`, and an agent of its own (`FLY_AGENT_ISOLATED=1`), which stops at the end of its input, when flyctl exits (one cut off while it makes the peer, which nothing bounds, finishes that call first, and can't save the peer once the folder is gone; GitHub ends any process left with the job); the peer's private key is in that folder, in the WireGuard state and, in clear, in the agent's log (0.5.8 swaps the JSON names of the two keys, so its log's redaction misses the private one), until the session's call has ended, when the folder is removed, and useless once the peer is removed; a run cancelled, cut off by the job's time or lost before then leaves the folder, with the key, until the runner ends, and its peer at Fly until it is removed by hand (below). ## ADR-038 · Each photo is prepared under a user of its own, so the image starts as root · 2026-11-23 · approved
Context: Each photo is decoded in a process of its own (PR #111, `services/worker/src/image-process.ts`), which runs as the worker's user, `node`, the image's `USER` (`docs/plans/api-b0-deploy.md`). Code that a stranger's bytes took over in a decoder could therefore read the worker's environment from `/proc` (the database URL and Storage's service key, T56), open the worker's standard output and write into its log (T52), stop or kill the worker by a signal, and leave a process behind that outlives the photo and opens the next photo's process's pipes through `/proc`, the next person's photo on its way in and its renditions on their way out (PR #111's round 4, R4-2; the check of its fifth commit, C5-1 and C5-3; `docs/plans/api-b2-worker-hardening.md` section 0; `docs/LIMITATIONS.md`, 2026-11-23). A process can keep these from another user's processes, and end every process of that user at once, only with the power to start processes as another user, which only root has. Measured in the session and in the pinned base image (the plan's section 0).
Decision (approved by the founder at 21:09 UTC on 2026-11-23, on the decision card in the api thread: "Yes, photos under their own user"):
- The image makes a system user and group `tadayo-image` (uid and gid 10001, no home, no shell, no password) and ends without `USER node`, so each process group's command starts as root and drops at once with `setpriv` (util-linux, in the base image), before Node starts.
- The API drops to `node` entirely (`setpriv --reuid=node --regid=node --init-groups --inh-caps=-all --bounding-set=-all --no-new-privs`), as it runs today.
- The worker drops its effective ids to `node` and keeps its real uid 0 with three capabilities, `CAP_SETUID`, `CAP_SETGID` and `CAP_KILL`, and no other (`setpriv --euid=node --egid=node --groups=node --bounding-set=-all,+setuid,+setgid,+kill --no-new-privs`). That makes it non-dumpable: its `/proc` files are the kernel's. It takes effective uid 0 for an instant three times a photo, nowhere else: to start the photo's process as `tadayo-image`, to kill that process's group, and to start a sweep as `tadayo-image` that ends every process of that user (`kill(-1)`) as the photo's end settles.
- `fly.toml`'s `[env]` names the photo user (`TADAYO_PHOTO_USER`); the worker refuses to start with the name but not the start, or the start but not the name.
- As built (`api/b2-worker-hardening`'s second commit; `services/worker/src/privileges.ts`), two points the building found, within the decision: the sweep runs as `tadayo-image` with the worker's own group, not `tadayo-image`'s, because Linux lets a process attach to another (`ptrace`, `/proc/<pid>/mem`) only when every user and group id matches, so a process a photo left behind can't take the sweep over and make it skip its `kill(-1)`; and a sweep that fails to start, exits other than 0 or takes more than 5 seconds stops the worker (exit status 1, which `[[restart]]` `on-failure` restarts with its Machine), where the proposal failed the photo as `ImageProcessFailed`: a leftover can still stop or kill the sweep, as it may signal any process of its user, and a worker that went on would start the next photo's process beside it. A third point came from the lane's own breakage run: the sweep's program checks its own user and exits 2 if it is root, before its `kill(-1)`, since a sweep run as root would end every process on the Machine; with the refusal before its start removed, a run of the harness as root did exactly that to the session's container, twice.
- As reviewed (round 1 of PR #118, its third commit), within the decision: a process a photo left behind could still take the sweep over through Node's inspector, which `SIGUSR1` opens on `127.0.0.1:9229` with no password, since it may signal the sweep (both reviewers found it, independently, and showed it). So every Node process of the image runs with `--disable-sigusr1`: the API, the worker, the photo's process and the sweep. The sweep now repeats its `kill(-1)` until no process of the user is left, then removes what the user owns in `/tmp`, `/var/tmp`, `/dev/shm`, `/dev/mqueue` and `/run/lock` and every System V object it owns or made, which could otherwise hold memory that later photos would need; the worker sweeps once as it starts, before it connects, and won't start if that sweep fails. The worker's command begins `prlimit --core=0 --nproc=256`: no core file, and at most 256 processes for `tadayo-image` (the kernel doesn't hold root's processes to it). A group kill the kernel refuses stops the worker, and none is sent once Node has reaped the child, when the group's number may be reused. The worker takes uid 0 at least four times a photo, not three (the start, the group's kill once the answer is in and again as the end settles, and the sweep), each for one system call. A rendition is kept only if it is a baseline JPEG with nothing else in it and of the size the answer states. And the context's "opens the next photo's process's pipes through `/proc`" was wrong: those are socket pairs, which `/proc` won't reopen; the way in was attaching, or `pidfd_getfd`, where Yama allows.
- As reviewed (round 2 of PR #118, its fourth commit), within the decision; neither reviewer found a way past the isolation. The sweep's files go through `find`, `chmod -R` and `rm -rf`, which take a name as its bytes and walk a tree of any depth: its first program skipped a name that isn't UTF-8, and the worker ran on with the file (both reviewers), and failed on a tree deeper than a path may be long and on tens of thousands of System V objects in one `ipcrm` call through Node's `execFileSync` (which threw once `ipcrm` had removed them), which now goes through `spawnSync`, 500 at a time. What it can't remove, once every process of the user has ended, is exit status 3, and the worker's stop line says so rather than that a process may be alive. The sweep starts in a session of its own: its `/proc` files are its user's, so a leftover could set its scheduling group's priority, which was the worker's, to the lowest, until a restart. The worker's command is now `prlimit --core=1 --msgqueue=0 --nproc=256 -- setpriv ... --inh-caps=-all ...`: a limit of 1 byte stops a core dump to a program as well as to a file, no POSIX message queue can be made to outlast the sweep where `/dev/mqueue` isn't mounted, and the inheritable set is emptied, as with a real uid of 0 it adds to what the worker keeps. Corrections to the note above: the worker takes uid 0 once to start the photo's process, once each time its end is reached before Node has reaped it (usually once), and once for the sweep, so usually three times, not "at least four"; and a rendition's check is of its segments (no metadata segment, one frame of the stated size, one scan), not of what is in its tables or scan, which are the child's like the picture. Two more ways for a leftover or a taken-over decoder to stop the worker, both the restart below: more files than the sweep removes in 5 seconds, and the kernel's OOM killer, which may take the worker once a decoder has lowered its own `oom_score_adj` back to 0 and holds memory in no process's resident set (System V shared memory, `/dev/shm`).
- As audited (the founder's outside audit of 2026-11-24, finding A6; PR #118's fifth commit, with round 3 of its review), within the decision: the start failed open. With no `USER` in the image and the drop only in fly.toml, a start as root alone (`docker run`, `fly machine run`, a configuration that copied `[processes]` without `[env]`) prepared strangers' photos as root. Now it fails closed. The Dockerfile names the photo user (`ENV TADAYO_PHOTO_USER=tadayo-image`, beside the user it makes; no longer fly.toml's `[env]`, a correction to the bullet above) and writes `/etc/tadayo-built-image`, by which, or by `NODE_ENV=production`, each entry knows it is in the image whatever a start's settings say. In the image the API refuses a real or effective uid of 0, and the worker refuses any start but fly.toml's worker command, read back from its ids (real uid 0, effective uid and group not 0) and from `/proc/self/status` (no new privileges, the bounding set exactly kill, setgid and setuid, no inheritable capability, no group of root's), before it reads any other setting; and no photo's process starts without its user in the worker's mode or in the image (`NoPhotoUser`). The root harness runs fly.toml's own worker command, and prepares a real photo with the real child as the photo user from a read-only view of the checkout (`docs/plans/api-b2-worker-hardening.md` section 6).
- As found on Fly (PR #132's start on `dev`, 08:57 UTC on 2026-11-25; `api/b2-worker-turn`, `docs/plans/api-b2-worker-turn.md`), for the founder's answer with its PR: the worker never started on Fly. Under `setpriv --euid=node --egid=node … --no-new-privs` it was found with uid 0, euid 0 and egid 0, every other fact as the command leaves it: Fly's kernel takes an exec under no new privileges whose effective ids differ from the real ones for a set-id program's and puts them back to the real ones, root's, where the session's kernel and Docker's keep them, so every test had passed (`docs/LIMITATIONS.md`, 2026-11-25). So the worker's `setpriv` sets no user or group id, and its first module, `services/worker/src/turn.ts`, imported before any other, takes `node`'s effective group and user itself (`privileges.ts` `turnToWorkerUser`), only when the start is fly.toml's (root's ids and `startedAsFly`'s facts). The state it reaches is the decision's, measured in the image: real uid 0, effective uid and group `node`'s, setuid, setgid and kill permitted and none effective, no new privileges, `/proc/self/environ` root's (`Uid: 0 1000 0 1000`: the saved uid is 0 where `setpriv` left 1000, which gives nothing more, as the real uid is 0, and takes away a process of `node`'s signalling the worker); the turn then checks every thread's status for exactly that (`turnedAsFly`, round 1 of PR #135's review). It changes the first consequence below: from the exec of `node` until that module runs, Node's own start-up runs as root, with setuid, setgid and kill alone effective, under no new privileges, and reads the worker's modules from the image; it reads no photo and nothing from the network in that time. As no id changes at that exec, Node honours the settings it reads from its environment, `NODE_OPTIONS` among them, which could load code before that module, and glibc its own, as root: the image's `ENV` and fly.toml's `[env]` set none (`tools/ops/src/deploy-files.test.ts` holds each to its names), the rest of the environment is Fly's secrets, which the founder sets, and whoever could set one could already run code as root through the programs before Node. The API is unchanged: its `setpriv` sets its real, effective and saved ids together, so its exec changes none.
Alternatives:
- Nothing as root: the worker hides its environment by running an execute-only copy of Node (an unreadable program makes its process non-dumpable), and ends every other process of `node` after each photo (`kill(-1)` from the worker). A photo's process would still share the worker's user: it could stop the worker with `SIGSTOP`, and photo preparation would wait until someone restarted it.
- The worker as root throughout: simplest, but the worker's own code, which reads every child's answer, would run as root.
- User and process-ID namespaces (`unshare`): no root needed if Fly's kernel allows them (unchecked), but the photo's process would keep the worker's uid, and a process root in its own namespace can unmount the `/proc` it was given and see the worker's.
- A cgroup of its own per photo, ended with `cgroup.kill`: depends on Fly delegating a cgroup to the process, unchecked, and leaves the shared uid.
Consequences:
- No Node code runs as root: `setpriv` drops before Node starts, and the worker's three moments at uid 0 are the only ones, each a synchronous call. A taken-over worker could still take uid 0 again, as its real uid is 0; it already holds every key the app has.
- `tools/ops/src/deploy-files.test.ts`'s rule that the image runs as an unprivileged user becomes: the image starts as root only to drop, each process group's command begins with its `setpriv` line, exactly. `docs/plans/api-b0-deploy.md`'s runtime stage says so.
- The isolation is tested as root: in the session directly, and in CI through `sudo -n` (the runner's password-less sudo), never skipped. It is verified on `dev` once its worker runs.
- `ops` runs, which `flyctl ssh console` makes as root, are unchanged.
- A process a photo left behind can still stop, slow or kill the sweep, which stops the worker: its Machine restarts, up to five times for one photo before the outbox gives it up (`MAX_ATTEMPTS`), and the day's generation, which runs in the worker, waits meanwhile. Fly's `[[restart]]` policy retries a failing Machine only so many times (`max_retries`, read on `dev`); past it the worker stays down until it is started. Recorded in `docs/LIMITATIONS.md`.
- What a photo's process sends back is still its own picture, tables and scan: a taken-over child could send another picture than the one screened, or bytes aimed at a decoder. B3's media route and the iOS app treat renditions as untrusted input, and FQ8's screening, when built, screens the renditions as stored. Re-encoding each rendition in a second, fresh process would make an attacker need two exploits; it isn't built (`docs/LIMITATIONS.md`).
Links: T52, T56; PR #111's R4-2, R4-3, C5-1, C5-3; `docs/plans/api-b2-worker-hardening.md`; `docs/LIMITATIONS.md`, 2026-11-23.
