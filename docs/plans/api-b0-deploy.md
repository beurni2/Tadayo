## 2. `fly.toml` and the two process groups

Each key was checked against flyctl 0.5.8's own reader of `fly.toml` on 11 November 2026 (`internal/appconfig/`: `config.go` for the keys and their types, `patches.go` for `kill_timeout = 30` read as 30 seconds, `service.go` for the service and its checks, `processgroups.go` for which group a section binds to, `machines.go` for the restart policy and the stop configuration; fly-go's `MachineAutostop` for `auto_stop_machines = "off"` and `MachinePort` for the ports). `fly.io` can't be reached from the session, so that source is what the keys rest on, and the first deploy is the proof.

- `app = "tadayo-api-dev"`, `primary_region = "iad"`, `kill_signal = "SIGTERM"`, `kill_timeout = 30`, `[build] dockerfile = "Dockerfile"`, `[deploy] strategy = "rolling"`.
- `[env]`: `TADAYO_ENVIRONMENT = "dev"`, `SUPABASE_URL` (`https://rhsycmycocbzakrydahi.supabase.co`), `SUPABASE_PUBLISHABLE_KEY` (the `Dev` configuration's, for the probe), `LOG_LEVEL = "info"`. Nothing else: a test lists the allowed names, and checks the values against `apps/ios/project.yml` and the verifier's own rule. The secrets (`DATABASE_URL`, `SUPABASE_SERVICE_KEY`) are Fly's.
- `[processes]`: `api = "node services/api/src/main.ts"`, `worker = "node services/worker/src/main.ts"`.
- `[[services]]` on the `api` group only (`processes = ["api"]`: `flyctl` refuses a `[[services]]` with no `processes` while `[processes]` is defined (`validation.go`, "Service has no processes set but app has 2 processes defined"); `[[restart]]`, `[checks]` and the like with none go to the default group only, `app` if there is one and else the first name in sorted order, here `api`; `[[vm]]` with none covers every group): `internal_port = 8080`, `auto_stop_machines = "off"`, ports 80 (`force_https`) and 443, and `[[services.tcp_checks]]` (grace 20 s, interval 15 s, timeout 3 s). It is a TCP check on the port and not an HTTP check on a path, because a path would be a route outside the contract, which the privacy matrix would have to cover (T58's rule that every route has a row), and the API listens only after the database and the clock are ready, so an open port means started. `[http_service]` can't carry a TCP check, which is why this is `[[services]]`.
- The `worker` group has no service: Fly's proxy never starts or stops it by traffic. `[[restart]] policy = "on-failure"` for both groups: a crash is restarted, a clean exit (what a stop is) is not, so a Machine `worker-scale` stopped stays stopped, and so does one stopped by hand across a deploy (`flyctl deploy` leaves a stopped Machine updated and not started). One Machine per group: `dev` has no spare, and the deploys pass `--ha=false`. `[[vm]]` is `shared-cpu-1x` with 512 MB, for both.
- No `release_command`: migrations run before the deploy, from the runner, as `tadayo_app` (TECH-DESIGN section 7), so a failed migration stops the deploy before a Machine changes.

## 3. The two entries learn to stop

- **The worker keeps running.** `services/worker/src/main.ts` starts, writes `worker: started, with no jobs yet`, and waits for SIGTERM or SIGINT, then exits 0 (`worker: stopped on SIGTERM`). It used to start, end its connection and exit 0 at once, which `startWorker`'s comment says the first of B1's jobs, or this slice if it comes first, replaces with the loop that keeps it running. Without it a worker that started would exit 0 at once and leave its Machine stopped (`[[restart]] on-failure` restarts a failure, not a clean exit), so `worker-scale --to started` would start it and read it stopped again. The wait is a timer that holds the process open, since a database connection the pooler closes doesn't. It does no work and polls nothing.
- **The API closes on a signal, and doesn't wait out the keep-alive time.** `services/api/src/shutdown.ts` (`stopOnSignal`), used by `main.ts`: on the first SIGTERM or SIGINT it says `api: stopping on SIGTERM`, calls `app.close()` (Fastify stops listening, ends the idle connections once and waits for the rest to end), then ends the database's connection, says `api: stopped`, and the process ends with exit code 0, so a deploy cuts no request short. A second signal isn't caught, so it ends the process as signals do.
  - The first version stopped there, and a real server showed it wrong. A connection a request has finished on stays open for Fastify's keep-alive time (72 seconds by default, longer than `fly.toml`'s `kill_timeout` of 30), and `close()` ends the idle connections once, when it is called, so a stop begun with one request in flight waited about 73 seconds and Fly would have killed the Machine first (reproduced with a real Fastify and a keep-alive client, before the fix). Now, while it waits, `closeIdleConnections()` runs every 250 ms (`SWEEP_MS`), so a connection is ended as soon as its request is done; and 25 seconds after the signal (`GRACE_MS`) the connections still in use are ended too (`closeAllConnections()`), once, with the line `api: requests still running after 25 seconds are ended`. A request that outlasts the grace is cut, and the log says so. Its query may still be running, so the database's connection is ended with `END_SECONDS` (3) for queries still running, after which postgres.js closes it anyway: by the app's own `onClose` hook, which `close()` runs (`app.ts`), and asked again by the stop in case the close failed first. Then `main.ts` ends the process, with the exit code the stop left, so that a socket postgres.js half-closed can't hold it past `kill_timeout` (round 2's R3: the end had no limit, and the hook that does it first is the app's). A test reads `fly.toml` and fails if `GRACE_MS` plus `END_SECONDS` plus two seconds is more than `kill_timeout`; another holds the app's end to `END_SECONDS`.
  - A close that fails, or a database connection that doesn't end cleanly, writes a message that holds none of the error's words (T52, T56): `api: the server didn't close cleanly` or `api: the database's connection didn't end cleanly`. The stop goes on to end the database's connection after a failed close, never says `api: stopped` after a failure, and the process ends with exit code 1.
- A limit, in `docs/LIMITATIONS.md` and the file's header: Node's `closeIdleConnections()` ends a connection as soon as its response is finished, which is when the last write is handed to the socket and not when the reader has it, so a stop can cut a large answer short for a slow reader. B0's answers are small; B3's media route, which streams files, revisits the sweep.
- Tests: `services/api/src/shutdown.test.ts` (16). Thirteen have fake signals, a stub server and fake timers: the order (the server closes before the database's connection ends), that it happens once, the sweeps and that they stop, the grace and its line, the grace not waited for when the server closes first, both failure messages and neither holding an error's words, and the `kill_timeout` bound. Three run a real Fastify on a real socket with a keep-alive client: a request in flight finishes with its 200 and the stop then ends at once instead of waiting out the keep-alive time; a client that holds an idle connection doesn't hold the stop; a request still in flight when the grace is over is ended, with the line that says so. Two of the three fail on the first version. And `tests/src/db/startup.test.ts` (the entries as processes against the test database): each stays up after starting, exits 0 on SIGTERM and on SIGINT, writes its stop line, two signals in a row begin one stop, and both stop with `dev` when the database has no dev clock.

## 4. `tools/ops`: one entry, one guard, the scripts

- **One entry.** `node tools/ops/src/main.ts <script> [--option value …]`. `run.ts` holds the scripts, each with the variables it reads from the environment and the options it takes (`parseArgs`, strict, no loose word); every effect on the world comes through the context's `connect`, `spawn`, `fetch` and `sleep`, so a test gives each a fake. Every line printed goes through the redactor (`output.ts`), which knows the environment's secrets by name and by shape, and a failure prints its message and never its stack.
- **One guard** (`environment.ts` and `fly.ts`, T56). A script acts on `tadayo-dev` and nothing else. The Fly app is the constant `DEV_APP`. `flyctl` is given the Fly token and `HOME` and nothing else of the environment, and never a shell, and `flyOf(...).run` refuses, before any process starts, an argument list that doesn't name the app (`forDevApp`: `-a` or `--app` followed by `DEV_APP`, and no other app flag in any spelling, such as `--app=x` or `-ax`), so that what `fly.ts`'s header promises is enforced by the one place that runs `flyctl` and not by each script. The only calls it lets through without an app flag are the two that name none: `orgs list --json`, and `apps create tadayo-api-dev` with `--org <slug>` or without. A database is `dev`'s only by what its connection string says: Supabase's session pooler (`<region>.pooler.supabase.com`, port 5432, database `postgres`, no query or fragment, one host) with `tadayo_app.<reference>` as the user, where the reference is `SUPABASE_DEV_PROJECT_REF`, and with a password (`devDatabaseUrl` refuses one with none, and one whose `%` isn't an escape, by the variable's name; a `#`, `/` or `?` written raw ends the user part, so the refusal says to write them as `%23`, `%2F` and `%3F`). A comma is a second host only after the last `@`, so a password may hold one. The app's password is 32 letters and digits (`docs/plans/B0.md`'s secrets row), which needs no encoding at all. No script takes an environment's name from its caller.
- **The database link** (`database.ts`, `connectionOptions`). The driver is given the parts the guard checked (`databaseOf`: host, port, user, password and database, decoded), never the string, which postgres.js would read its own way (it takes the host after the first `@`, a missing port from `PGPORT`, and `?host=`-style parameters), so nothing in the environment or in the string picks a host or a port. `psql` is given the same parts, in `PG*` variables. TLS is required (`ssl: "require"`: encrypted and not authenticated, a row in `docs/LIMITATIONS.md`; since `api/b0-pooler-ca`, PR #46, 2026-11-13: `ssl: poolerTls()`, which checks the pooler's chain against Supabase's root and its name against the host, and psql's `PGSSLMODE=verify-full` with the root's file, `docs/plans/api-b0-pooler-ca.md`), with one connection and a 20-second connect timeout, and Postgres's warnings go through the redactor. Each script's first query is `SELECT 1` (`run.ts`, `withDatabase`), so a connection the pooler refuses fails with the script's name, the variable, the driver's words (or "no reason was given") and what to look at: "Has ops bootstrap run, and does DATABASE_URL hold the password it set?" (since PR #46, a certificate the pin refused is said as one instead: `certificateRefusal`). A failure after that is the script's own, in its own words.

- The T1 one-clock scan now has one more kept line: `dev-clock.ts` reads Postgres's own clock to turn an instant into an offset, which is the dev clock's whole job and runs by hand on `dev` only (reason in the allowlist).

## 5. `storage-setup` and `supabase-probe`

> **Changed on 2026-11-12 (ADR-034).** The first `supabase-probe` on `dev` showed that `flyctl machine exec` is cut off at about 60 seconds (`docs/LIMITATIONS.md`), so `on-machine.ts` now runs the Machine's half with `flyctl ssh console -a tadayo-api-dev --machine <id> -q -C "<command>"`, reads the command's code from flyctl's exit status and last line, says every line that came back, and then removes the WireGuard peer the session made. `EXEC_SECONDS` became `COMMAND_SECONDS`, the 300 seconds the command gets once started, inside a 600-second session. What follows is the plan as it was built in slice 10a.

- **They run in the image, on the API's Machine, because the service key does** (Fly's secrets, set by the founder, T56). The runner's half finds a started `api` Machine, then `flyctl machine exec <id> "node /app/tools/ops/src/main.ts <script> --here --ref <reference>" --json`, reads the answer's `stdout`, `stderr` and `exit_code` (the call itself exits 0 when the command failed), and prints what the Machine printed; a non-zero `exit_code` fails the run (so would an `exit_signal`, but flyctl 0.5.8 doesn't print one: fly-go's type has no such field). A command ended part way, by memory, say, may still answer with no code, so the runner also asks for the script's own last line (round 2's R1): the probe's says how its checks went, and `storage-setup` says what became of each bucket; a report without it fails the run, even with an exit status of 0. `flyctl` leaves a key out of its JSON when it is empty or zero (Go's `omitempty`, read in its source), so a command that worked has no `exit_code` at all; that is why the answer is read strictly (`on-machine.ts`, `readAnswer`): nothing but those four keys, each of the right type, is an answer, and anything else fails the script and is never read as a success. On the Machine, `SUPABASE_URL` must be the project `--ref` names, which the runner read from `SUPABASE_DEV_PROJECT_REF`: a Machine whose environment names another project refuses before any request.
- **`storage-setup`** looks at each of `uploads` and `renditions`, makes it when it is missing (private, a file-size limit of 20 MiB sent as a whole number of bytes, `image/jpeg`, `image/png` and `image/webp`) and sets it to that when it differs, which includes making a public bucket private again. It makes no object policy, never deletes a bucket or touches an object, and says what it changed. Storage answers every error with HTTP 400 and the real status in the body, so every reply's status is the body's `statusCode` when it has one.
- **`supabase-probe`** has three layers, each a list of named checks; a run passes only if all do, and its report holds statuses, codes and counts, never a key, a token or a word of a body.
  - `dataApiChecks` (runner, Management API): no schema is exposed by the Data API (`db_schema` empty). The response carries the project's JWT secret, and is never printed.
  - `databaseChecks` (Machine, as the API's role): nothing in `app` is open to `anon`, `authenticated`, `service_role` or PUBLIC (the migrations' own `closedProblems`); Storage's `buckets` and `objects` have row-level security on and no policy; and the role the Data API connects as, `authenticator`, has no `pgrst.db_schemas` setting of its own, for the cluster or for this database, that exposes a schema (such a setting wins over the project's list, and `pg_roles` shows only the cluster's, so `pg_db_role_setting` is read). Its note counts schemas and names none.
  - `apiChecks` (Machine): Supabase's three public doors, REST, GraphQL and Storage, asked as the public key alone and as a signed-in user's token, for every table of `app` and the root: each is refused or comes back empty. Since early 2026 the gateway refuses the root (`/rest/v1/`) to the public key and to a user's token whatever the Data API's state (Supabase discussion 42949), so those two lines show a refusal and not the API off; the root is asked once more as the service key, the one caller the gateway lets read it: an error passes, and an answer that describes paths fails, with their count. A project that refuses everything proves nothing, so it first shows it could see what it is refused: the service key makes a probe user, the user signs in without an email, and the service key puts one test object in each bucket, reads it back, lists it and signs it. If any control fails, the run stops there and says so, and no refusal is run. Storage's own refusal (a body naming 403, or 404 for what the caller can't see) is the only one that counts; a gateway's 401, a malformed request's 400 and a server error are failures, since none says a policy refused.
  - After the controls, one check that isn't a control and so doesn't stop the run: with the service key, every bucket of the project is private and none is there but `uploads` and `renditions` (T53: a public bucket serves its objects with no key and no policy; a third bucket is someone's, or a probe's left over). A bucket that doesn't say `public: false` isn't shown to be private. The note counts the buckets and names none.
  - It is limited in time, since `flyctl machine exec` ends the command at 300 seconds (`EXEC_SECONDS`, which the runner asks for) and a kill skips every `finally`. The checks stop asking at 150 seconds (`BUDGET_MS`), the clean-up at 240 (`DEADLINE_MS`, a minute inside the Machine's limit), both counted from the start of the Machine's half, before the database's checks, so that those count too (round 2's R2), and a call in flight at either time is ended (`AbortSignal.any`, the budget's and the deadline's). Each check that wasn't asked fails with "the run's time ran out"; a refusal that was never asked has nothing of it to clean; and a clean-up the deadline cut is a failed check that names what is left. A test gives `apiChecks` signals of its own to stand for the two limits, and one holds the defaults to what is written here: the timeouts it asks for are `BUDGET_MS` and `DEADLINE_MS`, and the deadline is at least a minute inside `EXEC_SECONDS`; two more hold that the Machine's half starts both before it opens the database and that the doors' checks use those two and no others.
  - It leaves nothing behind: everything is named `probe/<run>/…`, the user `probe-<run>@probe.invalid` and the buckets a create that wasn't refused makes `probe-<run>-anon` and `probe-<run>-user`, and a `finally` deletes each object, bucket and the user whatever failed; a clean-up that fails is a failed check naming what is left. If nothing comes back from the Machine (the call failed or timed out, or its answer was empty or unreadable), or the report has the Machine's first line, `supabase-probe: run <id>`, and not its last, the runner can't know what was left, so it says what the project may hold and how to find it by name (`run.ts`, `probeFromRunner`): a user whose address starts with `probe-` and ends with `@probe.invalid`, objects under `probe/` in `uploads` and `renditions`, and buckets whose names start with `probe-`. A report without the first line failed before it made anything (a Machine without the service key, say), and the runner says nothing more (round 2's R5).
- Run here: the database layer against the ci-like Postgres (`tests/src/db/ops-probe.test.ts`), the HTTP layers and the two Machine halves against the in-process fake Supabase that also holds buckets and objects (`ops-scripts.test.ts`, `supabase-probe.test.ts`, `storage-setup.test.ts`, `run-remote.test.ts`), including a fake whose doors leak, one whose refusals are the wrong kind, a clean-up that fails, a project that answers too slowly (a spent budget, a call ended in flight and cleaned, a deadline that cuts the clean-up) and a Machine whose report never came back. ## 6. `deploy-branch`, `worker-scale`, `fly-app-create`

- **`deploy-branch --branch <name>`** puts a branch's head on `tadayo-api-dev` for a spike, only when that commit's `ci` run is green. In order, before anything is built: the name is a branch name as the repository uses them; the checkout is the branch's head on GitHub (`GET /repos/beurni2/tadayo/branches/<branch>`) with no change and no file git doesn't know (the build takes the files as they are, not the commit's); and the `ci` runs of that exact commit, on that branch, from a push, are all done and at least one passed (`GET …/actions/workflows/ci.yml/runs?head_sha=…`). It refuses, saying why and never printing GitHub's words, a commit with no `ci` run, one still running, one that failed, and one whose runs were all cancelled or skipped (`ci` cancels an older push's run, so the head is the one commit sure to have a whole run). Then `flyctl deploy --remote-only --config fly.toml --image-label sha-<sha> --ha=false --strategy rolling --yes`, and, once it says it is done, it reads the Machines back and checks that the started ones run that image instead of taking `flyctl`'s word. A stopped worker stays stopped and is `worker-scale`'s.
- **`worker-scale --to stopped|started`** stops or starts the one `worker` Machine, never the API's, and only when the app has exactly one (a second one, Fly's standby, would start along with it). It stops the Machine and doesn't scale the group to zero: scaling down destroys Machines, and the next deploy would make new ones. It reads the state back every 3 seconds, up to 10 times, and fails if the Machine hasn't reached it.
- **`fly-app-create [--org <slug>]`** looks first and makes only what is missing: the app (the token must be an organization's, and the organization is `--org`, or the one the token sees, never a guess between several), and the certificate of `api-dev.tadayo.app`. It makes no Machine, sets no secret and allocates no address (the first deploy gives the app its IPs, which the `fly.dev` name the CNAME points to resolves to). `flyctl certs add` and `certs check` exit 0 whether DNS is ready or not, so it reads their answers and says, in words the founder can follow, what is still to do. A certificate is called issued only when the answer's detail says `Ready` or an entry lists an issued certificate (`stateOf`): an entry's `status` of `active` means Fly has verified the host's ownership, which comes before the certificate (Fly's Machines API OpenAPI document, read by review E), so in between it says the certificate is on its way and to run it again.
- When the API has no started Machine, `storage-setup`, `supabase-probe` and `deploy-branch` name the app's Machines with their groups and states (`fly.ts`, `machineList`), and say to read Fly's log of the app when an `api` Machine is there but stopped (a crash that `[[restart]]` gave up on), else to deploy first.
- Not run: `flyctl` itself ("What I checked before planning" says why and what was read instead). Each call's argument list and each reading of its JSON are tested against `fake-fly.ts`, which answers in the shapes `flyctl` 0.5.8's source prints; the shapes that source doesn't settle (what `certs check` prints between ownership and issue, whether `certs check` fails for a host never added) are read defensively and named in `docs/LIMITATIONS.md`.

## 7. `apps/web`: the skeleton

- `public/` is the site and `dist/` is what Cloudflare Pages gets (`wrangler pages deploy dist`, in 10c's `deploy-dev`): `src/build.ts` copies `public/` whole, dot-folders included (a `cp -R public/*` would skip `.well-known`). Nothing is compiled; what the build is for is what it refuses to copy.
- `public/.well-known/apple-app-site-association` is `{"applinks": {"details": []}}`: it claims no app until spike S6 adds the app ID, which needs the Team ID (the GitHub variable `APPLE_TEAM_ID`, not in the repository). The build checks it against Tadayo's own rules, stricter than Apple's format, where almost every key is optional (`checkAssociation` lists them, and a refusal says they are the house's): JSON, 128 KB at most, only `applinks`, each detail with `appIDs` (a team ID and a bundle ID each) and `components` (each with a path that starts with a slash). `public/_headers` serves exactly that path as `application/json` (Pages would guess a type for a file with no extension), and the build reads `_headers` as Pages does (each line trimmed; a path starts with a slash or a scheme): one rule for that path, which sets `Content-Type: application/json` and doesn't remove it, and no `Content-Type` set or removed under any other path, since Pages applies every rule that matches a request and joins what they set. `public/index.html` and `public/404.html` are placeholders with `noindex`, no script and no link: the real pages are B1's invitation and B9's legal pages. A Pages site with no `404.html` answers every missing path with `index.html` and a 200, which would hide a missing association file from Apple behind a web page, so the build wants a `404.html`.
- The build refuses an output folder that is the source, inside it or holding it, and erases `dist/` only after the checks pass. `ci`'s `web` step (`python3 tools/ci/ci_steps.py web`) runs `pnpm -r run build`, which its ratchet already expected once a package had a `build` script.
