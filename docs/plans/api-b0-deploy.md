## 1. The image (`Dockerfile`, `.dockerignore`)

- Two stages from the pinned base (`ARG NODE_IMAGE=node:26.13.0-trixie-slim@sha256:…`: a tag for the reader and a digest for the build, bumped by hand in a PR of its own). There is no `# syntax=` line: it would pull a floating frontend image at every build, and nothing here needs one.
  - `deps`: `npm install --global pnpm@12.16.1` (the root `package.json`'s `packageManager`; Node 26 ships no corepack), the root manifests and every workspace package's `package.json` (pnpm reads them all), then `pnpm install --frozen-lockfile --prod --filter "@tadayo/api..." --filter "@tadayo/worker..." --filter "@tadayo/ops..."`: only what the three entries need, with no dev tools, no Prism and no tests' dependencies.
  - The runtime stage: the same base, `NODE_ENV=production`, `/app` from `deps` (manifests and `node_modules`, kept as pnpm lays them: the symlinks are what makes the workspace imports resolve), then only the `src` folders of `packages/contracts`, `packages/domain`, `services/api`, `services/worker` and `tools/ops`, `USER node`. `CMD ["node", "services/api/src/main.ts"]`, which `fly.toml`'s `[processes]` replace for each group. Nothing in `tools/ops/sql`, `db/` or `docs/` goes in: the scripts that read them (`bootstrap`, `migrate`, `seed`, `dev-clock`) run from the runner's checkout, and only `storage-setup` and `supabase-probe` have a half that runs in the image (section 5).
- `.dockerignore` is an allowlist (`*`, then what the two stages copy): the build context is sent to Fly's builder, and the repository holds the design renders, the journal and anything a session leaves in the tree. `**/*.test.ts` stays out of the image.
- The image holds no secret and no key: the Supabase project's public values are `fly.toml`'s, and the secrets are Fly's, set by the founder.
- Checked by tests that read the files (`tools/ops/src/deploy-files.test.ts`, section 8): the base is pinned with a digest; its Node major is `.nvmrc`'s; pnpm's version is `packageManager`'s; every `--filter` names a package that a `[processes]` command runs (or `ops`), and every command's package is installed; the last `USER` isn't root; no `ENV`, `ARG` or `COPY` names a secret, a `.env` file or a key; the allowlist is exactly the `COPY` sources and lets `.git`, `docs`, `design`, `node_modules` and `*.env*` in nowhere.
- Run here, as evidence (`image.txt` on the `evidence` branch): the build, the image's file list (no test, no `.env`, no dev dependency), the API in `dev`'s configuration against the ci-like Postgres (with `app.dev_clock` made by `tools/ops/sql/dev_clock.sql` for the run; without it both entries refuse with the one message): the 401 on `GET /v1/me`, a TCP connect (what `fly.toml`'s check does), SIGTERM and a stop in 0.1 s with exit code 0; the worker's two lines and the same stop; both entries' refusals; and the ops entry loading in the image and refusing cleanly.

## 2. `fly.toml` and the two process groups

Each key was read from Fly's own documentation and `flyctl`'s source (the research is in the journal's entry, not the repository).

- `app = "tadayo-api-dev"`, `primary_region = "iad"`, `kill_signal = "SIGTERM"`, `kill_timeout = 30`, `[build] dockerfile = "Dockerfile"`, `[deploy] strategy = "rolling"`.
- `[env]`: `TADAYO_ENVIRONMENT = "dev"`, `SUPABASE_URL` (`https://rhsycmycocbzakrydahi.supabase.co`), `SUPABASE_PUBLISHABLE_KEY` (the `Dev` configuration's, for the probe), `LOG_LEVEL = "info"`. Nothing else: a test lists the allowed names, and checks the values against `apps/ios/project.yml` and the verifier's own rule. The secrets (`DATABASE_URL`, `SUPABASE_SERVICE_KEY`) are Fly's.
- `[processes]`: `api = "node services/api/src/main.ts"`, `worker = "node services/worker/src/main.ts"`.
- `[[services]]` on the `api` group only (`processes = ["api"]`: a section with no `processes` binds to the first group only, except `[[vm]]`, which then covers every group): `internal_port = 8080`, `auto_stop_machines = "off"`, ports 80 (`force_https`) and 443, and `[[services.tcp_checks]]` (grace 20 s, interval 15 s, timeout 3 s). It is a TCP check on the port and not an HTTP check on a path, because a path would be a route outside the contract, which the privacy matrix would have to cover (T58's rule that every route has a row), and the API listens only after the database and the clock are ready, so an open port means started. `[http_service]` can't carry a TCP check, which is why this is `[[services]]`.
- The `worker` group has no service: Fly's proxy never starts or stops it by traffic. `[[restart]] policy = "on-failure"` for both groups: a crash is restarted, a clean exit (what a stop is) is not, so a Machine `worker-scale` stopped stays stopped, and so does one stopped by hand across a deploy (`flyctl deploy` leaves a stopped Machine updated and not started). One Machine per group: `dev` has no spare, and the deploys pass `--ha=false`. `[[vm]]` is `shared-cpu-1x` with 512 MB, for both.
- No `release_command`: migrations run before the deploy, from the runner, as `tadayo_app` (TECH-DESIGN section 7), so a failed migration stops the deploy before a Machine changes.

## 3. The two entries learn to stop

- **The worker keeps running.** `services/worker/src/main.ts` starts, writes `worker: started, with no jobs yet`, and waits for SIGTERM or SIGINT, then exits 0 (`worker: stopped on SIGTERM`). It used to start, end its connection and exit 0 at once, which `startWorker`'s comment says the first of B1's jobs, or this slice if it comes first, replaces with the loop that keeps it running. Without it Fly restarts a group whose process exits, forever, and `worker-scale` has nothing to stop. The wait is a timer that holds the process open, since a database connection the pooler closes doesn't. It does no work and polls nothing.
- **The API closes on a signal.** `services/api/src/shutdown.ts` (`stopOnSignal`), used by `main.ts`: on the first SIGTERM or SIGINT, `app.close()` (Fastify closes idle connections and finishes the requests in flight), end the connection, say `api: stopping on SIGTERM` and `api: stopped`, exit 0, so a deploy cuts no request short. A second signal kills it, as it does now. A failing close writes a message that holds none of the error's words (T52, T56) and exits 1.
- Tests: `services/api/src/shutdown.test.ts` (5, with fake signals and a fake server), and `tests/src/db/startup.test.ts` (the entries as processes against the test database): each stays up after starting, exits 0 on SIGTERM and on SIGINT, writes its stop line, a second signal doesn't start a second stop, and both stop with `dev` when the database has no dev clock.

## 4. `tools/ops`: one entry, one guard, the scripts

- **One entry.** `node tools/ops/src/main.ts <script> [--option value …]`. `run.ts` holds the scripts, each with the variables it reads from the environment and the options it takes (`parseArgs`, strict, no loose word); every effect on the world comes through the context's `connect`, `spawn`, `fetch` and `sleep`, so a test gives each a fake. Every line printed goes through the redactor (`output.ts`), which knows the environment's secrets by name and by shape, and a failure prints its message and never its stack.
- **One guard** (`environment.ts`, T56). A script acts on `tadayo-dev` and nothing else. The Fly app is the constant `DEV_APP`, every `flyctl` call names it, and `flyctl` is given the Fly token and `HOME` and nothing else of the environment, and never a shell. A database is `dev`'s only by what its connection string says: Supabase's session pooler (`<region>.pooler.supabase.com`, port 5432, database `postgres`, no query or fragment, one host) with `tadayo_app.<reference>` as the user, where the reference is `SUPABASE_DEV_PROJECT_REF`. No script takes an environment's name from its caller.
- **Where each runs, and what it reads.** The names are the repository secrets' without the `DEV_` prefix; the workflow (slice 10b) maps them. This table is the interface 10b builds on.

  | Script | Runs on | Reads | Options |
  |---|---|---|---|
  | `fly-app-create` | the runner | `FLY_API_TOKEN` | `--org <slug>` (when the token sees several) |
  | `bootstrap` | the runner | `DATABASE_ADMIN_URL`, `DATABASE_APP_PASSWORD`, `DATABASE_URL`, `SUPABASE_DEV_PROJECT_REF` | none |
  | `migrate`, `seed` | the runner | `DATABASE_URL`, `SUPABASE_DEV_PROJECT_REF` | none |
  | `dev-clock` | the runner | the same | `--to <instant>` |
  | `worker-scale` | the runner | `FLY_API_TOKEN` | `--to stopped\|started` |
  | `deploy-branch` | the runner | `FLY_API_TOKEN`, `GITHUB_TOKEN` (`contents: read`, `actions: read`) | `--branch <name>` |
  | `storage-setup` | the runner starts it on the API's Machine | runner: `FLY_API_TOKEN`, `SUPABASE_DEV_PROJECT_REF`; Machine: `SUPABASE_URL`, `SUPABASE_SERVICE_KEY` | `--here --ref <reference>` on the Machine |
  | `supabase-probe` | both | runner: `FLY_API_TOKEN`, `SUPABASE_DEV_PROJECT_REF`, `SUPABASE_ACCESS_TOKEN`; Machine: `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SERVICE_KEY`, `DATABASE_URL` | `--here --ref <reference>` on the Machine |

- `bootstrap` runs `db/bootstrap.sql` through `psql` with the admin's connection in `PG*` variables (so no password is on a command line) and the app password as a SCRAM-SHA-256 verifier, made here (`scram.ts`, tested against Postgres's own for the same salt and count), so the plaintext is in no argument and no environment variable psql is given. It refuses a `DATABASE_URL` whose password isn't `DATABASE_APP_PASSWORD`, then checks that the role logs in.
- `migrate` applies `db/migrations` as `tadayo_app` (the slice-3 engine; this slice only calls it, and `migrate-cli.ts` is its by-hand entry). `seed` applies the files of `db/seed`, each in its own transaction, with the search path empty, refusing a file that opens the schema or splits the transaction; with no files it says so.
- `dev-clock` makes `app.dev_clock` when it is missing (only on a database with no occurrence, so a table that was dropped after the clock moved can't restart at no offset: T3) and with `--to <instant>` moves it forward to an instant, never by an amount, so running the same command twice can't move the clock twice; it only grows, and never more than 366 days ahead of Postgres's own clock. It refuses first if the schema isn't closed, and checks the table as the API checks it at start-up. A prod configuration is refused two ways: the guard refuses a connection string that isn't dev's, before it connects (`run.test.ts`, "refuses a prod configuration"), and `prepareClock("prod")` refuses to start on a database that has the table (`tests/src/db/clock.test.ts`, from slice 5), so a clock made by hand on prod would stop prod's API and move nothing.
- The T1 one-clock scan now has one more kept line: `dev-clock.ts` reads Postgres's own clock to turn an instant into an offset, which is the dev clock's whole job and runs by hand on `dev` only (reason in the allowlist).

## 5. `storage-setup` and `supabase-probe`

- **They run in the image, on the API's Machine, because the service key does** (Fly's secrets, set by the founder, T56). The runner's half finds a started `api` Machine, then `flyctl machine exec <id> "node /app/tools/ops/src/main.ts <script> --here --ref <reference>" --json`, reads the answer's `stdout`, `stderr` and `exit_code` (the call itself exits 0 when the command failed), and prints what the Machine printed; a non-zero `exit_code` fails the run. On the Machine, `SUPABASE_URL` must be the project `--ref` names, which the runner read from `SUPABASE_DEV_PROJECT_REF`: a Machine whose environment names another project refuses before any request.
- **`storage-setup`** looks at each of `uploads` and `renditions`, makes it when it is missing (private, a file-size limit of 20 MiB sent as a whole number of bytes, `image/jpeg`, `image/png` and `image/webp`) and sets it to that when it differs, which includes making a public bucket private again. It makes no object policy, never deletes a bucket or touches an object, and says what it changed. Storage answers every error with HTTP 400 and the real status in the body, so every reply's status is the body's `statusCode` when it has one.
- **`supabase-probe`** has three layers, each a list of named checks; a run passes only if all do, and its report holds statuses, codes and counts, never a key, a token or a word of a body.
  - `dataApiChecks` (runner, Management API): no schema is exposed by the Data API (`db_schema` empty). The response carries the project's JWT secret, and is never printed.
  - `databaseChecks` (Machine, as the API's role): nothing in `app` is open to `anon`, `authenticated`, `service_role` or PUBLIC (the migrations' own `closedProblems`), and Storage's `buckets` and `objects` have row-level security on and no policy.
  - `apiChecks` (Machine): Supabase's three public doors, REST, GraphQL and Storage, asked as the public key alone and as a signed-in user's token, for every table of `app` and the root: each is refused or comes back empty. A project that refuses everything proves nothing, so it first shows it could see what it is refused: the service key makes a probe user, the user signs in without an email, and the service key puts one test object in each bucket, reads it back, lists it and signs it. If any control fails, the run stops there and says so, and no refusal is run. Storage's own refusal (a body naming 403, or 404 for what the caller can't see) is the only one that counts; a gateway's 401, a malformed request's 400 and a server error are failures, since none says a policy refused.
  - It leaves nothing behind: everything is named `probe/<run>/…` and the user `probe-<run>@probe.invalid`, and a `finally` deletes each object, bucket and the user whatever failed; a clean-up that fails is a failed check naming what is left.
- Run here: the database layer against the ci-like Postgres (`tests/src/db/ops-probe.test.ts`), the HTTP layers and the two Machine halves against the in-process fake Supabase that also holds buckets and objects (`ops-scripts.test.ts`, `supabase-probe.test.ts`, `storage-setup.test.ts`, `run-remote.test.ts`), including a fake whose doors leak, one whose refusals are the wrong kind, and a clean-up that fails. Not run: a hosted project. The first real run is on `dev`; a refusal the real gateway words differently shows up there as a failed check with its status, never as a silent pass.

## 6. `deploy-branch`, `worker-scale`, `fly-app-create`

- **`deploy-branch --branch <name>`** puts a branch's head on `tadayo-api-dev` for a spike, only when that commit's `ci` run is green. In order, before anything is built: the name is a branch name as the repository uses them; the checkout is the branch's head on GitHub (`GET /repos/beurni2/tadayo/branches/<branch>`) with no change and no file git doesn't know (the build takes the files as they are, not the commit's); and the `ci` runs of that exact commit, on that branch, from a push, are all done and at least one passed (`GET …/actions/workflows/ci.yml/runs?head_sha=…`). It refuses, saying why and never printing GitHub's words, a commit with no `ci` run, one still running, one that failed, and one whose runs were all cancelled or skipped (`ci` cancels an older push's run, so the head is the one commit sure to have a whole run). Then `flyctl deploy --remote-only --config fly.toml --image-label sha-<sha> --ha=false --strategy rolling --yes`, and, once it says it is done, it reads the Machines back and checks that the started ones run that image instead of taking `flyctl`'s word. A stopped worker stays stopped and is `worker-scale`'s.
- **`worker-scale --to stopped|started`** stops or starts the one `worker` Machine, never the API's, and only when the app has exactly one (a second one, Fly's standby, would start along with it). It stops the Machine and doesn't scale the group to zero: scaling down destroys Machines, and the next deploy would make new ones. It reads the state back every 3 seconds, up to 10 times, and fails if the Machine hasn't reached it.
- **`fly-app-create [--org <slug>]`** looks first and makes only what is missing: the app (the token must be an organization's, and the organization is `--org`, or the one the token sees, never a guess between several), and the certificate of `api-dev.tadayo.app`. It makes no Machine, sets no secret and allocates no address (the first deploy gives the app its IPs, which the `fly.dev` name the CNAME points to resolves to). `flyctl certs add` and `certs check` exit 0 whether DNS is ready or not, so it reads their answers and says, in words the founder can follow, what is still to do.
- Not run: `flyctl` itself. Each call's argument list and each reading of its JSON are tested against `fake-fly.ts`, which answers in the shapes the documentation and `flyctl`'s source give; the shapes that aren't documented (the Machine list's `image_ref`, `config.image`, the certificate's fields) are read defensively and named in `docs/LIMITATIONS.md`.

## 7. `apps/web`: the skeleton

- `public/` is the site and `dist/` is what Cloudflare Pages gets (`wrangler pages deploy dist`, in 10c's `deploy-dev`): `src/build.ts` copies `public/` whole, dot-folders included (a `cp -R public/*` would skip `.well-known`). Nothing is compiled; what the build is for is what it refuses to copy.
- `public/.well-known/apple-app-site-association` is `{"applinks": {"details": []}}`: it claims no app until spike S6 adds the app ID, which needs the Team ID (the GitHub variable `APPLE_TEAM_ID`, not in the repository). The build checks it as iOS 13 and later read it: JSON, 128 KB at most, only `applinks`, each detail's `appIDs` a team ID and a bundle ID, and refuses it otherwise. `public/_headers` serves exactly that path as `application/json` (Pages would guess a type for a file with no extension), and the build checks that rule. `public/index.html` and `public/404.html` are placeholders with `noindex`, no script and no link: the real pages are B1's invitation and B9's legal pages. A Pages site with no `404.html` answers every missing path with `index.html` and a 200, which would hide a missing association file from Apple behind a web page, so the build wants a `404.html`.
- The build refuses an output folder that is the source, inside it or holding it, and erases `dist/` only after the checks pass. `ci`'s `web` step (`python3 tools/ci/ci_steps.py web`) runs `pnpm -r run build`, which its ratchet already expected once a package had a `build` script.
