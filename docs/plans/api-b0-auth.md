## 1. Tokens and the gate (`services/api`)

- **`jose` 6.2.13** (MIT, no dependencies, published 20 October 2026, 22 days before the slice; the library Supabase's own guide uses). `src/identity/token.ts`:
  - `verifierFor(keys, { issuer })`: `jwtVerify` with `algorithms: ["ES256", "RS256"]` only (no `none` and no keyed hash, so a public key can never act as a shared secret), a key id named in the token's header (a token that doesn't say which key signed it is no session: without one the library picks the one key of the algorithm the set holds and refuses when a rotation puts two there, so the answer would depend on the set), `issuer` exact, `audience: "authenticated"`, `exp` and `sub` required, then `role === "authenticated"`, `sub` a UUID (lowercased), `is_anonymous` not true, and at most 8,192 bytes in compact form. It returns the subject and nothing else: the claims, the email among them, never leave it.
  - `supabaseProject(url)`: `url` must be `https://<20 lowercase letters>.supabase.co` with no path, port, credentials, query or fragment (a typo or a dashboard URL stops the API); `issuer` is `<origin>/auth/v1`, the keys `createRemoteJWKSet` on `<origin>/auth/v1/.well-known/jwks.json` with `cacheMaxAge` 10 minutes, `cooldownDuration` 30 s and `timeoutDuration` 3 s, and no fetch for 5 seconds after a failed one.
  - Two outcomes only: **no session** (everything wrong with the token: shape, signature, algorithm, key id, issuer, audience, role, expiry, subject) and **can't tell** (the key set unreachable, timed out, not JSON, malformed, empty (a project still on the legacy secret) or paused after a failure). Can't tell is a 503 with an empty body and an error log of one fixed word, never a 401, since the app ends a session on a 401 (FQ89) and a Supabase hiccup must not sign people out. No stale key is kept: a key set that can't be read once its 10 minutes are up means no token is judged.
  - A token's expiry is Supabase's own time, the library's wall clock, never the server's clock (T1's clock decides drops, and `dev`'s offset must not expire real tokens). No line of ours reads a clock (`packages/domain/src/time/one-clock.test.ts` keeps passing). The matrix's phase a year on proves it end to end.
- **The gate** (`src/session.ts`, one Fastify `onRequest` hook, driven by each contract route's `config`; Fastify's own answers stay neutral for everyone, since they carry no operation). It runs before the body is read, so a malformed body from a caller without a session is a 401:
  1. A `public` operation (`removeDevice`, `previewInvitationWeb`) skips it: no header is read, no account made.
  2. `Authorization: Bearer <token>` (the scheme in any case, one space) else 401.
  3. Verify, then the account for the subject (below). An account that isn't `active` is a 401: T27's "a deletion ends access at once", read on every request.
  4. An operation that isn't `beforeProfile`, for an account without the age confirmation or a name: 403 `PROFILE_INCOMPLETE` (FQ13, FQ69).
  5. Otherwise the handler gets `request.account`. The 63 operations nobody has built yet (66 in the contract, 3 built here) answer the neutral 404 to a caller the gate lets through.
- **One 401 for every cause**, byte for byte: `{"code":"UNAUTHENTICATED"}`, `Cache-Control: private, no-store`, `Content-Type: application/json; charset=utf-8`, no `WWW-Authenticate` (the contract declares none). The 403 likewise, with its own code. One module writes every answer with a body (`src/answers.ts`).
- **The account** (`packages/domain/src/identity/account.ts`): a `SELECT` by `auth_subject` first (the hot path, one query); none: `INSERT … ON CONFLICT (auth_subject) DO NOTHING` and a `SELECT` again, so a first sign-in retried or sent twenty times at once finds one row (0003's comment). `created_at` is the server clock's sample (T1). The row keeps no email, no phone, no claim; the subject is never logged. `newId("acct")` is `acct_` and 16 random bytes in base64url (`packages/domain/src/ids.ts`), as the tests' own ids are. A deleted account's shell has no subject, so its old token finds none and makes a new account (`docs/LIMITATIONS.md`; B6's deletion job closes it).
- **One seam for tests**: `buildApp({ sql, clock, authenticate, log })`, where `authenticate(header)` returns an `Account`, `null` (no session) or throws "can't tell". `sessions({ verifier, sql, clock })` composes the real one. `services/api/src/testing.ts` (export `@tadayo/api/testing`, as the domain's `./testing`, outside the main entry so no product code imports it) makes a test signer: a P-256 key, its key set and `token(subject, options)`, so the verifier's tests, the gate's and the matrix sign the same way. `startApi(env)` reads `SUPABASE_URL` (new, required, public) and `LOG_LEVEL` (default `info`); slice 10a puts `SUPABASE_URL` in `fly.toml`'s `[env]`.

## 2. The three routes

- **`GET /v1/me`**: `Me` from the account the gate loaded (`avatar_version` is the content version of a ready avatar upload, else absent; no email, ever). An explicit field list (T55), parsed in the tests with the contract's own schema.
- **`PATCH /v1/me`** (`packages/domain/src/identity/update-me.ts`, the first command, so it sets the pattern of TECH-DESIGN section 5), in one READ COMMITTED transaction. A refusal is a thrown `Refused` (`packages/domain/src/refused.ts`), which rolls everything back, the receipt included; the route turns it into the contract's answer, so the command knows nothing of HTTP:
  1. Before the transaction: the `Idempotency-Key` header a UUID, then the body by the contract's `UpdateMeRequest`, else 400 `INVALID_REQUEST` with `field` the first bad field, only a field the contract names (never an unknown key, never a value). Authentication was first.
  2. The clock is sampled once, first: the receipt's `created_at` and the age confirmation's instant. `updateMe` has no time rule, unlike the commands whose cutoffs must read the clock after their locks (T3).
  3. Reserve the receipt (`INSERT … ON CONFLICT DO NOTHING`); a key seen before is a replay of the stored `Me`, byte for byte, when the request hash matches, else 409 `IDEMPOTENCY_CONFLICT` (`requestHash`, `replayOutcome`).
  4. Lock the account's row, `FOR NO KEY UPDATE`: the receipt's own insert has already taken `FOR KEY SHARE` on it (its actor guard, `db/migrations/0009_platform.sql`), and two requests of one account that each went on from that to `FOR UPDATE` would wait for each other for ever. Not `active` now: 401.
  5. `expected_version` against the row's: 409 `VERSION_CONFLICT` with `current_version`.
  6. `age_confirmed: true` sets `age_confirmed_at` once (the trigger refuses anything else). A `display_name` or an `avatar_upload_id` needs the age confirmed, in this request or before: else 400 with that field. An avatar upload must be the caller's own, of purpose `avatar`: no such upload is 404 `NOT_FOUND` (a guessed id, another account's and a drop's photo get the same bytes, T14), one not `ready` is 409 `MEDIA_NOT_READY`, a ready one sets `avatar_upload_id`.
  7. Only a field that changes counts: no change writes nothing and moves no version, any change moves `version` by one. The receipt is completed with `Me`, and the answer is read back from it, so a replay is the first answer byte for byte.
  - **Not here**: the new roster revision a rename makes for someone who accepted an open one (FQ66, FQ84) is B1's, with the revision commands; no roster can exist through the API before then, and B1 must take the club's row before the account's (section 5's lock order). Pinned by a test that says what happens today, and recorded as B1's "Next".
- **`GET /v1/clubs`** (`packages/domain/src/clubs/club-list.ts`): both lists in one statement, so one snapshot, in a read-only transaction.
  - `server_now` is `contractInstant` of a clock sample taken in that transaction: whole seconds, rounded down.
  - `clubs`: each club where the caller has an *active* interval, oldest membership first, at most 50 (the contract's bound; B1 settles a cap per person): `id`, `name`, `timezone`, `my_membership_id`, `member_count` (active members), and `state`: `suspended` if `suspended_at`, else `proposed` if not `activated_at`, else `paused` under two active members, else `active` (a pure function with its own tests). **`open_day` and `next_day` are left out until B2** (Home's day logic; the contract makes them optional; no club can exist through the API before B1 and no B0 screen reads them); the row pins that, and B2 adds them with their checks.
  - `invitations`: each invitation whose link this account is bound to (`bound_user_id`) and whose candidate hasn't joined, newest first, at most 50: `invitation_id`, the club's `club_name`, the `inviter_name` (the candidate's proposer, by FQ75's rule: the interval's name while it is active, the name it ended with after), and `state`: `did_not_go_ahead` when the candidate ended; else `waiting` when the open revision lists the candidate as accepted with this link; else `roster_changed`. An invitation with no name to show for its inviter (a deleted account's empty name) is left out, a limit recorded for FQ75, needed by B6, which builds the deletion (this line said B1 until the check of the review's fixes). Nothing else of the club.
  - A new account that has finished its profile: `{ "server_now": …, "clubs": [], "invitations": [] }`. **An account that hasn't finished it gets 403 `PROFILE_INCOMPLETE`**, because the contract doesn't mark `listClubs` `beforeProfile`: the app reads `GET /v1/me` first (which does work before the profile is finished) and asks for clubs once the profile is. Flagged in the PR for the ios lane; if the app asks earlier, the contract changes in its own PR.

## 3. Logging (T52)

- Fastify's own request lines are off through its `logController` (`new LogController({ disableRequestLogging: true })`), since they carry the path and the query, and its `req` and `res` objects; so is its error line for a route it doesn't know. What is left of Fastify's is its one line when the server starts (its address and port) and the line of a request refused while the server closes, which names no one. Our own `onResponse` hook writes the one line a request gets: `reqId` (96 random bits, never Fastify's counter and never a header the caller sent), the operation's id, the status and the milliseconds. No URL, query, header, body, address or claim ever reaches a line; an error is logged as its class and its `code` only (Postgres's messages quote rows). pino's `redact` lists every T52 field (authorization, cookie, token, caption, text, body, note, url, email, push, exif, secret, names, the account and its subject, whole requests and answers …) at the top and one level down, so a later `log.info({ request })` still comes out `[redacted]`. `LOG_LEVEL` sets the level.
- **The log test** drives requests that carry an email address (in the token's claims, a body, a query, a header, an error's message), the token itself, a caption-like string and a subject, then asserts none of them is in the captured output, across a 200, a 400, a 401, a 403, a 409, a 404, a 503 and a 500; and `tests/src/db/startup.test.ts` pins the started process's own log to the listening line and one line a request.

## 4. The privacy matrix and the leak scanner learn the account routes (`tests/src/privacy`)

- **Real tokens.** The app is built with the real verifier on a test key set, the real account lookup and the fake clock. Every request of every cell carries a token signed for the role's account, so what an account's state makes of a request is the gate's, not a stand-in's.
- **12 roles**: the 11 of slice 6's world and "signed in, profile not finished (FQ13, FQ69)": an account with no age confirmation and no name. Each role's `session` (`active`, `unfinished`, `deleting`) is read from its account's row (`sessionOf`) and asserted equal to the role's own, so a role can't claim a state its row doesn't have. The gate's answer is a function of the operation and the session alone, pinned byte for byte in `account.ts` (`gateOf`, with its own copy of the contract's `public` and `beforeProfile` sets, which `account.test.ts` asserts equal to the contract's flags): `deleting`: 401 on every non-public route; `unfinished`: 403 on every non-public route that isn't `beforeProfile`; the same for every id, guessed or malformed, cursor and manipulated parameter, so an id can't change a gated answer (T14).
- **Rows.** `NONE` stays for the 63 operations nobody has built. `rows.ts` gives `getMe` (`ME`), `updateMe` (`UPDATE_ME`) and `listClubs` (`CLUBS`) their rows; `rowProblems` still refuses an operation with no row, a row with no operation, a row that isn't `NONE` and that nothing judges (`JUDGED`), and an operation judged whose row is `NONE`. For each cell the expected answer is computed in the test from the world's rows in plain code, never from the API's SQL (`cellExpected`): `getMe` (`Me`: the viewer's id, name, age, version, avatar version), `listClubs` (`clubsJudge`: the viewer's active clubs with their members counted, the invitations bound to them whose candidate hasn't joined and whose inviter has a name, and the server's instant), `updateMe` the 400 of a body-less request.
- **A body table for `updateMe`** (`updateMeCases`), each body with its exact answer, in every cell, per session: a name the contract refuses (400, `display_name`), a field it doesn't have (400), a version that isn't the account's (409 with the version), another account's avatar, an upload that names nothing and a drop's photo (404, the same bytes: one group, compared across the three), the viewer's own avatar not ready (409 `MEDIA_NOT_READY`), then the changes, after which the world is read again: the viewer's own ready avatar (200, its version in `Me`) and a new name (200). For the unfinished role: a name or an avatar before the age (400 with its field), and in the last phase the age and a name together (the profile is finished). For an account whose deletion has begun, every body gets the gate's 401, valid or not, before the body is read (T27).
- **Callers without a session**: the 3 of slice 7 and 16 kinds of token that are signed with real keys and name an account that exists, and still aren't a session (`tokens.ts`): an expired token, one not yet valid, one with no expiry, one signed by another key under this key's id, a token of another project, a key id the set doesn't hold, none at all, an unsecured token (`alg` none), a legacy shared secret's, another issuer, another audience, a service role's, an anon role's, an anonymous person's, no subject, a subject that isn't a UUID. Each gets the same 401 for every route that isn't public and the neutral 404 for the two that are, with the cell's ids, ids that name nothing and another club's, and a forged cursor; and each sends `updateMe` a valid body, a broken one and none: the 401 for all three. A deleted account's token isn't one of them: its subject is gone, so its token makes a new account (`docs/LIMITATIONS.md`; B6).
- **The scanner** (`scanner.ts`, its own tests first): `Viewer.account` and `WorldFacts.accounts` and `invitations`. New world checks: `Me` is the viewer's own (its `id`, `display_name`, `avatar_version`, `age_confirmed` and `version` are the row's); **no account id appears in any answer but the viewer's own `Me.id`** (found in a string, a header or a cursor's bytes); `MyInvitation`: its id is bound to the viewer and its candidate hasn't joined, and its `club_name` and `inviter_name` are that invitation's; the two names are the viewer's own text for the invitation they accepted and nobody else's (the header's slice 8 clause); no other invitation id is anywhere (T14). The sign-in token's claims are canaries that fail anywhere they appear: the test address, each account's subject, each token.
- Planted proofs, as slice 7 did: each new check has a planted leak in `scanner.test.ts` that only that check catches.
- **Not here**: a `ClubSummary` carries no `open_day` or `next_day` until B2 (the row's pin).
