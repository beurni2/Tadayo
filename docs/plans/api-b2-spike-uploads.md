# B2: Spike S1's server half, its first PR: the upload intent (`api/b2-spike-uploads`)

`POST /v1/uploads`, `GET /v1/uploads/{upload_id}` and `POST /v1/uploads/{upload_id}/complete`, the contract's `createUpload`, `getUpload` and `completeUpload`, for a drop's photo (spec 10, 11, 32, 33; TECH-DESIGN sections 5, 6 and 8; ADR-009, ADR-014, ADR-015, ADR-024; T3, T4, T9, T12, T14, T15, T17, T18, T19, T52, T53, T55, T56; D09, D10). Made from `main` at `e40b462`.

## 0. Where this sits, and the split

1. **Gate A needs spikes S1, S2 and S4, and their server halves are the api lane's.** B2's api work is on `main` (the schedule, generation, Home, reservations), and Gate 0 waits only on the founder's device run of spike S6. Spikes S1, S2 and S4 run once B1 and B2 are on `dev`, before Gate A and before B3 and B4 build media and contributing on them (ADR-024; `docs/MILESTONES.md`, B2, "Spikes S1, S2 and S4"). `docs/plans/B0.md` section 4 says what each needs on the server, and that "the B2 plan names their branches and schedules them". B2 was planned as one plan per PR, so this plan is that schedule for the api lane's half:
   - **S1, the share extension:** "on the server a minimal upload intent, signed upload URL and commit, so the receipt comes only after the commit". Two PRs: this one, the intent and its signed upload URL, then the commit, `api/b2-spike-commit` (`createDrop` for a photo: the receipt, the locks, the clock after them, the role's limits with the reservation consumed, the immutable audience and its seal; T3, T8, T17, T19, T20).
   - **S2, the photo pipeline:** "the worker's preparation (signature, limits, metadata stripped, renditions), timed on `tadayo-api-dev`", on S1's branches: `api/b2-spike-prepare`, the worker's outbox poller and its `upload.prepare` handler with `sharp` (TECH-DESIGN section 5, "Media pipeline", step 2), which this PR's `completeUpload` starts. It comes after this PR and before the commit's, since only a ready upload can be committed.
   - **S4, push:** device registration, the worker's APNs sender, quiet hours with the dev clock and the deep link, after S1's: it needs `APNS_KEY_ID`, `APNS_KEY_P8` and `APPLE_TEAM_ID` on Fly, which the founder adds when asked (ADR-024's consequences).
   - Spike code merges only if it's clean enough to keep (`docs/MILESTONES.md`), and spike routes are held to the invariants like any other (`docs/plans/B0.md` section 4): each calls the authorization module, has its privacy-matrix row and is scanned. So each of these PRs builds its routes as B3 will keep them, for a drop's photo, and B3 adds what the spikes don't need.
   - Each merges to `main` and reaches `dev` through `deploy-dev`, so no `deploy-branch` run is needed. The device runs themselves need the founder's account in an active club on `dev`, formed in the app (ADR-021, ADR-024), and the ios lane's share-extension build.
2. **This PR builds the drop's photo purpose only.** `CreateUploadRequest` has four purposes. `drop_photo` is the one S1 uses. `replacement` comes with B4's edits (`updateDrop`), `avatar` with the avatar's commit and its image route (`getMemberAvatar`, deferred by `docs/plans/api-b1-clubs.md` to "spike S1's server part, then B3"), and `conversation_photo` with B6's photo replies (T63, T64). Until each is built, `createUpload` answers it as the skeleton answers every unbuilt route: the neutral NOT_FOUND, with nothing made and no receipt. `getUpload` and `completeUpload` are built whole: they read and complete whatever upload the caller owns.
3. **The signed upload URL is signed after the transaction commits, and never stored.** Signing calls Supabase Storage over HTTPS; holding the day's and the counter's locks across a network call would make every other request on that counter wait for Storage. So `createUpload`'s transaction writes the upload and stores its receipt, whose body has no URL (TECH-DESIGN section 6: "the stored response leaves out" the URL), and commits; the handler then signs a URL for the upload's object and adds it as `signed_upload`. A replay finds the stored body and signs a new URL for the same object while the upload is still pending, and none once it isn't (the contract's `createUpload`; TECH-DESIGN section 6). When signing fails, the answer is a 503 with no body and the upload stays pending, so a retry under the same key replays the receipt and signs again; nothing about the failure reaches the log but its code (T52).
4. **The intent is for one random object, write only, with overwriting off (T12).** The object's key is 24 random bytes in base64url, 32 characters, made by the server, never derived from the account, the day or the bytes, and leaves the server only inside the signed URL. The URL is signed with the service key, which only the API and the worker hold (Fly secrets; TECH-DESIGN section 7), with upsert off, so once bytes are put nobody can put over them. Storage takes both the object and upsert from the signed token's own claims (`url`, `upsert`), so the client believes a token only when its `url` is this object in `uploads` and its `upsert` is false, and refuses any other as an error (round 1's P1); the Supabase probe proves on each project that a second `PUT` to the signed URL, other bytes with `x-upsert: true`, gets Storage's 409 and leaves the bytes as they were (section 1, "Storage"). The bucket `uploads` is private, with D09's 20 MiB and JPEG, PNG and WebP only (`tools/ops/src/storage-setup.ts`), so Storage refuses anything larger or of another declared type. The answer's `signed_upload` gives the full `https` URL, `PUT`, the headers to send (`Content-Type` as declared, and `x-upsert: false`), and `expires_at`: the clock's sample plus the token's own lifetime (its `iat` to its `exp`, read, never assumed), and never past the upload's own `expires_at`, after which the upload is nobody's (round 1's D4). The headers are named by the route, never copied from Storage's answer (T55).
5. **The signed URL's lifetime is Storage's own (section 1, "Storage"), and D10 doesn't bound it.** D10's five minutes is for a "signed media URL", which spec 33 places beside "no recipient media token is issued before reveal": a URL that reads media. No URL that reads storage ever leaves the server (ADR-009, T12), so D10 binds nothing a client gets. The upload URL writes one object of the caller's own, once, and the contract's examples give it Storage's two hours (`packages/contracts/src/fixtures/examples.ts`, `createUpload.pending`).
6. **An upload lives 24 hours from its intent, then counts as gone.** `uploads.expires_at` is the intent's instant plus 24 hours, as the contract's examples have it. A reservation lapses after 30 minutes, never past the reveal (`docs/plans/api-b2-reservations.md` section 0.4), but a ready upload can still be committed after its reservation lapsed, taking a free slot (`createDrop`'s description), and the app's draft keeps the photo meanwhile (FQ15). From its `expires_at` on, an upload is answered as one nobody has: `getUpload` and `completeUpload` give the neutral NOT_FOUND, and the commit will too. Deleting lapsed uploads and their objects is the purge job's (B3, with the worker's outbox in `api/b2-spike-prepare`); until then a lapsed row and its object stay private and unread.
7. **Who may start a drop's photo: only the holder of a live photo reservation in a day still collecting** (`DropPhotoUploadRequest`: "only a member with a held slot can write to storage"). The reservation is named by the body. The rules are the reservation's own (`docs/plans/api-b2-reservations.md` section 1), so they can't drift: who may add to the day (`addTargetOutcome`), then whose the reservation is (`ownsReservation`), both in the authorization module (T9).
   - A reservation that isn't the caller's, an earlier interval's after a rejoin, a guessed id, a link's reservation, or one no longer live (released, used, or lapsed at its `expires_at`): NOT_FOUND.
   - **One slot, one photo** (round 1's P2): a reservation that already holds an upload that isn't rejected, pending, preparing or ready, gives NOT_FOUND to a new key, so one live slot can't make any number of objects. After a rejection the slot takes another photo; otherwise the app releases the slot and holds a new one. The same request under the first key is the replay (section 0.8). The app holds the reservation's `expires_at` and its own release, so it knows to hold a new slot; the answer says nothing it doesn't know (T14).
   - A day whose star has gone (held, FQ63): MEMBERSHIP_CHANGED with no other field, as `createReservation` answers it.
   - From the reveal on: OCCURRENCE_CLOSED with `target` and `next_target` (T3, T4). A reservation never outlives the reveal (`app.reservations_guard`), so this answer and the lapse meet at the same instant; the cutoff is checked first, so the app is told the day opened, not that its slot is gone.
   - An account without a finished profile: PROFILE_INCOMPLETE, from the route, for every purpose but `avatar` (the contract: "Only the avatar's purpose works before the profile is finished"). The gate lets `createUpload` through before the profile (`beforeProfile`), so the route says it.
8. **Idempotency (T19).** `createUpload`'s receipt is the caller's, for the operation and the `Idempotency-Key`, over the body, made through `reserveAsMember` with the caller's interval as `createReservation`'s is (FQ112's default: a key an earlier interval used names nothing to the new one). The same request under the same key gets its first answer back, with a new URL while the upload is pending and without one after; another body under it is IDEMPOTENCY_CONFLICT. `completeUpload` takes no key (the contract): repeating it returns the current state.
9. **`completeUpload` checks that the bytes are there, then hands the upload to the worker.** It asks Storage, with the service key, for the object's details, before any transaction: a missing object is MEDIA_NOT_READY and changes nothing. Then, in one transaction, it locks the upload's row, and an upload still pending becomes `preparing`, with an `upload.prepare` event in the outbox under the dedupe key `upload.prepare:<upload id>` (T54), whose payload holds the upload's id alone (T52). An upload already past pending is answered as it is: repeating it returns the current state, 202. The worker's handler is `api/b2-spike-prepare`'s; until it merges, a completed upload stays `preparing`. `completeUpload` doesn't recheck the reservation or the day: preparing a photo grants nothing, and the commit checks everything again under its locks.
10. **The database's last guards.** `db/migrations/0016_upload_reservation.sql` adds `app.uploads_reservation_guard`, BEFORE INSERT on `app.uploads` for a drop's photo: its reservation is `live`, for a photo, and its `expires_at` is after the upload's `created_at`, read `FOR SHARE` so a release or a lapse settled meanwhile waits for the upload's transaction, and an upload waits for a change in flight. And `uploads_one_per_reservation`, a unique index on `reservation_id` over the uploads that aren't rejected (section 0.7). It adds and changes no column and drops nothing (FQ39), and checks only get stronger (T58): no project has a drop's photo upload yet. The domain checks both first, under the counter's lock; the guards are behind it. **The lock order every writer of a drop's photo upload keeps:** the counter's lock (`FOR NO KEY UPDATE`) before the insert, whose guard then reads the reservation `FOR SHARE`, the order a release takes them in (counter, then reservation), so the two wait on each other only at the counter (round 1's D2).
11. **An upload is the account's own, not an interval's** (round 1's P5). `getUpload`, `completeUpload` and a replay's signing go through `ownsUpload` in the authorization module (`packages/domain/src/authorization/upload.ts`): the owner's until its `expires_at`, nobody's from it on. So a member who left can still read the state of an upload they started until it lapses, and complete it, which grants nothing: the upload names only its own id, purpose, state and expiry, never the day or the club (T14). Starting one checks the reservation's interval (`ownsReservation`, before the receipt and again under the locks), and the commit (`api/b2-spike-commit`, then B3) checks the reservation's interval again under its locks, so nothing a former member uploaded can reach a day.

## 1. What each route answers

### `createUpload`, one command for a drop's photo (TECH-DESIGN section 5)

1. **The request**, parsed by the contract's `CreateUploadRequest`: the `Idempotency-Key` first, then the body, strict. A purpose other than `drop_photo`: NOT_FOUND (section 0.2). An account without a finished profile: PROFILE_INCOMPLETE (section 0.7).
2. **Who may, with no lock:** the reservation's day by `loadAddTarget` and `addTargetOutcome`, then `ownsReservation`. A caller the day gives nothing, or whose the reservation isn't: NOT_FOUND, before the receipt (T14).
3. **The receipt** (`reserveAsMember`, the clock's first sample its `created_at`): a replay returns its stored body here, and the handler signs again if the upload is still pending (section 0.3).
4. **The locks, in TECH-DESIGN's order:** the club's row and the day's `FOR SHARE`, the caller's and the star's membership rows `FOR SHARE`, the counter `FOR NO KEY UPDATE` (`lockCounter`), then the reservation `FOR SHARE`. Every change of a reservation's state happens under its counter's lock (`docs/plans/api-b2-reservations.md` section 1), so its state read after it is final for the command.
5. **The clock after the locks** (T1, T3), and the facts again.
6. **The policy, in this order:** step 2's rules again, `ownsReservation` on the facts read under the locks (NOT_FOUND); a held day (MEMBERSHIP_CHANGED); the cutoff (OCCURRENCE_CLOSED with `target` and `next_target`); the reservation live at the sample, for a photo (`state = 'live'`, `expires_at > at`, `media_class = 'photo'`), and holding no upload but rejected ones (section 0.7), else NOT_FOUND. Lapsed reservations are not settled here: settling changes the counter's counts, which is the reservation's and the commit's business, and a lapsed one is refused whether settled or not.
7. **The write:** the upload, `pending`, with a new `upl_` id, the owner, `drop_photo`, the reservation, the declared type and size, the object's key (section 0.4), `created_at` the sample and `expires_at` 24 hours on (section 0.6).
8. **The answer:** the contract's `Upload` without `signed_upload` (`id`, `purpose`, `state`, `expires_at`), stored in the receipt, 201. After the commit the handler adds `signed_upload` (section 0.3).

### `getUpload`

The caller's own upload, live (`expires_at` after the clock), by `ownsUpload` (section 0.11), with no lock: its `UploadStatus` (`id`, `purpose`, `state`, `rejection` when rejected, `expires_at`), never a URL (T12). Anyone else's, a lapsed one, a guessed id: NOT_FOUND (T14). It works before the profile is finished (the contract).

### `completeUpload`

1. The caller's own live upload, as `getUpload` finds it, else NOT_FOUND.
2. Still pending: Storage is asked whether its object is there (section 1, "Storage"). Not there: MEDIA_NOT_READY, nothing changed.
3. One transaction: the upload's row `FOR NO KEY UPDATE` (round 1's D3: nothing references an upload's key yet, and no stronger lock is needed), the clock, ownership and life again by `ownsUpload`; if still pending, `preparing`, and the `upload.prepare` event, `available_at` the sample.
4. The answer: 202 with its `UploadStatus`, whatever its state. It works before the profile is finished (the contract).

### Storage

`services/api/src/media/storage.ts`, the API's only Storage client, with the service key from `SUPABASE_SERVICE_KEY` (Fly secrets, T56) and the project's URL from `SUPABASE_URL`, which the API already reads:
- `signUpload(objectKey)`: `POST /storage/v1/object/upload/sign/uploads/<key>` with the body `{}` and no `x-upsert: true`. Storage's source (`supabase/storage`, `src/http/routes/object/getSignedUploadURL.ts`) reads upsert from that header alone, `=== 'true'`, and carries it in the token; the `PUT` (`uploadSignedObject.ts`) takes upsert from the verified token, never from the `PUT`'s own header, so a client can't turn it on. It answers `{ url, token }`, `url` relative. The client builds the full URL itself, `<SUPABASE_URL>/storage/v1/object/upload/sign/uploads/<key>?token=<token>`, the form the Supabase probe's `PUT` uses on `dev` after every deploy (`tools/ops/src/supabase-probe.ts`), and reads the token's own `exp` for `expires_at`. The lifetime is Storage's setting (`uploadSignedUrlExpirationTime`; `storage-js` documents two hours) and the caller can't choose it. A token whose `iat` and `exp` can't be read, or are less than a minute or more than a day apart, or whose `url` claim isn't `uploads/<this key>`, or whose `upsert` claim isn't `false`, is refused as an error, never assumed (`signedLifetime`); each of the token's three parts must be plain base64url. It answers `{ url, lifetimeSeconds }` and nothing else of Storage's. The session can't reach supabase.com's documentation (`docs/LIMITATIONS.md`); so the Supabase probe (`tools/ops/src/supabase-probe.ts`) now signs its upload URL exactly as this client does, with the body `{}` and no `x-upsert`, and its control "the service key signs an upload URL" holds only when Storage's answer is a 200 in its status and its body, and the token is one this client believes, read by the same rule (`believedUploadToken`: this object, `upsert` false, a minute to a day); its control "the signed URL puts nothing over the object" sends a second `PUT`, other bytes with `x-upsert: true`, which must get Storage's 409 and leave the bytes as they were; and its new control "the service key finds the object's details" asks for its object's details as `objectThere` does, which must find the object it put and Storage's own not-found for one never put, read as this client reads them (`storageStatus`). `deploy-dev` runs the probe on `dev` at this PR's merge, so a project whose tokens this client can't believe, or whose answers to `objectThere` it would misread, fails there, not at a person's first upload.
- `objectThere(objectKey)`: `GET /storage/v1/object/info/uploads/<key>` with the service key: true on a 200 whose status in the body is 200 too and whose body is a JSON object, false when Storage says the object isn't there, and an error for anything else, which the route answers 503 with no body. Storage answers errors with HTTP 400 and the real status in the body's `statusCode` (`tools/ops/src/supabase.ts`), so the client reads that: a `HEAD` has no body, and `storage-js`' `exists()` takes every 400 as missing, which would read a refused key as "not there". Only a 404 in the body, or a plain 404, is missing.
- Every call carries the key as Storage asks (`tools/ops/src/supabase.ts`' header comment says how the gateway reads `apikey` and `Authorization`), has a timeout, and never logs a URL, a token or a key (T52, T56). A test fake (`services/api/src/testing.ts`) stands in for it in every test; the real one is tested against a fake `fetch`.
- `services/api/src/start.ts` refuses to start without `SUPABASE_SERVICE_KEY`, as it does without `SUPABASE_URL`. Fly's secrets reach both process groups, and `storage-setup` already reads the key on the API's Machine (`tools/ops/src/run.ts`).

## 5. For the ios lane

When this merges and is on `dev`: the share extension's upload is `createReservation` (photo), `createUpload` with `{ purpose: "drop_photo", reservation_id, content_type, byte_size }` and an `Idempotency-Key` kept with the queued item, a `PUT` of the bytes to `signed_upload.url` with exactly `signed_upload.headers` before `signed_upload.expires_at` (a background `URLSession` upload task), then `completeUpload`, then `getUpload` until it is `ready` (once `api/b2-spike-prepare` merges), then `createDrop` (once `api/b2-spike-commit` merges). A replay of `createUpload` under the same key gives a new URL for the same object while the upload is pending, so a transfer iOS lost can start again; a `PUT` after the bytes are in is refused by Storage (upsert off: HTTP 400 with `statusCode` "409" in the body), and the app goes on to `completeUpload`. A slot holds one photo: a new `createUpload` under a slot whose upload is pending, preparing or ready is NOT_FOUND, so the app retries under the same key, and holds a new slot (releasing the old one) for another photo; only after its upload is rejected does the same slot take another. `signed_upload.expires_at` is never past the upload's own `expires_at`.
