## 1. What changes

**The four states, by answer** (`i.js` `outcomeOf`, `check`):

| State | When | Shows |
|---|---|---|
| checking | at once when the script starts, and again after Retry | "Checking invitation…" (utilityTitle 32/35 bold, primaryText); no Retry on the first load, its slot kept so Get Tadayo doesn't move; after Retry, Retry stays in place, busy (frame 12) |
| failed, network | no complete answer: the request failed (a connection, a CORS refusal, a redirect), the 15-second wait ran out, or the answer's body couldn't be read as JSON | "Couldn’t check the invitation link." (utilityTitle) over "Check your connection and try again." (body 17/23, secondaryText), Retry, Get Tadayo (frame 13) |
| failed, answered | an answer read in full that is neither a 404 nor a 200 with a name: a 400, a 429, a 5xx, a 200 without a usable name; and a page with no API named, which can't ask | "Couldn’t check the invitation link." over "Try again.", Retry, Get Tadayo |
| invited, unavailable | a 200 with a name; a 404 or a fragment that holds no token | as before (`G02-web`, `G02-web-revoked`) |

A 200 whose body isn't JSON is read as no usable answer, a connection's fault: over HTTPS and CORS, a captive portal's page can't reach the script as a readable 200 (it comes as a redirect, which `redirect: "error"` turns into a failed request, or as a TLS failure), so only something the device trusts between the page and the API could send one (the API's edge, or a TLS proxy installed on the device), never the server's answer about the link. One that is JSON without a name is the server's answer.

**The live region** (`liveRegion`): one `role="status"`, `aria-live="polite"`, `aria-atomic="true"` element, in the HTML before any update, holding each state's title and line and nothing else. It stays polite after Retry; the script never turns it off, never focuses a heading, and sends no alert. Retry and Get Tadayo are outside it. PR #94 turned the region off after Retry and moved focus to each part's first line; both go.

**Retry** (`afterRetry`, `focus`): a button outside the region, shown in the failed state and, busy, in the checking state that follows Retry. A click while busy does nothing (the guard is the script's, not `disabled`, which would drop focus). Busy: `aria-disabled="true"`, its description "In progress" (`handoff9.check.busy.value`) followed by its hint (frame 12 keeps both: `aria-describedby="retry-busy retry-hint"`), the label still "Retry", a decorative spinner (`aria-hidden`) to the label's left. Not busy: its description is the hint "Try checking this invitation link again.". The first load moves no focus. After Retry, the checking state is drawn before the answer replaces it, however soon the answer comes (a request that fails at once, offline): the page waits for one drawn frame (`requestAnimationFrame`, then a task) beside the answer, so the region's text changes twice and is read; the first load waits for nothing. When the answer after Retry is a failure, Retry stays where it is, with the focus on it if the person left it there. When the answer is final (invited or unavailable), Retry goes; if it had the focus, the focus moves to Get Tadayo, and otherwise it stays where the person put it.

**The spinner:** an inline SVG of the frame's eight ticks (frame 12: centre, radii 4.32 to 6.88, stroke 2 with round caps, opacity 0.125 to 1 in eighths, `onAction`), 16 px square, its right edge 8 px from the label, which stays where it is without the spinner; turning in eight steps a second, and still under `prefers-reduced-motion: reduce`.

**Without JavaScript** (`noScript`): the wordmark, "Turn on JavaScript to check this invitation." (body, secondaryText) in a `<noscript>` where the state's title goes, and Get Tadayo. The checking part is hidden in the HTML and shown by the script when it starts, so a page with JavaScript off never says it is checking; Retry is hidden in the HTML too.

**Get Tadayo's hint** (`getHint`) follows its destination: "Open TestFlight in the App Store." under FQ133's trial address, in every state, the unavailable page's too. Handoff 4 gave the unavailable page's link the spoken name "Get Tadayo from the App Store." (`unavailable.web.get.vo`); handoff 9's precedence map supersedes it (`precedence.getHint`: "FQ133 trial TestFlight link never uses a Tadayo App Store claim"; `precedence.rule`: later guidance supersedes conflicting earlier guidance), so its name is "Get Tadayo", its visible label, in every state (review round 1, S1 and W2). Its name and hint are in the HTML and never change.

**Layout** (`defaultGeometry`, at a 393 px viewport): the wordmark 144 × 45.64 from 124; in checking, failed and the no-JavaScript state, the status block from 260 (90.36 under the wordmark), at least 132 high, then Retry's slot 32 under it (424 to 474, 353 × 50, radius 13, `action` with `onAction` text, `actionPressed` while pressed, the brand's focus ring), and Get Tadayo's target 16 under that (490 to 540); the title's line 16 above its body. The contract's `statusBlockMinimum` is 134 with "+2 optical allowance", and its rects put Retry at 424, which is 132 + 32 from 260: the page follows the rects, which the SVG draws. Text in `rem`, gaps and the slot's least height in px, so at 200% text the text doubles, the blocks grow and the page scrolls (`textZoom200`); Retry and its slot are at least `max(50px, 2.75rem)` high, as Get Tadayo's target already is. At 200% the status block grows with its text, so a failure's block is taller than the checking's. From Retry to the answer the page holds the block at the height it was drawn at (`min-height` from its drawn height, fractions included), so Retry and Get Tadayo stay under the person's finger (`layout`: "Both controls keep position between checking and failure"; review round 1, S2); the hold goes with the answer, so a final answer's own layout follows. The first load holds nothing. Dark: the dark tokens, `onAction` `#18233B` on `action` `#AFBEFF` (`dark`). The invited and unavailable states keep their gaps from PR #94. On iOS Safari a button shows its `:active` colour (`actionPressed`) only when the page listens for `touchstart`, so Retry gets a passive listener that does nothing, and `-webkit-tap-highlight-color: transparent`, so Safari's grey tap highlight doesn't cover that colour (review round 1, S3; to check on the founder's iPhone).

**Another link in the same tab:** opening a second invitation link while the page is open changes only the address's fragment, which reloads nothing, so the page reloads itself on `hashchange`: what it shows, and what Retry asks about, is always the address's link's (review round 1, W3, which was so since PR #94).

## 2. Tests first (`apps/web/src/page.test.ts`)

- What each answer means: a failure carries its reason, network or answered, for each status, body and error above; the page with no API named is answered.
- What the page shows: one part at a time; the failed part shows its reason's line alone; Retry hidden but in failed and in a checking after Retry; Get Tadayo's hint and name by state.
- Retry: busy while it checks (`aria-disabled`, "In progress", still shown), a second click while busy asks nothing, focus never moved on a failure; a final answer moves the focus to Get Tadayo only if Retry had it; the first load moves none; the live region is never turned off.
