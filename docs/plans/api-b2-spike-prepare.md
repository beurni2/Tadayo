# B2: Spike S2's server half: the worker's photo preparation (`api/b2-spike-prepare`)

The worker's outbox poller and its first event handler, `upload.prepare`: what `completeUpload` starts (spec 32, 33, 34; TECH-DESIGN sections 1, 5 and 6, "Media pipeline", step 2; ADR-014, ADR-024; T1, T10, T12, T21, T52, T54, T56; D09; FQ8, FQ10). Made from `main` at `2312359`, PR #109's merge.

## 0. Where this sits, and the decisions

1. **S2 needs the worker's preparation, timed on `dev`.** `docs/plans/B0.md` section 4: "the worker's preparation (signature, limits, metadata stripped, renditions), timed on `tadayo-api-dev`", on S1's branches; `docs/MILESTONES.md`, S2: "A 48-megapixel photo from an iPhone camera reaches the server as a JPEG of at most 4096 px with no GPS. The worker validates it and makes the renditions within the chosen Fly machine's memory, with the time measured (ADR-014)." `docs/plans/api-b2-spike-uploads.md` section 0.1 schedules this PR between the upload intent (PR #109, merged) and the commit (`api/b2-spike-commit`), since only a ready upload can be committed. This PR builds the worker's half as B3 will keep it:
   - **Here:** the outbox poller (section 1), the `upload.prepare` handler with `sharp` (sections 2 to 4), the worker's Storage client and the probe's controls for it (section 5), and a line per preparation with its times and the worker's peak memory (section 6).
   - **Not here:** the device conversion to JPEG (the ios lane's, ADR-014); the measured run itself, which needs the founder's 48-megapixel photo (the B0 plan's F9), the commit PR, the ios lane's share-extension build, and the `dev` worker started (`ops` `worker-scale --to started`, on the founder's yes; it has stayed stopped since PR #70); reading the worker's lines from `dev`, which needs an `ops` entry, so a CI-configuration PR (T58), with S2's report; the purge of lapsed uploads and their renditions (B3); a moderator's decision on a held upload (no provider holds anything in the trial, FQ8); Live Photos' motion (FQ10: the still only); the conversation photo's thumbnail (B6) and the avatar's renditions (the avatar's PR).
2. **No migration and no contract change.** `app.outbox_events` (0009), `app.uploads` and `app.upload_renditions` (0006, 0011) already hold everything: the states, the rejection codes, the scoped content hash, the content version, and each rendition's key, size and dimensions, written once. No route changes: `getUpload` and `completeUpload` already answer `ready`, `held` and `rejected` with `rejection`, by an explicit field list (`services/api/src/media/uploads.ts` `uploadBody`; T55), and nothing a preparation writes is in it.
3. **`sharp` 0.35.5** (`services/worker/package.json`, exact, as every dependency is pinned). Published 27 September 2026. It has no install script: its native part comes as prebuilt optional packages (`@img/sharp-linux-x64` and `@img/sharp-libvips-linux-x64` for the image's glibc, Debian trixie), so `pnpm-workspace.yaml`'s `allowBuilds` needs no new entry, and the Dockerfile none (`pnpm install --prod --filter "@tadayo/worker..."` already installs the worker's dependencies). Its other dependencies are `@img/colour`, `detect-libc` and `semver`. The worker alone imports it: the API never decodes an image.

## 1. The outbox poller (T54; TECH-DESIGN section 5, "The worker"; spec 34)

`services/worker/src/outbox.ts`. One event at a time, as the machine has one shared CPU and 512 MB (`fly.toml` `[[vm]]`), and `sharp` runs one task at a time (section 4).

1. **Claim, in its own short transaction.** The clock's sample (T1: the dev clock moves it, the tests' fake clock holds it), then the oldest due event of a topic this worker handles, `state = 'pending' AND available_at <= sample AND topic = ANY(handled)`, `ORDER BY available_at, id LIMIT 1 FOR UPDATE SKIP LOCKED`, through the partial index `outbox_events_due`. A topic no handler knows is never claimed, so an event a newer API writes waits for a worker that knows it. The claim counts the attempt and leases the event: `attempts + 1`, `available_at = sample + LEASE` (5 minutes), and commits.
   - **Why the attempt is counted at the claim, outside the work:** a photo that killed the process (memory, a crash in native code) would roll back an attempt counted in the work's own transaction, and come back for ever, killing the worker each time. Counted at the claim, it comes back once its lease has passed, at most `MAX_ATTEMPTS` times.
   - **Why a lease rather than one transaction around the work:** the work downloads up to 20 MiB, decodes and uploads; a transaction held open across it would keep a connection and the event's row lock for seconds of network and CPU. The lease does what the lock did: nobody else claims the event while it lasts.
2. **Already spent:** an event claimed with `attempts >= MAX_ATTEMPTS` (5) becomes `dead` at once, `processed_at` the sample, `last_error` `lease_lapsed`, and the alert line is written (item 5). Its last attempt never reported back: a last attempt that failed dies as it reports (item 3). Until PR #111's first review (R1-3) it kept an earlier attempt's code, which pointed at that attempt's failure rather than at the one that never came back; each earlier attempt's code is in its own line.
3. **The work**, outside any transaction: the handler for its topic (section 2), given the payload, which holds ids alone (T52). It ends one of three ways:
   - **Done:** the handler's own last transaction marks the event `done` with `processed_at`, in the same transaction as the change it records, so the change and the event's end commit together (section 2, step 6).
   - **Failed, to be tried again** (Storage away, a timeout, a database error): a new transaction sets `last_error` to the failure's code (item 4) and `available_at = sample + BACKOFF × 2^(attempts − 1)` (30 seconds, then 1, 2 and 4 minutes), or, at `attempts >= MAX_ATTEMPTS`, `dead` with the alert.
   - **Only over its own claim** (R1-7): a failure is written where the event is still `pending` and its `attempts` are still this attempt's. If the attempt outlived its lease and another worker claimed the event, the newer claim's attempt decides, and the older one's failure writes nothing and says nothing.
   - **Failed for good** (a payload that names no upload, a purpose not built yet): `dead` at once, with its code and the alert. Retrying it would end the same way.
4. **Codes, never messages** (T52; 0009's `last_error` check): `storage.unavailable`, `image.timeout`, `db.<SQLSTATE>`, `sys.<code>` (a system's or the driver's own code, lower-cased: a lost connection), `unknown` (anything else), `payload`, `purpose.<purpose>`, `topic` (a claimed event no handler knows, which the claim's own filter keeps from happening), `lease_lapsed` (`outbox.ts` `failureCode`). An error's message can quote a row or a URL, so it reaches neither the row nor the log.
5. **The dead letters' alert.** TECH-DESIGN: "a dead-letter table that raises an alert". The dead-letter table is `outbox_events` with `state = 'dead'` (0009), and the alert is a line on the worker's standard error, `worker: an event is dead: <topic> <event id> after <n> attempts: <code>`, which Fly's logs keep. Nothing pages anyone yet: that is monitoring's (B9, spec 34: "Operators can see pending job age and failed deletion tasks"), recorded in `docs/LIMITATIONS.md`. Each line is written as soon as what it says is committed (`outboxPass`'s `warn`), so a pass that then fails, or runs on while events keep coming, loses or holds back none (R1-2). A dead event is put back by an operator setting it `pending` with `attempts = 0` and `processed_at = NULL` (0009's check ties `pending` to no `processed_at`); no script does that yet.
6. **A pass drains, then waits.** `outboxPass` claims and runs events until none is due or the worker is told to stop, then returns; its own loop (`runLoop`, `loop.ts`) runs it again a second later. Generation keeps its own loop, a pass a minute. A second's wait is a cheap indexed read of a table that holds a few rows, and it is what makes a photo ready within about two seconds of its completion on top of the work itself; `LISTEN`/`NOTIFY` would be quicker but needs a connection outside the pooler's transactions, which nothing else here needs.
7. **A stop** finishes the event in hand, then claims no other (each step of the work is bounded, section 2). If Fly's 30 seconds (`kill_timeout`) run out first, the process ends; the event's lease passes and the next worker tries it again, with that attempt counted. Nothing is half written: the upload changes in one transaction, after every rendition is stored.
8. **Each transaction has the limits generation's have**: `lock_timeout` 5 seconds, `statement_timeout` 10 seconds (`generation.ts` `LOCK_WAIT_MS`, `STATEMENT_MS`).

## 2. `upload.prepare` (TECH-DESIGN section 5, "Media pipeline", step 2)

`services/worker/src/prepare.ts`, for the event `markPreparing` writes (`packages/domain/src/media/upload.ts`): dedupe key `upload.prepare:<upload id>`, payload `{ upload_id }`.

1. **The payload:** an object whose `upload_id` is an id (`app.id`'s pattern), else failed for good (`payload`).
2. **The upload, read with no lock:** its owner, purpose, state, object key, declared type and expiry. No row (it can't be deleted while an event names it, but a later purge may), or a state other than `preparing`: nothing to do, and the event is done. So a repeat of the event, or an event for an upload another run already prepared, changes nothing (T54). An upload past its `expires_at` (by the clock's sample in that read, `uploadToPrepare`) is nobody's (`docs/plans/api-b2-spike-uploads.md` section 0.6): nothing is made for it, and the event is done; it stays `preparing` until B3's purge. One that lapses during the work is found lapsed again under the record's lock (step 6), and nothing is recorded; its renditions, already stored, are found by its key (section 4.5).
3. **The purpose:** `drop_photo` and `replacement` are a drop's photo and get `display` and `full` (TECH-DESIGN section 1, "Images"). `avatar` and `conversation_photo` aren't built (their uploads can't be made yet: `createUpload` answers NOT_FOUND for both), so their events fail for good (`purpose.avatar`, `purpose.conversation_photo`) rather than make renditions their PRs would have to change.
4. **The original**, from the private bucket `uploads` with the service key (section 5), read to at most 20 MiB and one byte. Not there: rejected `unreadable` (the bytes can't be read, and `completeUpload` saw them there, so they won't come back). Storage away or slow: failed, to be tried again.
5. **The checks and the renditions** (sections 3 and 4), from the bytes alone: rejected with its code, or ready with `display` and `full`, each stored in `renditions` before anything is written to the database.
6. **One transaction:** the upload's row `FOR NO KEY UPDATE` (as `markPreparing` locks it: no key column changes, so the renditions' foreign keys, which lock it `FOR KEY SHARE`, don't wait on it); the clock's sample, after the lock (T1); still `preparing` (another run may have finished first) and live by that sample (R1-5), then:
   - rejected: `state = 'rejected'`, `rejection` its code;
   - ready: a row in `app.upload_renditions` for each (its kind, its key, width, height, byte size, `created_at` the sample), then `state` by the safety provider (`ready`, or `held` if it held the photo; section 2.8), `content_hash` and `content_version`;
   - and the event `done`, `processed_at` the sample, in the same transaction. If the upload had left `preparing`, or lapsed, only the event is done.
7. **The scoped content hash** (T21; 0006: "A hash of the bytes scoped to the owner, so it never matches another account's photo"): HMAC-SHA-256 of the original's bytes, keyed by `tadayo.upload.v1:` and the owner's id. The same photo uploaded twice by the same account matches, so the commit can answer "View existing" for a second add of it to the same day (T21, `api/b2-spike-commit`); two accounts' hashes of the same photo never match, and the hash says nothing about the bytes to anyone without the owner's id and the photo. **The content version** is random, `mv_` and 128 bits (`newId`), never derived from the bytes (0006; T21): the photo's `media_version`, which B3's media route gives as its ETag.
8. **The safety provider (FQ8):** an interface, `SafetyProvider`, which is given the original's bytes and answers `clear` or `hold`, and the provider `none` for the closed trial, which answers `clear`. FQ8's default: "the pipeline has a provider interface, with the provider set to `none` for the closed trial of invited friends", and a provider is required before anyone outside the trial joins (Gate D). So nothing is held yet, and `held`'s way out (a moderator's `ready` or `rejected`, 0006's guard) waits for a provider and the operator scripts.

## 3. The checks (D09, spec 33, ADR-014)

`services/worker/src/image.ts` `prepareImage(bytes, declaredType)`, pure but for `sharp`, in this order, so the cheapest refusal comes first and nothing is decoded that a header refuses:

1. **Size:** more than 20 MiB (D09; `UPLOAD_MAX_BYTES`): `too_large`. Storage's bucket refuses a larger `PUT` already (`tools/ops/src/storage-setup.ts`); this holds if that setting ever changed.
2. **The file signature, from the real bytes** (spec 33: "Validate actual file signatures ... rather than trusting extension or MIME label"): JPEG `FF D8 FF`; PNG `89 50 4E 47 0D 0A 1A 0A`; WebP `RIFF`, four bytes, `WEBP`. Anything else: `unsupported_type`. A signature that isn't the type the intent declared is `unsupported_type` too: the device always sends what it declared (ADR-014), so a mismatch is a broken or hostile client, and the strict reading costs nobody a photo.

   Then **the file's structure, walked before any decoder reads it** (FQ138, added after PR #111's third review, R3-2 and R3-6, and the lane's own probes): two shapes no encoder makes cost a decoder time, or memory, out of all proportion to the file.
   - A JPEG of more than 100 scans (`MAX_JPEG_SCANS`): `unsupported_type`. libjpeg takes in every scan before it gives a row, in one step no timeout interrupts, and each scan is a pass over every block of its component: one of 2,688 scans, at the budget, took 20 seconds where `sharp`'s own progressive JPEG of the same size, 10 scans, took 0.7. `jpegScans` counts the SOS markers as libjpeg finds its markers, up to the first EOI: a marker segment is passed over by its length, so a thumbnail inside an EXIF block isn't counted, and in a scan's data a marker is a 0xFF followed by a byte that isn't a stuffed 0x00, a fill 0xFF, a restart or TEM. An encoder's progressive JPEG has about 10 scans; `jpegtran`'s scan scripts allow 100.
   - A WebP of more than 1,000 chunks at its top level (`MAX_WEBP_CHUNKS`): `unsupported_type`. A still image has at most six, an animation one more for each frame. libwebp keeps a record of every chunk, and libvips finds each frame by walking that list from its start: a 20 MiB file of 2.6 million empty chunks held 400 MiB, and 20,000 frames took 4.6 seconds, a time that grows with the square of their number (5,000 took 0.54 s, 10,000 took 1.23 s).
   - A WebP whose RIFF size isn't its length (`webpChunks` undefined): `unreadable`. libwebp reads no further than the size says, and a check that read on would see what the decoder doesn't: round 3's one-frame animation kept its `ANMF` frame inside the RIFF and had a still `VP8 ` chunk's 8 bytes after it, so the chunks read past the RIFF said "lossy", counted 0, while libvips decoded the animation (R3-2: 210 bytes, 467 MiB). `webpCoding` too now stops at the RIFF's end.
3. **The decoder, limited to those three, whatever the bytes say** (spec 33: "Reject active formats"): at the worker's start, `sharp.block({ operation: ["VipsForeignLoad"] })` blocks every libvips loader, then `sharp.unblock` allows `VipsForeignLoadJpegBuffer`, `VipsForeignLoadPngBuffer` and `VipsForeignLoadWebpBuffer` alone (`sharp`'s own example of an allow list, `utility` in its source). The prebuilt libvips can read SVG, PDF-like and other formats; with this, a file that slipped past the signature check is refused by the decoder too. Tested (`image.test.ts`, "decodes none but the three, even past the signature check"): GIF, TIFF, AVIF and SVG bytes, given to the decoder itself with no signature check, are each refused, and the three allowed are read. HEIF bytes were refused the same way in the session; `sharp`'s prebuilt libvips can't write one for a test.
4. **The header:** `sharp(bytes, { limitInputPixels: false }).metadata()`, which reads the header and decodes no pixels; with the pixel limit on, `metadata()` itself throws "Input image exceeds pixel limit", which would leave the code to read an error's words. Its `format` must be the signature's (else `unsupported_type`); its width and height whole and positive, and their product at most 64 megapixels, 64,000,000 pixels (D09), else `too_many_pixels`. A header that can't be read: `unreadable`.
5. **What the decode would hold** (FQ138, added after PR #111's first review, R1-1, and widened after its second, R2-1 and R2-2): most decodes here stream, a few rows at a time. Five kinds hold the whole image before they give a row, and `heldBytes` counts each from the header and, for a WebP, its chunks:
   - A JPEG whose data comes in more than one scan (progressive, or each component in a scan of its own, which libvips reports as `isProgressive` too: seen in the session with a file `jpegtran -scans` made) keeps every coefficient, 2 bytes for each of a component's samples. Counted: every component at full size, padded to 32-pixel MCUs, which is the most a subsampled one needs.
   - An interlaced PNG keeps every pixel. Counted: its samples at 1 byte, or 2 at 16 bits.
   - A lossless WebP (`VP8L`) keeps every pixel as ARGB. Counted: 4 bytes a pixel.
   - A lossy WebP with an `ALPH` chunk keeps its alpha plane, and when that alpha is coded losslessly with a predictor, the lossless decoder's 4 bytes a pixel as well (a 1.06 MB file of 64 megapixels added 340 MiB). Counted: 5 bytes a pixel. An alpha coded as a palette decodes in less, which is why `sharp`'s own large images with alpha stayed small; the code doesn't read how the alpha is coded, so it counts 5 either way.
   - An animated WebP (libvips gives `pages` to every WebP that says it is animated, even one of a single frame, and to no still one) composites each frame onto a canvas of 4 bytes a pixel, beside another. Measured up to 9.2 bytes a canvas pixel, with a full first frame whose alpha is coded losslessly and then a small frame at the far corner. Counted: 10 bytes a canvas pixel, for any `pages` at all: round 2's count took `pages` above 1, and round 3 found a single small frame on a 64-megapixel canvas, which libvips puts on its canvas whole (R3-2). A file of a few hundred bytes can name a 64-megapixel canvas.

   `webpCoding` reads a WebP's chunks as libwebp does: the first `VP8 ` or `VP8L` at the top level, and whether an `ALPH` came before it. A WebP whose coding can't be read that way (an animation's frames sit in `ANMF` chunks) counts 10 a pixel, as an animation. A lossy WebP with no alpha streams, as libvips gives libwebp the scale it needs, and counts nothing.

   Within 64 megapixels the counts reach 610 MiB (an animated WebP), and the reviews measured the process at up to 776 MiB during one preparation. More than 128 MiB (`MAX_HELD_BYTES`) is `too_many_pixels`, the closest of 0006's codes. The app never sends one (a baseline JPEG of at most 4096 pixels a side, or a screenshot's PNG, and never a WebP: ADR-014), and a 4096-pixel progressive JPEG still fits.
6. **All of it, in a process of the photo's own** (FQ138, after PR #111's third review, R3-1, R3-3 and R3-4; `services/worker/src/image-process.ts` `prepareIsolated`, `services/worker/src/image-child.ts`). Three reviews each found a hold no header shows: round 3's were a PNG's compressed text (`zTXt`, `iTXt`), which libpng inflates as it reads the header (a 50 KB file whose one text inflates to 49 MiB took the process to 398 MiB, four texts of 40 MiB to 943 MiB), and a lossless WebP's Huffman tables (a 1-megapixel image of 65,536 groups took the process to 488 MiB). And glibc's allocator keeps much of what a long-lived process freed, so photos that each pass every check grew the worker photo by photo (R3-3). No count from a header can close that, so the worker never decodes a photo itself:
   - **The child.** For each photo the worker starts a Node process (`fork`) that runs `prepareImage` on the one photo it is sent, answers and exits, and whatever it held goes back to the system with it. It is given the declared type and the decode's limit as its arguments, says it is ready over Node's channel, then reads the photo's bytes from its standard input, which the worker writes without a copy (a copy sent over the channel grew the worker by each photo). Its answer, the renditions and its own peak, comes back over the channel (`serialization: "advanced"`, so the renditions arrive as bytes).
   - **Its memory.** The worker reads the child's peak resident memory (Linux's `VmHWM`, which only rises) from `/proc/<pid>/status` every 10 ms, and past 352 MiB (`PEAK_BYTES`) kills it with SIGKILL: the photo is refused as `too_many_pixels`, as for a decode past the budget (step 5). A child that reports a peak past it is refused the same way, as is one that SIGKILL ends though the worker didn't send it: the child writes 1000 to its own `oom_score_adj`, so should the Machine run out between two reads, the kernel's out-of-memory killer takes the child, not the worker. 352 MiB is above the largest peak of any photo the checks take (section 4.4: 324 MiB, an interlaced PNG at the budget), and with the worker's own memory while it waits (96 MiB with its modules loaded, measured, and the photo's 20 MiB at most) within the Machine's 512 MB, 488 MiB. Over many photos the worker rises by up to 92 MiB more, memory freed but not yet given back (section 4.4), so a child near the cap can reach the Machine's end: then the out-of-memory killer takes the child, and the photo is refused all the same. A photo the size the app sends peaks at 137 to 148 MiB.
   - **Its time.** Past 150 seconds (`DEADLINE_SECONDS`: the header, both decodes at their 60-second limit, and the child's start), the child is killed and `ImageTimeout` thrown, as for a decode's own timeout, which libjpeg can outlast, as it takes in every scan of a progressive JPEG in one step. The outbox tries a timeout again.
   - **Its other ends.** A child that dies otherwise once it holds the photo (a decoder's crash, an allocation refused) refuses it as `unreadable`. A child that ends before it is ready for the photo, whose code throws, or whose answer isn't the shape the worker records (`wellFormed`: each rendition `full` or `display`, its bytes bytes, its width and height whole and at least 1) is a failure, `image.process_failed`, tried again: it says nothing about the photo. `outcomeOf` turns a child's end into its answer, and is tested case by case.
   - **Why not a limit the kernel enforces.** A resource limit on the child's memory (`prlimit`, as the reviewer suggested) can't be used: Node reserves about 1.2 GB of address space as it starts, and in the session it wouldn't start under an address-space limit of 1 GiB (it did at 2 GiB) or a data limit of 512 MiB. So the worker watches the resident memory instead, and the out-of-memory killer is the backstop.
   - **What it gets.** No environment (`env: {}`), so none of the worker's secrets (T56) is in the process that parses a stranger's bytes; no output (`stdio` ignored but for its input and the channel), so nothing it writes reaches the worker's log (T52); no Node flags (`execArgv: []`). It reads the 20 MiB cap from `@tadayo/domain/limits` (`packages/domain/src/media/limits.ts`), not the whole domain, which would cost each child about 45 MiB. When the channel to the worker closes, as it does when the worker is killed, nobody watches the child any more, so it kills itself (SIGKILL): `process.exit` would wait for a decode in progress to finish, and a child whose worker was killed mid-decode lived on 2.3 s in the session, as it could for its two decodes' limits. The lane's own breakage run found that: the test first took the child as soon as it passed 64 MiB, before its decode began, so it ended of its cut-short input either way; the test now waits until the child passes 200 MiB, its decode well under way (tested: a worker killed mid-decode leaves no process behind within a second; breakages X14 and X15).
7. **The decode**, with `limitInputPixels: 64_000_000` again (`sharp` refuses the pixels themselves past it, whatever the header claimed), `failOn: "warning"` (`sharp`'s default, named: "Use the default 'warning' level with untrusted input"), the first frame of an animated file only (`sharp`'s default), and a timeout (`timeout({ seconds: 60 })`). Pixel data that won't decode: `unreadable`. The timeout is the worker's limit, not the photo's fault, so it is a failure to try again (`image.timeout`), not a rejection.

## 4. The renditions (TECH-DESIGN section 1, "Images"; T12; spec 23)

1. **Two, for a drop's photo, JPEG:** `full`, inside 2560 by 2560 px, and `display`, inside 1290 px wide by 2560 px tall, each `fit: "inside"` and `withoutEnlargement: true`, so a smaller photo keeps its size and neither is ever larger than the original. TECH-DESIGN gives `display` "1290 px wide"; the height bound is this plan's, so a long screenshot's `display` is never taller than its `full` (a 1290 by 2796 screenshot gives 1181 by 2560 for both), and every rendition fits 0006's check of 20,000 px. `widget` waits for widgets (FQ9) and `thumbnail` for B6.
2. **Oriented and stripped:** `autoOrient: true`, so the stored pixels are upright and the EXIF orientation is gone; and nothing kept: `sharp`'s output, without `withMetadata`, `keepExif` or `keepIccProfile`, carries no EXIF (GPS, capture time, camera), XMP, IPTC or ICC profile, and is converted to sRGB ("The default behaviour, when withMetadata is not used, is to strip all metadata and convert to the device-independent sRGB colour space", `sharp`'s types). A test puts GPS and a capture date in a photo's EXIF and finds neither, nor any EXIF, XMP, IPTC or ICC block, in either rendition, by `sharp`'s reading and by a search of the bytes.
3. **JPEG at `sharp`'s defaults:** quality 80, 4:2:0, baseline. No source asks for more, and B3 measures the reveal's loading (spec 35).
4. **Memory:** `sharp.cache(false)`, so no decoded image outlives its job, and `sharp.concurrency(1)`, one thread for libvips, as the machine has one shared CPU (`sharp` already chooses one on glibc without jemalloc). Each rendition is its own pipeline from the bytes, one after the other, so no two decodes are held at once; each streams, except the kinds section 3.5 bounds. `display` is not made from `full`'s pixels, which would save a decode's time on `dev`'s shared CPU: S2 measures that time on `dev` first (section 6). Measured in the session, after PR #111's third review, by `services/worker/src/image-memory.test.ts`. It sends each photo through `prepareIsolated`, as the worker does, one at a time, each made from a pattern that isn't one colour (a codec stores a flat image in less, so it would measure a decoder at its best), and takes the child's peak (Linux's `VmHWM`) as the worker reads it. It fails when an honest photo's child passes 352 MiB (`PEAK_BYTES`), when one past the budget isn't refused by its header and chunks under 160 MiB, when a hostile file isn't refused with its code, or when the worker's own peak rises more than 128 MiB over the largest photos sent back to back, twice. On a faster CPU than `dev`'s (so for the memory rather than the time), the child's peak, in five runs (the three greyscale photos in the last two, and once more in a probe of their own):
   - a progressive JPEG at the budget (4704 by 4704): 279 MiB in every run;
   - a progressive CMYK JPEG at the budget (4096 by 4096): 286;
   - an interlaced RGBA PNG at the budget (5792 by 5792): 323 to 324, and 301 once;
   - an interlaced 16-bit RGBA PNG at the budget (4096 by 4096): 310 to 311;
   - three greyscale photos, which reach 64 megapixels within the budget with one or two samples a pixel: a progressive JPEG, 261 to 262; an interlaced 16-bit PNG, 276; an interlaced PNG with alpha, 297;
   - a lossless WebP at the budget (5792 by 5792): 249 to 250;
   - a lossy WebP with a lossless alpha at the budget (5181 by 5181): 251;
   - an animated WebP at the budget (3663 by 3663, its first frame lossy with a lossless alpha): 285 to 286;
   - a 16-bit RGBA PNG of 64 megapixels, which streams: 303 to 304;
   - a baseline JPEG of 64 megapixels turned upright: 170 to 171;
   - a lossy WebP of 64 megapixels: 181 to 182;

The worker itself, the largest honest photos sent back to back twice, went from 66 to 117 or 118 MiB at its peak over 20 photos (three runs) and to 131 or 132 over 26, the greyscale three added (two runs), its children at most 323 to 324 MiB each; before round 3 the worker decoded each photo itself and kept much of what it freed (R3-3). The test first bounded that rise at 64 MiB, and 26 photos took it to 65; a probe of 13 photos sent six times over (78) found where it stops: the worker's peak went 102, 137, 156, 156, 158 and 158 MiB after each 13, from 66, and with a collection forced after each 13 (`--expose-gc`) its memory after the collection went 82, 134, 140, 141, 141 and 142. So it levels off, 75 to 92 MiB above where it started: each photo's bytes and renditions wait for V8, which collects memory held outside its heap lazily, and the allocator keeps much of what is freed (`MALLOC_MMAP_THRESHOLD_` at 128 KiB didn't lower it). It isn't a leak and it isn't a decode, which would pass 250 MiB at the first large photo, so the test's bound is 128 MiB. That process loaded only the photo's process's module; the worker as it runs, with its modules loaded and no photo, is at 96 MiB (measured), and holds the photo's bytes (at most 20 MiB) while the child works. `dev`'s worker Machine has 512 MB, 488 MiB: 96 MiB, up to 92 more, and a child at the cap can pass it, and then the kernel kills the child, as it asked, and the photo is refused as `too_many_pixels`; a photo the size the app sends leaves more than 150 MiB to spare. Before the budget and the child, the reviews measured up to 668 MiB added (round 1: a 64-megapixel 16-bit interlaced PNG, peaking at 773 MiB), a 115 KB animated WebP of 64 megapixels at 689 MiB (round 2), and the texts above (round 3). Round 1's own figures were read from `process.resourceUsage().maxRSS`, which starts a child at the size of the process that started it, and round 2's from a fresh process that loaded `sharp` and the domain before the photo; the figures above, the child's alone, replace both.
5. **The objects:** in the private bucket `renditions`, at `<the upload's object key>/<kind>`: derived from a key that is random and leaves the server only inside the upload's own signed URL (T12, T21), never from the account, the day or the bytes. They are written with upsert on (`x-upsert: true`), which only the service key can do: a run that stored a rendition and then failed before its transaction is tried again and writes over its own object, so no try leaves an object no row names, and B3's purge finds every rendition of an upload from the upload's own key, rows or not. `sharp` is deterministic for the same bytes and options, so a second writer of the same rendition writes the same bytes (tested).

## 5. Storage (TECH-DESIGN section 6; T12, T53, T56)

1. **The worker's client,** `services/worker/src/storage.ts`, with the service key (`SUPABASE_SERVICE_KEY`, a Fly secret, which reaches both process groups) and the project's URL (`SUPABASE_URL`, `fly.toml` `[env]`), which `services/worker/src/start.ts` now requires, as the API's start does:
   - `readOriginal(objectKey)`: `GET /storage/v1/object/authenticated/uploads/<key>` (the probe's control "the service key reads the object back from uploads" proves it on `dev` at every deploy), read to at most 20 MiB and one byte; `null` on Storage's not-found (404 in the body or the status), an error otherwise.
   - `putRendition(key, bytes)`: `POST /storage/v1/object/renditions/<key>` with `content-type: image/jpeg` and `x-upsert: true`.
   - The rules of the API's client (`services/api/src/media/storage.ts`): Storage's real status read from the body (`statusCode`), redirects refused, a timeout on each call (30 seconds), and no key, URL or object key in any message (T52, T56). `projectBase` and `logicalStatus` move from the API's client to `packages/domain/src/media/storage-http.ts`, so the two clients share one reading of Storage's answers.
2. **The probe gains two checks**, `tools/ops/src/supabase-probe.ts`, so the worker's write is proved against real Storage at every `deploy-dev`, as its read already is by the control that reads back from `uploads`: the service key puts an object in `renditions` with `x-upsert: true` and reads it back; it puts other bytes at the same key and reads those back. They are named `worker: …`, not `control: …`: no refusal needs them, so a failure is recorded and the run goes on to the refusals. Its cleanup deletes the object, as it deletes the others. The fake project (`tools/ops/test/fake-supabase.ts`) now honours `x-upsert: true` on a `POST`, as Storage does; it took only a `PUT` as an overwrite before.

## 6. The time measured (S2)

1. **A line per preparation**, on the worker's standard output, with no content (T52): `worker: prepared an upload <id> in <total> ms (read <a>, image <b>, store <c>, record <d>), <ready|held|rejected <code>>, peak memory: worker <w> MiB, photo <p> MiB`. The id is opaque (T52 allows it), so S2's report can find the founder's photo's line. The worker's peak is its own process's (`process.resourceUsage().maxRSS`); the photo's is its child's (section 3.6), the higher of what the worker read and what the child reported, which `sharp`'s native memory counts in, and 0 when no child ran (an original that wasn't there).
2. **The durations come from the time module** (`packages/domain/src/time/stopwatch.ts`, `stopwatch()`), as nothing else reads a clock (TECH-DESIGN section 5; `one-clock.test.ts`). A stopwatch measures and decides nothing: no time rule, lease or due date reads it.
3. **What S2's report will need** (its own PR): the line of the founder's photo from `dev`, read through an `ops` entry, and the same pipeline run on the worker's Machine on the largest inputs D09 allows. Section 4.4's numbers are the session's, recorded as such.

## 7. What a person sees

- `getUpload` answers `preparing`, then `ready`, or `rejected` with its code, usually within a few seconds of `completeUpload` (TECH-DESIGN section 6). After a rejection the slot takes another photo (`docs/plans/api-b2-spike-uploads.md` section 0.7).
- An upload whose event died stays `preparing` until it lapses 24 hours on, and the app's draft keeps the photo (FQ15). A rejection would say something false about the photo, so the worker doesn't make one up; the alert says an operator must look.
- Nothing about a preparation reaches anyone but the uploader, and the uploader sees only the state and the code (T10, T12, T55).
