# B2: Spike S2's server half: the worker's photo preparation (`api/b2-spike-prepare`)

The worker's outbox poller and its first event handler, `upload.prepare`: what `completeUpload` starts (spec 32, 33, 34; TECH-DESIGN sections 1, 5 and 6, "Media pipeline", step 2; ADR-014, ADR-024; T1, T10, T12, T21, T52, T54, T56; D09; FQ8, FQ10). Made from `main` at `2312359`, PR #109's merge.

## 0. Where this sits, and the decisions

1. **S2 needs the worker's preparation, timed on `dev`.** `docs/plans/B0.md` section 4: "the worker's preparation (signature, limits, metadata stripped, renditions), timed on `tadayo-api-dev`", on S1's branches; `docs/MILESTONES.md`, S2: "A 48-megapixel photo from an iPhone camera reaches the server as a JPEG of at most 4096 px with no GPS. The worker validates it and makes the renditions within the chosen Fly machine's memory, with the time measured (ADR-014)." `docs/plans/api-b2-spike-uploads.md` section 0.1 schedules this PR between the upload intent (PR #109, merged) and the commit (`api/b2-spike-commit`), since only a ready upload can be committed. This PR builds the worker's half as B3 will keep it:
   - **Here:** the outbox poller (section 1), the `upload.prepare` handler with `sharp` (sections 2 to 4), the worker's Storage client and the probe's controls for it (section 5), and a line per preparation with its times and the worker's peak memory (section 6).
   - **Not here:** the device conversion to JPEG (the ios lane's, ADR-014); the measured run itself, which needs the founder's 48-megapixel photo (the B0 plan's F9), the commit PR, the ios lane's share-extension build, and the `dev` worker started (`ops` `worker-scale --to started`, on the founder's yes; it has stayed stopped since PR #70); reading the worker's lines from `dev`, which needs an `ops` entry, so a CI-configuration PR (T58), with S2's report; the purge of lapsed uploads and their renditions (B3); a moderator's decision on a held upload (no provider holds anything in the trial, FQ8); Live Photos' motion (FQ10: the still only); the conversation photo's thumbnail (B6) and the avatar's renditions (the avatar's PR).
2. **No migration and no contract change.** `app.outbox_events` (0009), `app.uploads` and `app.upload_renditions` (0006, 0011) already hold everything: the states, the rejection codes, the scoped content hash, the content version, and each rendition's key, size and dimensions, written once. No route changes: `getUpload` and `completeUpload` already answer `ready`, `held` and `rejected` with `rejection`, by an explicit field list (`services/api/src/media/uploads.ts` `uploadBody`; T55), and nothing a preparation writes is in it.
3. **`sharp` 0.35.5** (`services/worker/package.json`, exact, as every dependency is pinned). Published 27 September 2026. It has no install script: its native part comes as prebuilt optional packages (`@img/sharp-linux-x64` and `@img/sharp-libvips-linux-x64` for the image's glibc, Debian trixie), so `pnpm-workspace.yaml`'s `allowBuilds` needs no new entry, and the Dockerfile none (`pnpm install --prod --filter "@tadayo/worker..."` already installs the worker's dependencies). Its other dependencies are `@img/colour`, `detect-libc` and `semver`. The worker alone imports it: the API never decodes an image.

## 1. The outbox poller (T54; TECH-DESIGN section 5, "The worker"; spec 34)

`services/worker/src/outbox.ts`. One event at a time, as the machine has one shared CPU and 512 MB (`fly.toml` `[[vm]]`), and `sharp` runs one task at a time (section 4).

1. **Claim, in its own short transaction.** The clock's sample (T1: the dev clock moves it, the tests' fake clock holds it), then the oldest due event of a topic this worker handles, `state = 'pending' AND available_at <= sample AND topic = ANY(handled)`, `ORDER BY available_at, id LIMIT 1 FOR UPDATE SKIP LOCKED`, through the partial index `outbox_events_due`. A topic no handler knows is never claimed, so an event a newer API writes waits for a worker that knows it. The claim counts the attempt and leases the event: `attempts + 1`, `available_at = sample + LEASE` (5 minutes), and commits.
   - **Why the attempt is counted at the claim, outside the work:** a photo that killed the process (memory, a crash in native code) would roll back an attempt counted in the work's own transaction, and come back for ever, killing the worker each time. Counted at the claim, it comes back once its lease has passed, at most `MAX_ATTEMPTS` times.
   - **Why a lease rather than one transaction around the work:** the work downloads up to 20 MiB, decodes and uploads; a transaction held open across it would keep a connection and the event's row lock for seconds of network and CPU. The lease does what the lock did: nobody else claims the event while it lasts.
2. **Already spent:** an event claimed with `attempts >= MAX_ATTEMPTS` (5) becomes `dead` at once, `processed_at` the sample, its `last_error` kept, or `lease_lapsed` when it has none (the last attempt never reported back), and the alert line is written (item 5).
3. **The work**, outside any transaction: the handler for its topic (section 2), given the payload, which holds ids alone (T52). It ends one of three ways:
   - **Done:** the handler's own last transaction marks the event `done` with `processed_at`, in the same transaction as the change it records, so the change and the event's end commit together (section 2, step 6).
   - **Failed, to be tried again** (Storage away, a timeout, a database error): a new transaction sets `last_error` to the failure's code (item 4) and `available_at = sample + BACKOFF × 2^(attempts − 1)` (30 seconds, then 1, 2 and 4 minutes), or, at `attempts >= MAX_ATTEMPTS`, `dead` with the alert.
   - **Failed for good** (a payload that names no upload, a purpose not built yet): `dead` at once, with its code and the alert. Retrying it would end the same way.
4. **Codes, never messages** (T52; 0009's `last_error` check): `storage.unavailable`, `image.timeout`, `db.<SQLSTATE>`, `payload`, `purpose.<purpose>`, `lease_lapsed`. An error's message can quote a row or a URL, so it reaches neither the row nor the log.
5. **The dead letters' alert.** TECH-DESIGN: "a dead-letter table that raises an alert". The dead-letter table is `outbox_events` with `state = 'dead'` (0009), and the alert is a line on the worker's standard error, `worker: an event is dead: <topic> <event id> after <n> attempts: <code>`, which Fly's logs keep. Nothing pages anyone yet: that is monitoring's (B9, spec 34: "Operators can see pending job age and failed deletion tasks"), recorded in `docs/LIMITATIONS.md`. A dead event is put back by an operator setting it `pending` with `attempts = 0`; no script does that yet.
6. **A pass drains, then waits.** `outboxPass` claims and runs events until none is due or the worker is told to stop, then returns; its own loop (`runLoop`, `loop.ts`) runs it again a second later. Generation keeps its own loop, a pass a minute. A second's wait is a cheap indexed read of a table that holds a few rows, and it is what makes a photo ready within about two seconds of its completion on top of the work itself; `LISTEN`/`NOTIFY` would be quicker but needs a connection outside the pooler's transactions, which nothing else here needs.
7. **A stop** finishes the event in hand, then claims no other (each step of the work is bounded, section 2). If Fly's 30 seconds (`kill_timeout`) run out first, the process ends; the event's lease passes and the next worker tries it again, with that attempt counted. Nothing is half written: the upload changes in one transaction, after every rendition is stored.
8. **Each transaction has the limits generation's have**: `lock_timeout` 5 seconds, `statement_timeout` 10 seconds (`generation.ts` `LOCK_WAIT_MS`, `STATEMENT_MS`).

## 2. `upload.prepare` (TECH-DESIGN section 5, "Media pipeline", step 2)

`services/worker/src/prepare.ts`, for the event `markPreparing` writes (`packages/domain/src/media/upload.ts`): dedupe key `upload.prepare:<upload id>`, payload `{ upload_id }`.

1. **The payload:** an object whose `upload_id` is an id (`app.id`'s pattern), else failed for good (`payload`).
2. **The upload, read with no lock:** its owner, purpose, state, object key, declared type and expiry. No row (it can't be deleted while an event names it, but a later purge may), or a state other than `preparing`: nothing to do, and the event is done. So a repeat of the event, or an event for an upload another run already prepared, changes nothing (T54). An upload past its `expires_at` (by the clock's sample in that read, `uploadToPrepare`) is nobody's (`docs/plans/api-b2-spike-uploads.md` section 0.6): nothing is made for it, and the event is done; it stays `preparing` until B3's purge.
3. **The purpose:** `drop_photo` and `replacement` are a drop's photo and get `display` and `full` (TECH-DESIGN section 1, "Images"). `avatar` and `conversation_photo` aren't built (their uploads can't be made yet: `createUpload` answers NOT_FOUND for both), so their events fail for good (`purpose.avatar`, `purpose.conversation_photo`) rather than make renditions their PRs would have to change.
4. **The original**, from the private bucket `uploads` with the service key (section 5), read to at most 20 MiB and one byte. Not there: rejected `unreadable` (the bytes can't be read, and `completeUpload` saw them there, so they won't come back). Storage away or slow: failed, to be tried again.
5. **The checks and the renditions** (sections 3 and 4), from the bytes alone: rejected with its code, or ready with `display` and `full`, each stored in `renditions` before anything is written to the database.
6. **One transaction:** the upload's row `FOR NO KEY UPDATE` (as `markPreparing` locks it: no key column changes, so the renditions' foreign keys, which lock it `FOR KEY SHARE`, don't wait on it); the clock's sample; still `preparing` (another run may have finished first), then:
   - rejected: `state = 'rejected'`, `rejection` its code;
   - ready: a row in `app.upload_renditions` for each (its kind, its key, width, height, byte size, `created_at` the sample), then `state` by the safety provider (`ready`, or `held` if it held the photo; section 2.8), `content_hash` and `content_version`;
   - and the event `done`, `processed_at` the sample, in the same transaction. If the upload had left `preparing`, only the event is done.
7. **The scoped content hash** (T21; 0006: "A hash of the bytes scoped to the owner, so it never matches another account's photo"): HMAC-SHA-256 of the original's bytes, keyed by `tadayo.upload.v1:` and the owner's id. The same photo uploaded twice by the same account matches, so the commit can answer "View existing" for a second add of it to the same day (T21, `api/b2-spike-commit`); two accounts' hashes of the same photo never match, and the hash says nothing about the bytes to anyone without the owner's id and the photo. **The content version** is random, `mv_` and 128 bits (`newId`), never derived from the bytes (0006; T21): the photo's `media_version`, which B3's media route gives as its ETag.
8. **The safety provider (FQ8):** an interface, `SafetyProvider`, which is given the original's bytes and answers `clear` or `hold`, and the provider `none` for the closed trial, which answers `clear`. FQ8's default: "the pipeline has a provider interface, with the provider set to `none` for the closed trial of invited friends", and a provider is required before anyone outside the trial joins (Gate D). So nothing is held yet, and `held`'s way out (a moderator's `ready` or `rejected`, 0006's guard) waits for a provider and the operator scripts.

## 3. The checks (D09, spec 33, ADR-014)

`services/worker/src/image.ts` `prepareImage(bytes, declaredType)`, pure but for `sharp`, in this order, so the cheapest refusal comes first and nothing is decoded that a header refuses:

1. **Size:** more than 20 MiB (D09; `UPLOAD_MAX_BYTES`): `too_large`. Storage's bucket refuses a larger `PUT` already (`tools/ops/src/storage-setup.ts`); this holds if that setting ever changed.
2. **The file signature, from the real bytes** (spec 33: "Validate actual file signatures ... rather than trusting extension or MIME label"): JPEG `FF D8 FF`; PNG `89 50 4E 47 0D 0A 1A 0A`; WebP `RIFF`, four bytes, `WEBP`. Anything else: `unsupported_type`. A signature that isn't the type the intent declared is `unsupported_type` too: the device always sends what it declared (ADR-014), so a mismatch is a broken or hostile client, and the strict reading costs nobody a photo.
3. **The decoder, limited to those three, whatever the bytes say** (spec 33: "Reject active formats"): at the worker's start, `sharp.block({ operation: ["VipsForeignLoad"] })` blocks every libvips loader, then `sharp.unblock` allows `VipsForeignLoadJpegBuffer`, `VipsForeignLoadPngBuffer` and `VipsForeignLoadWebpBuffer` alone (`sharp`'s own example of an allow list, `utility` in its source). The prebuilt libvips can read SVG, PDF-like and other formats; with this, a file that slipped past the signature check is refused by the decoder too. Tested in the session: GIF, TIFF, SVG, AVIF and HEIF bytes are each refused, and the three allowed are read.
4. **The header:** `sharp(bytes, { limitInputPixels: false }).metadata()`, which reads the header and decodes no pixels; with the pixel limit on, `metadata()` itself throws "Input image exceeds pixel limit", which would leave the code to read an error's words. Its `format` must be the signature's (else `unsupported_type`); its width and height whole and positive, and their product at most 64 megapixels, 64,000,000 pixels (D09), else `too_many_pixels`. A header that can't be read: `unreadable`.
5. **The decode**, with `limitInputPixels: 64_000_000` again (`sharp` refuses the pixels themselves past it, whatever the header claimed), `failOn: "warning"` (`sharp`'s default, named: "Use the default 'warning' level with untrusted input"), the first frame of an animated file only (`sharp`'s default), and a timeout (`timeout({ seconds: 60 })`). Pixel data that won't decode: `unreadable`. The timeout is the worker's limit, not the photo's fault, so it is a failure to try again (`image.timeout`), not a rejection.

## 4. The renditions (TECH-DESIGN section 1, "Images"; T12; spec 23)

1. **Two, for a drop's photo, JPEG:** `full`, inside 2560 by 2560 px, and `display`, inside 1290 px wide by 2560 px tall, each `fit: "inside"` and `withoutEnlargement: true`, so a smaller photo keeps its size and neither is ever larger than the original. TECH-DESIGN gives `display` "1290 px wide"; the height bound is this plan's, so a long screenshot's `display` is never taller than its `full` (a 1290 by 2796 screenshot gives 1181 by 2560 for both), and every rendition fits 0006's check of 20,000 px. `widget` waits for widgets (FQ9) and `thumbnail` for B6.
2. **Oriented and stripped:** `autoOrient: true`, so the stored pixels are upright and the EXIF orientation is gone; and nothing kept: `sharp`'s output, without `withMetadata`, `keepExif` or `keepIccProfile`, carries no EXIF (GPS, capture time, camera), XMP, IPTC or ICC profile, and is converted to sRGB ("The default behaviour, when withMetadata is not used, is to strip all metadata and convert to the device-independent sRGB colour space", `sharp`'s types). A test puts GPS and a capture date in a photo's EXIF and finds neither, nor any EXIF, XMP, IPTC or ICC block, in either rendition, by `sharp`'s reading and by a search of the bytes.
3. **JPEG at `sharp`'s defaults:** quality 80, 4:2:0, baseline. No source asks for more, and B3 measures the reveal's loading (spec 35).
4. **Memory:** `sharp.cache(false)`, so no decoded image outlives its job, and `sharp.concurrency(1)`, one thread for libvips, as the machine has one shared CPU (`sharp` already chooses one on glibc without jemalloc). Each rendition is its own pipeline from the bytes, so each streams the decode rather than holding the whole image. Measured in the session (a faster CPU than `dev`'s, so for the memory rather than the time; section 6): a 12-megapixel JPEG in 0.34 seconds, the process's peak memory 47 MiB over its start; a 64-megapixel PNG in 2.4 seconds, 83 MiB over; a 64-megapixel WebP in 5.1 seconds, 91 MiB over. `dev`'s worker Machine has 512 MB.
5. **The objects:** in the private bucket `renditions`, at `<the upload's object key>/<kind>`: derived from a key that is random and leaves the server only inside the upload's own signed URL (T12, T21), never from the account, the day or the bytes. They are written with upsert on (`x-upsert: true`), which only the service key can do: a run that stored a rendition and then failed before its transaction is tried again and writes over its own object, so no try leaves an object no row names, and B3's purge finds every rendition of an upload from the upload's own key, rows or not. `sharp` is deterministic for the same bytes and options, so a second writer of the same rendition writes the same bytes (tested).

## 5. Storage (TECH-DESIGN section 6; T12, T53, T56)

1. **The worker's client,** `services/worker/src/storage.ts`, with the service key (`SUPABASE_SERVICE_KEY`, a Fly secret, which reaches both process groups) and the project's URL (`SUPABASE_URL`, `fly.toml` `[env]`), which `services/worker/src/start.ts` now requires, as the API's start does:
   - `readOriginal(objectKey)`: `GET /storage/v1/object/authenticated/uploads/<key>` (the probe's control "the service key reads the object back from uploads" proves it on `dev` at every deploy), read to at most 20 MiB and one byte; `null` on Storage's not-found (404 in the body or the status), an error otherwise.
   - `putRendition(key, bytes)`: `POST /storage/v1/object/renditions/<key>` with `content-type: image/jpeg` and `x-upsert: true`.
   - The rules of the API's client (`services/api/src/media/storage.ts`): Storage's real status read from the body (`statusCode`), redirects refused, a timeout on each call (30 seconds), and no key, URL or object key in any message (T52, T56). `projectBase` and `logicalStatus` move from the API's client to `packages/domain/src/media/storage-http.ts`, so the two clients share one reading of Storage's answers.
2. **The probe gains two checks**, `tools/ops/src/supabase-probe.ts`, so the worker's write is proved against real Storage at every `deploy-dev`, as its read already is by the control that reads back from `uploads`: the service key puts an object in `renditions` with `x-upsert: true` and reads it back; it puts other bytes at the same key and reads those back. They are named `worker: …`, not `control: …`: no refusal needs them, so a failure is recorded and the run goes on to the refusals. Its cleanup deletes the object, as it deletes the others. The fake project (`tools/ops/test/fake-supabase.ts`) now honours `x-upsert: true` on a `POST`, as Storage does; it took only a `PUT` as an overwrite before.

## 6. The time measured (S2)

1. **A line per preparation**, on the worker's standard output, with no content (T52): `worker: prepared an upload <id> in <total> ms (read <a>, image <b>, store <c>, record <d>), <ready|held|rejected <code>>, peak memory <m> MiB`. The id is opaque (T52 allows it), so S2's report can find the founder's photo's line; the peak is the process's own (`process.resourceUsage().maxRSS`), which `sharp`'s native memory counts in.
2. **The durations come from the time module** (`packages/domain/src/time/stopwatch.ts`, `stopwatch()`), as nothing else reads a clock (TECH-DESIGN section 5; `one-clock.test.ts`). A stopwatch measures and decides nothing: no time rule, lease or due date reads it.
3. **What S2's report will need** (its own PR): the line of the founder's photo from `dev`, read through an `ops` entry, and the same pipeline run on the worker's Machine on the largest inputs D09 allows. Section 4.4's numbers are the session's, recorded as such.

## 7. What a person sees

- `getUpload` answers `preparing`, then `ready`, or `rejected` with its code, usually within a few seconds of `completeUpload` (TECH-DESIGN section 6). After a rejection the slot takes another photo (`docs/plans/api-b2-spike-uploads.md` section 0.7).
- An upload whose event died stays `preparing` until it lapses 24 hours on, and the app's draft keeps the photo (FQ15). A rejection would say something false about the photo, so the worker doesn't make one up; the alert says an operator must look.
- Nothing about a preparation reaches anyone but the uploader, and the uploader sees only the state and the code (T10, T12, T55).

## 9. Tests first

- **Pure** (`services/worker/src/image.test.ts`, with images `sharp` makes in the test, so no binary fixture is committed): each signature and its mismatch with the declared type; GIF, TIFF, SVG, AVIF, HEIF and plain text bytes refused; more than 20 MiB; more than 64,000,000 pixels by the header (a PNG of 8001 by 8000) and exactly 64,000,000 accepted; a truncated JPEG `unreadable`; each rendition's size for a landscape, a portrait, a long screenshot and a photo smaller than both; EXIF orientation 6 made upright; GPS, capture date, EXIF, XMP, IPTC and ICC gone; the same bytes giving the same renditions; the hash the same for one owner and different for two. (`outbox.test.ts`): the backoff and the codes. (`storage.test.ts`): each call's path, method and headers against a fake `fetch`; not-found; a body past the cap; no key or URL in a message. (`stopwatch.test.ts`.)
- **Postgres** (`tests/src/db/worker-outbox.test.ts` and `worker-prepare.test.ts`, on a freshly made database, with the fake clock and a fake Storage):
  - a completed upload becomes ready, with both renditions' rows and objects, its hash and version, and its event done, in one transaction;
  - each rejection, with no rendition row and the event done;
  - two workers claim different events, and never the same one (`SKIP LOCKED`); an event not yet due, or of a topic no handler knows, isn't claimed;
  - a failure is tried again after its backoff, by the fake clock, and dies after five attempts, with its code and the alert line; a claim whose work never reported back dies at its next claim once attempts are spent (`lease_lapsed`);
  - an event for an upload no longer `preparing`, or lapsed, changes nothing and is done; a repeat of a done event's work changes nothing;
  - a rendition stored, then a failure before the transaction: the retry writes over the same objects and the upload is ready once;
  - two runs of one event recording at the same time: the second waits on the first's lock and then writes nothing, while a row naming the upload (its foreign key's `FOR KEY SHARE`) goes by (the lock is `FOR NO KEY UPDATE`); and a second run that records first leaves the first nothing to write.
- **The privacy matrix** (`tests/src/privacy/matrix.test.ts`): after the uploads' table completes an upload with a real photo's bytes, the worker's handler prepares it, given that upload's own event as a claim gives it (a whole pass would take every other file's events of the topic too), so later phases read a ready upload by every role (its owner's alone, T12, T14), and the leak scanner looks for its renditions' keys and its content version in every answer, as it already looks for every object key and version in the world.
- **The probe's own tests** (`tools/ops/src/supabase-probe.test.ts`): the two checks, with the worker's method, type, key and `x-upsert`; a Storage that refused the upsert, or kept the first bytes, fails the run and the refusals still run.
