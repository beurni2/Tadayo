## 2. Slices in order

Each slice is one PR, reviewed as `docs/GITHUB.md` says. A slice that touches authorization, the database, time, idempotency, media, caches, tokens, notifications or the video viewer also gets the privacy and security review. Sizes aim at under 400 hand-written lines.

**Two threads (ADR-025).** Slices 1, 2 and 9 run first, in the api thread alone, with slice 9 moved up from after slice 8. Once `ios.yml` has run green on the latest check branch, the ios thread builds slices 11 and 11b while the api thread builds 3 to 8 and 10a. Then 10b, the steps after it, 10c and 12 each go up with nothing else open in either thread, and the spikes follow one at a time. `docs/MILESTONES.md`, "Lanes", gives the rules both threads keep. The table below lists slice 9 after slice 2; slices 11 and 11b run beside 3 to 10a, and if 11b hasn't started when 10a has merged, it starts once 10c has merged.

**Workflow files decide the order** (`docs/GITHUB.md`, "Workflow files"):
- A workflow PR is ready only when no other branch of either thread that is meant to merge exists, opened as a PR or not (a branch waiting for a design upload, and a slice in progress, included; `ios/b0-ios-check`, `draft/b0-plan` and `evidence` never merge and don't count), because after it merges every such branch has to merge `main`, and whether the session can push such a merge, one that brings a workflow change, hasn't been tested. "Nothing else open" in the table below means the same.
- So no branch waits across a workflow merge: each feature branch that comes after a workflow is made from `main` once that workflow has merged. The `ci.yml`, `ios.yml`, `ops.yml`, `deploy-dev.yml` and `ios-release.yml` PRs (2, 9, 10b, 10c, 12) each go up with nothing else open.
- If a branch in progress can't be finished without a workflow change (for example, slice 11's snapshot runs show a fault in `ios.yml` itself, not in `tools/ci/`), that branch is set aside, and the other thread finishes or sets aside any branch of its own that is meant to merge (`docs/MILESTONES.md`, "Lanes", "A freeze before every workflow PR"). A branch set aside has its PR, if opened, closed with a comment linking the workflow PR, and no longer counts. The workflow PR goes up alone, once the other thread's branch has merged or been set aside, and once the workflow PR has merged each slice set aside is re-applied on a fresh branch from `main` (`docs/GITHUB.md`, "Workflow files").
- `ci.yml` comes second, so every later PR has `ci`. Its first push was the one-time test of whether the session can push a workflow file, and its merge the one-time test of whether the session can merge one (ADR-022): GitHub accepted both, on 2026-11-03 (PR #8, `docs/LIMITATIONS.md`), so I push every later workflow file myself, each in its own PR.
