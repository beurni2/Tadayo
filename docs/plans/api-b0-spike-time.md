# Spike S5, Time: `api/b0-spike-time`

The api lane's plan for spike S5 (`docs/plans/B0.md` section 4, row 1; `docs/MILESTONES.md`, the spike table), written before the code, then revised after a critique by fresh reviewers through three lenses (rules: 9 findings; privacy and security: 7; mechanics: 10; each put to a refuter, who upheld 24 at least in part, 3 of them medium or high: the held day's deletion condition, the dev clock on the Machine, the order of work). It is pasted into the PR's Plan section.

S5 retires the time unknowns B0 can reach: that the day's two instants are right in every zone ADR-008 names, and that on `dev`, with the worker stopped and the dev clock moved, what Home shows switches at 07:00 and at 01:00 exactly, by the server's clock alone.

The answer is recorded in the journal and in B0.md section 4's S5 row. Until S5's PR is approved, no freeze is asked for, no `ops` PR opened and `dev` isn't claimed (section 8).
2. **The "minimal Home read" is Home's day choice, read through `listClubs`' `open_day` and `next_day`; the PR asks the founder to confirm it.** `getHome` (B2, by `docs/MILESTONES.md`) can't be built minimally and truthfully in S5: its `day` mode is the day's first page (`RevealedDay`: the drops, their media, reactions, favourites and highlights), B3's, B5's and B6's work, and a `day` with an empty or partial page while drops exist would say something false (T49). The choice S5 tests is the question `getHome` asks first: which day is open now, and which opens next. The contract already asks `listClubs` for exactly that choice, with no page (`open_day`, `next_day`), and `listClubs` is built and in the matrix. So S5 builds the choice once, in the authorization module, and `listClubs` answers with it; `getHome` calls the same function when B2 builds it. The PR's "Risks and open questions" asks: "Does Home's day choice, read through `listClubs`' `open_day` and `next_day`, count as S5's 'Home switches' for Gate 0? Default yes; if not, the live run waits for `getHome` in B2." The founder's approval of the PR and yes for the runs answer it before the dev clock moves. It is FQ103 in `docs/QUESTIONS.md` (raised by the PR's first review), with the default yes.
3. **The live run's club is made by a script, not by `db/seed`.** `tools/ops/src/seed.ts` says the spikes' few occurrences go in `db/seed`. But a seed file can't compute an instant (ADR-008: TypeScript resolves them; the one-clock test refuses any clock in `db/`), so it would carry literal instants for fixed dates, and the dev clock, which only moves forward, would use those dates up on the first run. The run's own script on the Machine (ADR-013: "Demonstrations are scripts in `tools/ops/`") picks dates just ahead of `dev`'s clock, resolves their instants with `dayInstants`, and can run again. `seed.ts`' header is corrected. Either way the observation needs an `ops` entry of its own (no existing script reads the API as a member), so the `ops` PR is the same.

## 2. Home's day choice (`packages/domain/src/authorization/days.ts`)

One function in the authorization module, as `readableDrops` is for drops (T9; TECH-DESIGN section 5's "SQL fragments that filter reads"): `daysByClub(sql, viewer, now)`, a fragment with one row for each of the viewer's clubs, its `club_id`, the day open now and the day that opens next. A caller joins it on the clubs it wants (`listClubs` on the clubs it lists, `getHome` on its path's `club_id`), and it enforces every rule itself, so a guessed or foreign `club_id` finds no row and `getHome` needs no other check. A TypeScript policy states the same rules on loaded facts, and a test runs both on the same rows, as `tests/src/db/authorization.test.ts` does for drops.

- **Only the viewer's clubs.** The viewer's account is active and has an active interval in the club (`EXISTS` on `app.memberships` with `club_id`, `user_id` and `state = 'active'`, as `readableDrops` joins the viewer). A stranger's club, a club the viewer left, or a guessed id gives nothing (T14). A rejoined member sees the club's days on the new interval.
- **Not a suspended club.** A suspended club has no day (Home's `unavailable` mode, spec 22). A proposed or paused club gives the days its rows hold: FQ50 keeps a paused club's announced day until it passes; a proposed club has none (spec 04 confirms days only on activation), and `getHome` puts `awaiting_activation` before `day` anyway.
- **Only a scheduled day.** A suspended or cancelled day is neither open nor next (T5: "the next scheduled occurrence"; spec 06; `occurrences_upcoming` is `WHERE status = 'scheduled'`). Its neutral answer, phase `unavailable`, is `getOccurrence`'s (`UnavailableDay`, spec 22). What Home shows while a suspended day's window is open is B6's (`H01-day-suspended`, section 12).
- **Not a held day.** A day is held, and never open or next, when its star's interval ended before its reveal or its star asked to delete their account before its reveal: `(s.left_at IS NULL OR s.left_at >= o.reveal_at) AND (su.deletion_requested_at IS NULL OR su.deletion_requested_at >= o.reveal_at)`, the read predicate's two star conditions (`read-sql.ts`; `read.ts`' `notBeforeReveal` on `starLeftAt` and `starDeletionRequestedAt`), from one shared source in the module so the two can't drift, whatever the worker that ends the interval has done (T1, T27; FQ63's reading). A day already open when its star leaves or asks to delete stays open to its close, as its drops stay readable.
- **Open:** `reveal_at <= now < close_at`. Two days of a club can't overlap (one date each, `UNIQUE (club_id, local_date)`, and a day ends at 01:00 on the next date, before that date's 07:00); the choice takes the earliest reveal regardless.
- **Next:** the earliest `reveal_at > now`, so while a day is open, `next` is the one after it (H01-quiet's "Next: Nina"). Sunday and unused weekdays never appear, since rows exist only for days a schedule assigns (the insert guard). No row, no `next`: it never invents a date (T49).
- **`now` is the caller's sample,** `Clock.sample(tx)` taken first in the transaction (T1), bound as a `timestamptz`. The function reads no clock.
- **Phase:** `collecting` before `reveal_at`, `open` until `close_at`. The choice never returns a past or unavailable day.
- **The star** as `Person`: the star's interval id; the name: the current `display_name` while the interval is active and no deletion is requested, the interval's `ended_display_name` once it has ended (FQ75), and the current name while a deletion requested during the open day hasn't yet ended the interval; the avatar's version only while the interval is active and the account is `active`. A star whose account was deleted during the open day may have no name at all (the interval's `ended_display_name` can be null for `account_deleted`, and the account's `display_name` is null); then that day is left out, filtered in the SQL as `club-list.ts` leaves out a nameless inviter, never thrown and never sent without a name, and a `docs/LIMITATIONS.md` row keeps it open until B6, which settles a deleted account's days (`OccurrencePhase`; FQ75). `next_day` is unaffected. No B0 route can make that case.

## 4. The privacy matrix and the leak scanner

- **`listClubs`' judge** (`tests/src/privacy/account.ts`) gains the two fields, judged from the world's own rows, never from the answer or a state's name: in the world's club (Europe/London; Ana's Saturday, 2026-11-07, its one day), at `collecting` (reveal less a microsecond) `next_day` is Ana's Saturday in phase `collecting` and there is no `open_day`; at `open` `open_day` is it in phase `open` and there is no `next_day`, the world having no later day; at `past` and a year on, neither. ## 6. The live run's script (`tools/ops/src/spike-time.ts`)

An `ops` script with a runner half and a Machine half, like `supabase-probe`: the runner starts it on the API Machine over SSH (`on-machine.ts`: 300 seconds for the command), where `DATABASE_URL` (as `tadayo_app`), `SUPABASE_URL`, the publishable key and the service key are. It acts only on `tadayo-dev`: the project ref in its database URL and its Supabase URL must match the `--ref` the runner passes from `SUPABASE_DEV_PROJECT_REF`, as the probe checks. Every time it writes comes from `Clock.sample` (the one-clock test scans `tools/ops`); limits are `AbortSignal.timeout`s, which read no clock.

0. **Its limits and its name.** Before it makes anything, it prints `spike-time: run <id>` (a random UUID, which names everything it makes) and starts a budget after which no new work begins (180 seconds: sign-in, the club, two moves, two windows of at most 60 seconds) and a later deadline for the clean-up (240 seconds, a minute inside `COMMAND_SECONDS`, as the probe's). Every Auth call goes through `supabase.ts`' `send` with its own limit; every API call has `AbortSignal.timeout` joined with the budget; each database transaction sets `statement_timeout` and `lock_timeout` locally, before anything else (the club's before dev's clock is checked); a database call still under way when the run's limit comes is left to end on its own, the run going on to its clean-up and saying the club or the move may still commit, and the connection's end waits 5 seconds at most for it.
1. **A reader who can sign in.** It makes a Supabase user with the admin API (`spike-<id>@probe.invalid`, confirmed, no email sent) and signs in with a code from `generate_link`, as the probe does. Through the API at `https://api-dev.tadayo.app`: `GET /v1/me` makes the account, and `PATCH /v1/me` with its `expected_version`, `age_confirmed` and the name `Ana` finishes the profile, so the account is made the product's way and `GET /v1/clubs` passes the gate.
2. **The club, in one transaction, as `tadayo_app`.** First `dev`'s clock, checked as the API checks it at start-up (`prepareClock("dev", tx)`), and the account, which must be the run's own: the subject it signed in as, named `Ana`, its age confirmed. Then a second synthetic person, `Ben` (an account with a random `auth_subject` nobody can sign in as, age confirmed); the club `S5 <first 8 of the id>` in `America/New_York`, Ana its creator; Ben joining by the roster chain the guards require (a proposal, its members, a candidate, the seal, an invitation bound to Ben, the approvals, applied), as `tests/src/db/world.ts`' `joinByRoster` does; `activated_at`; a schedule version from the first day's date with spec 05's four days for a pair (T6): Ana the first date's weekday and one more, Ben the next date's weekday and one more, never Sunday, each `first_date` the first such weekday on or after the version's start; the two occurrences the run needs, the first date's (Ana's) and the next date's (Ben's), with `reveal_at` and `close_at` from `dayInstants` and `collecting_from` the transaction's sample. Ids from the domain's id maker. Instants are bound as text with an explicit cast to `timestamptz` (postgres.js' default would cut them to milliseconds). 3. **The first instant.** It moves the dev clock to 20 seconds before the first day's `reveal_at` with `dev-clock.ts`' `devClock(tx, { to })`, forward only, under the 366-day cap, the schema checked closed before and after. The image has no `tools/ops/sql`, so `devClock`'s `makeSql` becomes optional: without it, a missing `app.dev_clock` is refused, naming `ops dev-clock` as the script that makes it, and nothing is made (dev's API won't start without the table anyway, `prepareClock`; it was made on 2026-11-12). Then it reads `GET /v1/clubs` with the reader's token every 250 milliseconds until five answers after the switch, at most 60 seconds. For each answer: status 200, `Cache-Control: private, no-store`, and the whole `ClubList`, compared key for key with the one T5 gives at the answer's `server_now` (`expectedClubList`: the club's summary and nothing else, no invitation): `open_day` is the first day, phase `open`, exactly when `reveal_at <= server_now < close_at`, and `next_day` is the first day (`collecting`) before it and the next day after. `server_now` is floored to the second and both instants are whole seconds, so the comparison holds exactly at the boundary: an answer at 06:59:59 must not show the day, one at 07:00:00 must.
4. **The second instant.** The same from 20 seconds before the first day's `close_at`: `open_day` gone exactly from `close_at`, `next_day` the next day throughout. Both instants are watched whatever the reveal's window found, except when it had no answer at all: then the close's couldn't either, so dev's clock isn't moved the further 18 hours or so, and a failed check says so.
5. **The end.** It deletes the Supabase user at the end, using only the deadline; if the deadline cuts the clean-up or Auth won't delete it, the run fails naming the user left, and if the call that makes the user had no clear answer (none, a server error, or a 200 with no id), so the user may exist with no id the run knows, the run fails naming the address to delete it by. It never lists Auth's users to look for one, which would read other accounts. The club, its two accounts and its days stay: the schema never deletes them (`0003`, `0005`), and they are synthetic. The account Ana keeps an `auth_subject` whose Supabase user is gone, so nobody can sign in as it.
6. **The report**, one line each: the run, the club's zone and dates, each instant, the dev clock's offset before and after each move, the number of answers on each side of each instant, the last answer before and the first after (their `server_now` and what each showed), the time from the instant to the first answer after it, by that answer's `server_now`, to the second, which is the contract's precision, and the result. (The run reads no clock of its own between reads: the one-clock test scans `tools/ops`, and `server_now` is what T5 is judged by.) An answer with another Cache-Control, or none, is said as such, never by the header's value. A wrong answer is said by where it differs from T5's, by the keys' path only, never a value, and by which of the run's own two days it showed, found by their ids and named and dated from what the run wrote, never from the answer (another club, a day not the run's, or a phase outside the contract's two is said in those words). An Auth failure is said by its status and code only (`supabase.ts`' `describe`); "what it saw" is only ever the API's `ClubList` answers.
