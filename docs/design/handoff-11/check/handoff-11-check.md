## 5. The server

The api lane's PR #145 (`removeCandidate`, `DELETE /v1/candidates/{candidate_id}`, `docs/plans/api-b2-unpropose.md` section 2 on that branch) and handoff 11's section 10 agree on who (the candidate's proposer, an active member; anyone else NOT_FOUND, T14), on which candidates (any open one, accepted or not; a joined one is NOT_FOUND), on the links (all stop at once), on the open revision (a server-made revision without the removed person, everyone else approving and accepting again, the proposer's approval standing, FQ60 and FQ121; or the end when nobody else is open), and on a retry after a lost answer (answered as removed again). They differ in two places, neither of which a frame depends on:
- **No idempotency key.** Handoff 11 asks for one; `removeCandidate` takes none, because repeating it returns the same answer (as `revokeInvitation` does), so a retry can't commit twice (T19 is about commits a retry could repeat).
- **No roster-version guard.** Handoff 11 asks for "a current-roster concurrency guard"; `removeCandidate` names the candidate by id, takes the club's row lock first (as every roster command does), and answers NOT_FOUND for a candidate who joined meanwhile, so the confirmation can't land on another person. What can be stale is the alert's last paragraph, chosen from the roster as last read; the later PR reads Members or the list again after any answer.

A removal of a candidate already ended by something else (a decline, FQ120, FQ121) is answered as removed too, so the app can say "Nina’s invitation was removed." where a decline ended it a moment before: true in what the person sees (Nina's invitation has ended), and it names nobody else's action. The api lane is told these three points.
