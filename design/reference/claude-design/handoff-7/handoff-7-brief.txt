Three rules for frames 1 to 16:
- Busy. Your handoff 1: "Use one in-flight request per primary action. While sending or verifying, keep the button height and label stable, disable repeated submission and expose the busy state accessibly. Do not display a successful transition until the server responds." No frame draws it, and the sheet has no busy state. Frame 2 sets it.
- Failures. A request can fail for want of a connection, or because the server refused or failed. The frame draws the first; give the second's line in writing, and it takes the same place and form unless you say otherwise. Every failure names the action that failed and keeps what Ben typed (T43). It never blames the address or the code for a connection or server problem (your handoff 1: "Never turn a network failure into a wrong-code claim."), and it promises no wait (your handoff 4: a refusal supplies no wait time, so no "shortly" and no invented cooldown).
- Announcements. Give the VoiceOver words for each busy state, each failure and each change of the resend row. Your handoff 1 asks to "Announce errors and resend availability without stealing focus." and delivered no words.
